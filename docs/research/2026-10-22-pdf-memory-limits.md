# PDF解析のメモリ実測と上限の再検討

## 結論

**10MiB・100ページ・12万文字は、通常文書の受付上限として維持する。ただし、これらをメモリ枯渇対策として扱わない。PDF解析をアプリ本体とは別の128MB上限のisolateへ移し、資源超過を取り込み失敗として処理する方式を推奨する。**

ファイル上限を5MiBまで下げると、今回測った日本語論文（5.61MiB、10ページ）を排除する。一方、約66KB・1ページ・抽出本文2,309文字の細工したPDFは通る。ページ数・本文文字数を下げても、この問題は防げない。

本PRは測定ツールと検討結果を追加する。**対策実装、本番での再現、本番設定の変更は含まない。現行の取り込み経路にある資源枯渇の懸念は残っている。** 隔離処理は未実装であり、以下の上限は安全性を保証する設定値ではない。

## 測定方法

- 測定日：2026-10-22。macOS arm64、Node v26.12.1、unpdf 1.9.1、Miniflare 4.20260730.0。測定時のアプリ基点は `a9b3bae`。
- `scripts/measure-pdf-memory.mjs` が既存の `server/pdf.ts` の `extractPdf()` をesbuildでバンドルし、そのまま呼ぶ。パーサー・上限検査・解放処理を別実装に置き換えていない。
- 文書ごとに新しいNodeプロセスと新しいローカルworkerd isolateを使う。NodeはPDF.jsをロードし、入力を読んでGCしてから解析前の値を取る。
- NodeはRSS、JSヒープ、external、ArrayBuffer、起動からの最大RSS、解析時間を記録する。externalはArrayBufferを含むため、両者を足してはいけない。最大RSSにはモジュール読み込み等も含まれる。
- workerdはPDF.jsロード後・解析終了直後のCDP `Runtime.getHeapUsage` を取得する。JSは `usedSize`、バッファ等は `backingStorageSize`。表の2値の和は比較用であり、厳密な課金・上限判定値ではない。
- workerdの値は**終了直後のスナップショットであり、解析途中のピークではない**。本体アプリ全体や同時実行、CPU制限、本番のOOM挙動は測っていない。ローカルで128MiB超の処理が完了しても、本番で許容される証拠にはならない。
- 合成PDFはFlate圧縮した本文ストリームを持つ。異常ケースは可視本文の前に大量の空白を入れ、展開量だけを増やしたもの。外部ネットワーク・本番・保存済みの個人データにはアクセスしない。

## 実測

単位はMiB（1MiB = 1,048,576 bytes）。測定値はGC等で変動する。各ケース1回の代表値であり、統計的な分布ではない。

| 文書               |       PDFサイズ | ページ | 抽出文字数 | Node RSS 解析前→最大 | workerd 終了直後 JS / バッファ等 |
| ------------------ | --------------: | -----: | ---------: | -------------------: | -------------------------------: |
| 合成記事           |     4,843 bytes |     10 |     23,108 |          148.4→161.9 |                        7.0 / 0.9 |
| 合成の長い文書     |    18,434 bytes |     40 |     92,438 |          149.2→170.7 |                        9.6 / 0.9 |
| 英語論文           | 2,215,244 bytes |     15 |     41,066 |          152.6→201.5 |                       15.0 / 3.6 |
| 日本語論文         | 5,878,244 bytes |     10 |     19,239 |          160.1→194.1 |                       13.9 / 8.6 |
| 8MiBの空白を展開   |     8,946 bytes |      1 |      2,309 |          148.8→175.7 |                      10.5 / 16.9 |
| 64MiBの空白を展開  |    66,023 bytes |      1 |      2,309 |          149.0→312.0 |                       8.4 / 64.9 |
| 128MiBの空白を展開 |   131,253 bytes |      1 |      2,309 |          148.5→443.4 |                      8.4 / 129.0 |

通常の論文2件は、終了直後のJSヒープとバッファ等の合計が約19〜23MiBだった。合成の長い文書も約11MiBだった。ただし、これで任意の10MiB PDFのピークが128MB以内だとは保証できない。

約66KBの入力でNode RSSが約163MiB増え、指摘と同種の増加を再現した。約131KBの入力では、workerdの終了直後のバッファ等だけで約129MiBに達した。空白は抽出本文に含まれず、文字数上限に引っかからない。処理はNodeで約0.2〜0.4秒で完了したため、20秒タイムアウトを短縮するだけでも防げない。

Nodeの通常論文でもRSSは128MiBを超えるが、これはNode全体のメモリであり、Workersのisolate使用量と同じ指標ではない。指摘の「86→252MiB」だけで本番のOOMを断定することはできない。一方、展開量に制限がないことと、128MiB以上のバッファを持つ入力に到達できることは確認できた。

実資料：

- [Attention Is All You Need（arXiv）](https://arxiv.org/pdf/1706.03762)
- [香川大学における予実管理ダッシュボードの内製開発（学術情報処理研究29巻1号）](https://www.jstage.jst.go.jp/article/jacn/29/1/29_0022/_pdf/-char/en)

## 保存する文書量との関係

- **保存件数と解析時メモリを分けて考える。** `server/workflows.ts` は一件ずつ本文をR2へ保存し、PDFファイル自体を蓄積しない。全件の原文を常時メモリに保持する構造ではない。取り込み時のメモリは、主として解析中の文書と同時処理数に依存する。
- 日本語BMP文字だけの12万文字なら、本文一件はUTF-8で最大約360,000 bytes（約0.34MiB）。一般のUTF-16文字列では最大約360,000 bytesが保守的な上界となる。1,000件なら約343MiB、既定の一日200件をすべてこの量で保存すると約69MiB/日。これは本文だけの概算で、要約・履歴・他のデータやR2の費用を含まない。全件を同時にRAMへ載せる量ではない。
- `server/ai.ts` は本文を1万文字単位に分けて順番に要約する。上限12万文字なら初回12回と統合11回で最大23回の要約呼び出しになる。実際には既存の利用枠でも制限される。本文上限は保存容量よりもAI処理量・待ち時間の管理にも意味がある。
- 今回の日本語論文は約1.9万文字、英語論文は約4.1万文字。本文上限を手動入力と同じ2万文字に揃えると後者を除外する。12万文字の本文は文字列だけなら小さく、今回の大きな消費源は圧縮ストリームの展開だった。
- 実際に保存済みのコーパスの件数・文書長の分布は取得していない。論文2件と合成データだけから、全利用文書の何%をカバーできるかは算出できない。

## 上限の判断と対策候補

| 対象         | 判断                               | 根拠・限界                                                                                                                             |
| ------------ | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 受信ファイル | 10MiBを維持                        | 5.61MiBの実論文を取り込める。取得時のバッファ量は抑えるが、圧縮後のサイズは展開量を表さない。                                          |
| ページ数     | 100ページを維持                    | 長い文書を許容しつつ処理回数を制限する。1ページの異常入力を防ぐ役割はない。                                                            |
| 抽出本文     | 12万文字を維持                     | 実論文と長い文書を許容し、後続の要約量を制限する。ページ全体を取得してから検査する現状は、ストリーム単位で早期停止する改善余地がある。 |
| 待機時間     | 20秒を維持                         | 通信・解析待ちの利用者向け制限。同期的な展開中にはJSタイマーが割り込めないため、メモリ保護には使わない。                               |
| 解析時メモリ | アプリと別の128MB上限isolateへ隔離 | 任意PDFの内部資源を受付上限だけで拘束できない。上限到達を呼び出し元で捕捉し、URLを維持して本文補完を案内する。                         |
| 同時実行     | 隔離先の同時処理も制御する         | 現行のジョブ同時数はユーザー単位であり、同一isolateの合計メモリを保証するものではない。                                                |

Cloudflareの[メモリ制限](https://developers.cloudflare.com/workers/platform/limits/#memory)はisolate単位で128MB。JSとWebAssemblyを含み、同一isolateの複数リクエストで共有される。ローカル測定値を根拠に、本体isolateで解析を続けたまま数値だけを緩めることは推奨しない。

現実的な実装候補は次の2つ。

1. **PDF専用の別Workerへ処理を移す。** 本体とのサービスバインディングで取得済みバイト列と抽出結果だけを渡し、外部URL取得、DB、R2、認証情報を渡さない。OOMやCPU超過は本体側で通常の取り込み失敗として処理する。CMapだけは同梱資源として利用できるようにする。Workerの追加とデプロイ構成の変更が必要。
2. **Worker LoaderのDynamic Workerへ移す。** [独立したisolate](https://developers.cloudflare.com/dynamic-workers/)へパーサーをロードし、[外向き通信を遮断](https://developers.cloudflare.com/dynamic-workers/api-reference/#globaloutbound-servicestub-null-optional)、[CPU時間を制限](https://developers.cloudflare.com/dynamic-workers/usage/limits/)する。Paidプランが必要で、[作成数による課金](https://developers.cloudflare.com/dynamic-workers/pricing/)がある。毎文書 `load()` / 一意IDを使うと、200件/日で30日6,000回作成となり、無料内訳を単純に差し引いた概算で作成料だけ約$10/月になる（他用途・請求期間・利用分は別）。安定IDの `get()` で再利用すると作成料を抑えられるが、複数のPDFが同じisolateを共有し得るため同時処理の設計が必要。

展開量を厳密に拘束できるパーサーへの変更も選択肢だが、現在使っているunpdfの公開APIに文書全体の展開バイト上限はない。`streamTextContent()`による本文の早期停止だけでは、本文以外のストリーム・フォント等の解析を拘束できない。依存の内部に個別の展開サイズ検査を追加する場合も、すべての経路を制限できるか別途検証が必要。

## 再現手順

```sh
pnpm install --frozen-lockfile
node scripts/measure-pdf-memory.mjs
```

外部資料を比較する場合は別途ローカルへ取得し、パスを追加する。スクリプト自身はダウンロードしない。

```sh
node scripts/measure-pdf-memory.mjs /absolute/path/attention.pdf /absolute/path/jstage.pdf
```

合成PDF5件と指定したPDFを測定し、一文書一行のJSONを標準出力へ出す。生成したPDFとバンドルは `.cache/pdf-memory/` の一時ディレクトリへ作り、終了時に削除する。測定用コードは本体アプリの起動・ビルド・取得経路に接続しない。
