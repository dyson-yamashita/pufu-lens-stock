# メモリの差分更新と反映履歴

## 目的と要求

通常のストック追加は「現在のメモリ＋未取り込みの記事要約」で更新し、過去の記事要約を毎回AIへ送らない。再生成ボタンは確認ダイアログを開き、「未反映分を反映」「全件から再生成」を選べるようにする。プロジェクトとユーザー全体の反映履歴を独立に管理する。

## 採用する設計（実装上の判断）

- 既存のCloudflare Workflows / D1 / Reactを利用し、依存は増やさない。
- `memory_sources` にメモリID・記事ID・入力のハッシュを保存する。ハッシュには記事要約、タイトル、保存時のメモ、保存先、保存日時を含める。記事削除後も履歴を残し、削除の検出に使う。メモリ削除時は履歴も削除する。
- `memories.context_hash` で自己紹介・プロジェクトの説明などの変更を検出する。既存メモリには履歴がないため、次の更新は一度全件更新して履歴を確立する。
- 通常は追加分だけを既存メモリへ順次統合する。分割する場合も、直前の統合結果と次の追加グループだけを送る。根拠IDは既存メモリと追加記事に限定する。
- トピックの総件数はDBの全対象から集計し、上位30件の小さな集計値として渡す。過去の要約は再送しない。デモでもこの集計値を使い、追加後の件数を正しく表示する。
- 未反映の記事がなければAIを呼ばない。初回は全件が未反映なので従来の全件生成を使う。
- 取り込み済み記事の削除・移動・メモ/要約変更、背景情報変更は差分追加では取り消せないため全件更新を行う。画面にも理由を表示する。
- メモリと入力履歴は同じトランザクションで保存し、更新番号が最新の場合だけ反映する。失敗・利用上限・途中の追加では未完了分を反映済みにしない。
- 要約は25件ずつのページとして取得・永続化し、状態判定のステップには未反映の記事IDだけを保存する。全要約を単一のステップ結果へ重複保存しない。
- 手動更新の `mode` は `incremental` / `full`。旧クライアントの省略時は従来どおり `full`。同じrequest_idで異なるmodeは409にする。手動更新でも更新番号を進める。
- 明示した全件更新の要求は `memories.force_full` として保持し、後続の自動更新に集約されても失わない。
- プロジェクトからの再生成は従来どおりプロジェクト＋ユーザー全体の両方を同じモードで更新する。
- メモリ画面に反映済み・未反映・要約未完了の件数を表示。全件更新が必要なら理由も表示する。ダイアログは差分を既定とし、全件更新が必要な場合は全件を選択する。
- 全件更新が必要なときは差分の選択を無効化し、理由を表示する。未反映0件でも全件更新を選択できる。処理中は二重送信を防ぎ、失敗はダイアログ内に表示する。

## 非対象と制約

本番デプロイ・マージは行わずPRまで。AIモデル・出力上限・利用枠は変更しない。過去の全記事を永久に文章として保持する機能や履歴画面は追加しない。既存の入力制約、ユーザー分離、同じ記事の重複排除、30秒の要求集約を維持する。

## 検証

実D1を使う既存Vitest基盤で、追加分だけがAI入力になること、両スコープの履歴、反映不要時のAI省略、削除/変更で全件更新、古い結果・失敗の非反映、再生成モードと冪等性、旧データからの移行を検証する。ダイアログは外部AIを使わないローカルブラウザで選択・件数・送信・キーボード操作を確認する。
