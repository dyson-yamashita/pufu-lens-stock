# お知らせとWeb Push

ユーザー依頼：お知らせページとPush通知機能を追加し、有効化の場所と更新・配信運用を検討する。追加指定：お知らせはDB登録とし、登録スキルを用意する。記事ごとに通知あり／なしを選択する。

## 採用する構成（実装担当の判断）

- ログイン後のサイドバーに「お知らせ」を追加。`/#announcements` と `/#announcements/<id>` から一覧・本文を読める。通知未設定でも閲覧できる。
- 通知設定はプロフィールの末尾だけに置く。プロフィール内は「プロフィール → 利用状況 → 表示設定 → 通知設定」の順にし、お知らせ画面から設定カードを外す。初期値はOFF。ページ表示ではOSの許可を要求せず、説明後のスイッチ操作でだけ要求する。
- 通知は運営のお知らせだけ。処理完了通知は今回含めない。日本語・英語に対応する。
- 対応するHTTPSブラウザーのWeb Pushを使う。iPhone/iPadはiOS/iPadOS 16.4以降でホーム画面に追加したアプリから有効化する。未対応・許可拒否・管理者未設定・通信失敗を区別して案内する。
- 購読は端末/ブラウザーおよびログインセッションに結び付ける。解除、ログアウト、退会、セッション失効で送信を停止する。再ログイン後は再度有効化する。
- 通知には運営の公開文面だけを入れ、個人のストック・問い・プロフィールは入れない。配信先と暗号化鍵は本人のAPIと管理者権限以外に公開しない。

## 更新・通知の運用

お知らせはD1のannouncementsテーブルへ管理者CLIで登録し、通常の追加・訂正にはコードの再デプロイを不要にする。登録用スキルで原稿を整え、対象DB・公開日時・通知あり／なしを揃える。通知有無が未指定なら登録前に確認する。下書きは公開日時なし、予約公開は未来の公開日時。通知の有無を明示して登録し、通知ありの場合は公開日時以降の配信日時も設定する。既存の本文訂正ではID・通知日時を変えず、再通知が必要な内容は新しいIDにする。

既存の毎分CronがD1の配信台帳を使い、通知日時以前から有効な購読だけを対象にする。新規購読へ過去分を配信しない。配信開始可能期間は通知日時から7日、1回のCronで最大100購読/記事を追加、最大20送信。成功の台帳で再送を防ぎ、一時障害は最大5回、失効した購読は削除する。外部サービスの受理とDB保存を原子的にはできないため、障害時の厳密な一度だけ配信は保証せず通知tagで重複表示を抑える。

本番の秘密鍵設定・DB migration・リリースは手順を文書化し、この依頼ではPRまで作る。本番反映・実ユーザーへの通知は行わない。
