# MCPストックのハイブリッド検索

## 目的と範囲

語句が異なる保存情報もMCPから探せるようにする。ユーザーの提案に沿って、Workers AIの`@cf/baai/bge-m3`（1024次元）とVectorize V2を使う。既存のキーワード検索、認証、compact/full、件数指定、保存日時順の互換性を維持する。

最初の対象はストックのタイトル・正常な要約（概要/要点/トピック）・個人メモ。記事本文、問い、公開ページの検索やWeb画面の検索モードUIはこの改修では追加しない。問いのキーワード検索とWeb画面の既定動作は変えない。

## 入出力

- MCP `list_stocks` と既存の本人用 `GET /api/v1/stocks` に `mode: keyword|semantic|hybrid` を追加。既定はkeyword。
- qが空白だけ/未指定なら一覧としてkeywordを使い、AIもVectorizeも呼ばない。
- semantic/hybridでは `min_score`（0〜1、既定0.35）を使う。実モデルでの精度評価前の調整可能な初期値であり、精度保証値ではない。
- keywordは既存のLIKE・保存日時順・正確な件数を維持。semanticは意味の近い順、hybridはkeyword順位とsemantic順位のRRF（k=60、同点は保存日時降順/ID降順）。検索結果の並びは保存日時orderの指定より関連度を優先し、応答でもsort_by=relevance/order=descを示す。
- ベクトル上位100件、キーワード上位100件の候補を統合してページングする。total/has_moreは候補集合についての値で、searchメタデータにcandidate_limit=100と候補打ち切りの有無を返す。全件を列挙したい場合はkeywordを使う。
- metadataは要求/実際のmode、fallback_reason、候補制限、索引待ち件数を返す。hybridで未設定・外部障害・利用上限の場合はkeywordへ戻り理由を返す。semanticでは503/429を返し、意味検索が実行できたようには扱わない。

## 権限と整合性

ユーザーIDをVectorize namespaceに、project_idをmetadata filterに使用する。project_idの文字列metadata indexを作成する。候補IDから本文やメモを直接返さず、D1のstocks/projectsと現行の索引世代を結合し、本人・許可プロジェクト・お気に入り・ソース・状態を再確認する。Vectorizeのmetadataは返さない。

MCPの既存stocks:readとプロジェクト制限をそのまま適用する。検索前にもD1でプロジェクト所有権を確認する。移動/編集/削除で古くなった索引IDはD1の現行世代との照合で即時除外する。公開アクセスではAI/索引作成を実行しない。

## 索引の作成・同期

D1にバージョンごとの索引要求を保存する。要求IDは32桁のランダムIDで、そのままVectorize IDに使う。ストックの追加、title/note/project変更、記事title/summary/status変更時にSQLトリガーで旧要求を無効化し新要求を作る。削除は無効化だけを行う。世代ごとのIDにより遅れた古いupsertが新しいベクトルを上書きしない。

要求にはcurrent/ready/touched/write_pending、処理リース、再試行日時を記録する。ユーザー削除後もVectorize削除を再試行できるよう、要求テーブルにはusers/stocksへの外部キーを付けない。ユーザー/プロジェクト削除のCASCADEでもstocks削除トリガーを通ることをテストする。

既存データはmigrationで一括して索引要求を作る。Cronが1回最大10件を処理する。記事が取得・要約中なら完了後の新世代を待つ。現在の値をD1から読み、本文を含めず最大8000文字に結合して埋め込む。upsert直前にtouched/write_pendingを保存し、応答不明でも削除対象を失わない。完了を観測できない書き込みは旧IDを退役し、新しい要求IDで登録し直す。旧IDは約1時間ごとに削除を続け、完了観測後にもう一度削除してから追跡行を除去する。削除開始時点で未確定なら、その削除の応答待ち中に書き込みが完了しても行は消さない。Worker終了で完了観測できなければ最小限のID記録と削除再試行を維持する。未送信の旧要求は外部呼び出しなしで除去する。処理リースにより並行Cronで同じ要求を二重処理せず、claim時に未完了条件を再確認する。重複生成や削除競合は回帰テストで扱う。

Vectorizeの反映は非同期なので、一時的にヒットしない場合がある。索引が古いときに誤ったデータを返すより、最新世代の登録まで意味検索から除外する。

## 費用と運用

検索のembeddingは明示的なsemantic/hybridかつqがある場合だけ。検索はユーザーごと100回/24h、索引用embeddingは200回/24hを初期上限とする（環境変数で調整可能）。既存のai_calls/ai_attemptsに記録し、AI全体500回/24h・同時呼び出し上限も共有する。失敗呼び出しも回数に含め、停止した検索呼び出しの枠をCronで回復する。外部呼び出しはタイムアウトさせ、ログには検索語・メモ・ベクトルを出さない。

Vectorizeバインディングは任意。`VECTORIZE_INDEX_NAME`をビルド/開発設定で指定したときだけ`SEARCH_INDEX`を追加する。インデックスは環境別に作成し、dimensions=1024、metric=cosine、project_id metadata indexを設定する。既存の未設定環境はそのまま開発・ビルド・デプロイできる。本番資源の作成やデプロイはこの作業では行わない。管理者用手順に作成コマンド、移行、索引進行確認と再試行、無効化時の注意を記載する。

## 検証

既存の実D1/MiniflareとMCPテスト基盤を使う。Vectorize/Workers AI境界だけを決定的なテスト用実装へ置換し、実モデルの精度/本番疎通と単体・統合テストを区別する。関連語の候補統合、RRF重複排除、最小スコア、ページング、全フィルター、他人/許可外/古い索引の除外、追加/要約/編集/移動/削除/退会、移行、並行処理、外部失敗と再試行、利用上限とkeywordのAI未呼び出しを保護する。ユーザーマニュアルにはMCPで検索方式を指定できることと未設定時の動作だけを短く追加する。
