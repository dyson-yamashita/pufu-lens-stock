# MCPから既存局面を保持して次局面を追加する

ユーザーの起案本文を要件とする。Webの「局面を追加」は変更しない。

## 設計

- `add_pufu_phase` は `pufu_id`・最新の `revision`・UUIDの `request_id` を必須とし、完全なEditor形式の `projectScore` と `reason`（1〜2,000文字）を任意で受け取る。
- `projectScore` 省略時は最新局面を複製する。変更するときは `get_pufu` の内容を土台に必要箇所を変更した完全なJSONを渡す。サーバーで独自の差分形式・AI補完は導入しない。
- `pufus:write` を要求し、本人・許可プロジェクト・完成状態・revisionをサーバーで確認する。既存の問いやストックの紐付けは維持する。
- 新局面と本体の更新、任意の最初の時系列コメント、リクエストのハッシュと結果をD1の単一batchで確定する。既存局面の内容・時刻・コメントは変更しない。旧形式の第1局面が欠けている場合だけ、保存済み内容・日時から補う。
- 同じUUID・同じ入力は元の結果を返す。異なる内容・別のプ譜へのUUID再使用、古いrevisionは409。同時実行でも1局面だけを作る。リクエスト記録はプ譜・アカウント削除で連鎖削除する。
- 応答は `pufu_id`, `phase`, `current_phase`, `revision`, `updated_at`, `created`。理由ありの場合は `comment_id` も返す。再送では後続の局面追加後も元の結果を維持する。

## 手順

1. `tests/mcp-pufu-phases.test.ts` で追加、複製、内容保全、任意コメント、再送、同時実行、認可、競合、不正入力をテストし、未実装で失敗を確認。
2. `shared/pufu.ts` の入力型、`migrations/0032_pufu_phase_requests.sql`、`server/pufu-phases.ts` のトランザクション、`server/mcp.ts` のツール登録を実装。
3. マニュアルのMCP説明と `docs/SPEC.md` を最小限更新。関連テスト・型・lint・format・ビルドを確認。実データ・本番を変更せず、ダミープ譜に2〜3局面を追加してWebの局面取得・表示を検証する。
4. standard scoped監査と独立した読み取り専用コードレビューを完了し、指摘修正後にコミット・push・main向けPRを作成。マージ・本番反映は行わない。

## レビュー重点

- 古い局面・コメント・UUID・配列順・任意の進捗などが保持される。
- 再送の競合と別リクエストの競合を区別し、コメントやリクエスト記録だけが残らない。
- 再送時にも現在の閲覧・書込対象の認可を確認する。
- MCP外部呼出しの既存サイズ上限と保存時の256KiB上限を維持する。
