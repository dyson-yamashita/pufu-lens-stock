# 永続利用量制限の修正

ユーザーの依頼範囲はAI処理、保存上限、依存脆弱性の修正とローカル検証・コミット。本番反映は行わない。

## 設計

- ストック新規挿入時、D1トリガーで削除されない履歴を同一トランザクションに記録し、直近24時間200件を強制する。移行時は現存データを引き継ぐ。
- AIジョブはユーザー単位の利用枠をD1で原子的に予約する。プ譜20件、メモリ48件、記事200件、問い200件/24時間、実行中ジョブ2件を暫定値とする。手動APIでは不足時にトランザクションを中止し429を返す。自動生成はpendingで保留し、古いメモリ要求は最新世代へ集約する。
- 分割要約や自動再試行の増幅にも備え、実AI呼び出しを500回/24時間、同時2回、同一ステップ最大3試行に制限する。呼び出し結果を永続化し再実行時は再利用する。障害で成否が不明な呼び出しは自動で再発行しない。
- メモリ再生成にrequest_idを追加し、同じIDの再送は同じ処理を返す。既存クライアントのIDなしリクエストもサポートする。
- uuidのみ修正版へ限定更新し、short-uuidとエディターのAPIを維持する。

## 作業・検証

1. 最小の回帰テストを追加し現状の失敗を確認。
2. D1履歴、予約、共通AI呼び出し制限と全経路への接続、429表示を実装。
3. 依存更新、Vitest/Miniflare、エディターの生成・表示・編集・保存を確認。
4. 独立レビュー、npm run check、npm audit、コミット。

採用値の理由：プ譜は手動操作の通常利用を満たし25連続生成を拒否。メモリはプロジェクト/ユーザー両方の更新を想定。AI呼び出し総数も別に制限し分割数の増幅を抑える。同時2件で小規模運用の負荷を抑える。環境変数で調整可能にする。

## 検証の記録

- 最初の回帰3件は修正前に失敗（削除・並行生成・メモリ連続生成）、修正後に成功。
- 独立レビューで、不明なAI呼び出しが枠を恒久占有する経路と通信例外で同じ生成を再発行する経路を発見。終端確認での回復と、通信成否不明時の再発行禁止を実装。対応テスト2件は修正を外して失敗し、復元後に成功することを確認済み。
- 旧移行テストの部分スキーマは現行の制限基盤を補って動かす。これとは独立に0012から0013への順次移行・既存履歴引継ぎ・削除後の上限維持を検証する。
- レビューが実行対象外とした本番移行・実Cloudflare障害挙動は、ユーザーの指定どおり実行しない。ブラウザ・全テスト・auditは本作業で確認する。

- 最終点検でWorkflow開始直後にquota保留へ戻った状態をdispatcherが上書きする競合を再現。Workflow起動前の条件付きclaimへ変更し、並行dispatcherの二重起動も防止。回帰テストでRED→GREENを確認。
- ブラウザ（隔離したMiniflareデータ、外部AI送信なし）でプ譜生成→表示→施策追加（short-uuid ID生成）→編集→保存→再読込を確認。メモリ再生成の429と理由・再試行日時も表示確認。
- 本番デプロイは行わず、0013はローカルD1にのみ適用。既存の秘密情報・ユーザーデータは外部の検証に送信していない。

## 最終結果

- `npm run check`: 型チェック・lint・Vitest 173件（20ファイル）・format・buildすべて成功。
- `npm audit`: 0 vulnerabilities。uuid解決版11.1.1、short-uuid4.2.2とpufu-editor0.9.14を維持。
- 独立レビューのImportant（恒久枠占有、通信例外再発行）は修正し、失敗を再現するテストでRED→GREENを確認。Minorの順次移行検証も追加済み。未対応のレビュー指摘なし。
- 既存のZod注釈・エディターバンドルサイズのビルド警告は継続。実Cloudflareでの障害注入・本番移行は実行対象外。
