## アプリの構成

Web記事や入力テキストを保存し、要約・問い・メモリ・プ譜へつなげます。Google認証を使い、データをユーザーごとに管理します。

| 要素         | 役割                                                                                |
| ------------ | ----------------------------------------------------------------------------------- |
| ユーザー     | 名前・自己紹介、複数プロジェクト、ユーザーメモリを持つ                              |
| プロジェクト | ストックの保存先。概要とプロジェクトメモリを持つ                                    |
| 記事         | URLから取得した本文、または入力テキストと要約。同じユーザーの複数ストックで共有する |
| ストック     | 記事と保存先プロジェクトの対応。メモ・お気に入りを持つ                              |
| 問い         | ストックに紐づくAIまたはユーザーの問い                                              |
| プ譜         | 問いに紐づく課題の解決案。1つの問いに複数作成できる                                 |
| 局面         | 1つのプ譜内で編集結果や振り返りを保持する段階                                       |

| 技術                      | 用途                                             |
| ------------------------- | ------------------------------------------------ |
| React / Vite              | 日本語のWeb画面とビルド                          |
| Cloudflare Workers / Hono | Web配信、認証、API                               |
| D1                        | ユーザー・ストック・問い・プ譜・メモリ・利用履歴 |
| 非公開R2                  | 記事の本文                                       |
| Workflows / Cron          | 取得・生成の非同期実行、再試行と未起動処理の回復 |
| Workers AI                | 要約、問い、メモリ、プ譜の生成                   |
| Browser Run / Readability | 通常取得で本文が不足するページへの対応、本文抽出 |
| @goto-lab/pufu-editor     | プ譜の表示・編集と標準データ形式                 |

- Google OpenID Connectログイン（PKCE、state、nonce、IDトークン署名検証）とセッションCookie
- ユーザーごとのプロジェクト作成・編集・削除
- URL／テキストを選んで保存、一覧、検索、web／ユーザーの作成元フィルター、ページ送り
- 保存時のメモ、プロジェクト間の移動、削除、取得失敗の再試行
- iOSショートカット用Bearerトークンの発行・失効・有効期限・保存先制限
- 本文抽出、R2保存、Workers AIによる記事要約
- ストックごとに1つのAIの問いの自動生成、ユーザーの問いの手入力、問い一覧・検索・プロジェクト別表示、生成失敗の再試行
- プロジェクトとユーザーのメモリ更新、根拠記事の閲覧、テキストのダウンロード
- Workflowsの工程ごとの再試行、D1の処理要求、Cronによる未起動処理の回復
- メモリの更新番号による古い結果の上書き防止

ユーザーメモリは各プロジェクトのメモリを再要約するのではなく、対象プロジェクトに保存した記事の要約から直接生成します。同じ記事を複数プロジェクトに保存しても、ユーザー全体では1件に集計します。記事・メモリ・本文を他ユーザーと共有しません。

## 画面と基本操作

`/manual` に、ログインなしで読めるユーザーマニュアルを用意します。トップページとログイン後のサイドメニューから開けます。ストック・問い・プ譜・メモリ・公開・連携の基本操作を案内し、機能や利用手順が変わる場合だけ更新します。文言や見た目の微調整、内部改善はマニュアルに記録しません。

「記事をストック」のフォームで種別を「URL」「テキスト」から選べます。テキストは本文20,000文字まで、任意のタイトル200文字までです。タイトル未入力時は本文の先頭行（80文字まで）を使います。テキストも要約・AIの問い・両方のメモリ更新の対象で、詳細の「入力した本文」タブから読み返せます。

「あなたのメモリ」の上にある「すべての問い」メニューで、ストックから生まれた問いを閲覧できます。ストック一覧と記事詳細にも「問い」タブがあります。ローカルでAI未接続の場合は、記事の要点とプロジェクト名から定型の問いを生成します。

全体のストック・問いの画面にあるプロジェクトメニューは一覧の絞り込みです。選択しても画面とURLは維持し、ストック／問いのタブ間で選択を引き継ぎます。追加フォームの保存先にも選択したプロジェクトを反映します。サイドメニューのプロジェクトからは専用画面を開き、専用画面のストック・問いにはプロジェクト選択メニューを表示しません。

全体のストック・問い・メモリ画面には「ストック」「問い」「メモリ」のタブを表示します。「メモリ」は一覧のプロジェクト絞り込みにかかわらず「あなたのメモリ」を開きます。メモリのタブを経由して一覧に戻っても、プロジェクトの絞り込みは保持します。

サイドメニューは右上の「×」ボタンで閉じられ、閉じている間はヘッダーのハンバーガーボタンから再表示できます。広い画面で折りたたむと本文領域が広がります。モバイルでは重ねて表示し、閉じるボタン・背景のタップ・Escapeキーで閉じられます。

「すべての問い」には検索や絞り込みに関係なく本人の問いの総件数を表示します。`GET /projects` の各プロジェクトの `question_count` を合計し、既存のプロジェクト取得・定期更新を使って反映します。問いの集計には既存のプロジェクト別インデックスを使い、追加の一覧取得やDB移行は行いません。

各プロジェクトの「ストック」「問い」の右にある「設定」タブから、プロジェクト名・プロジェクト概要を編集できます。保存後も設定画面を維持します。プロジェクトの削除も設定タブから行えます。全体画面には設定タブを表示しません。

プロジェクト追加フォームと設定画面の「詳細設定」には「ストック追加時にユーザーのメモリを更新する」のトグルを置きます。詳細設定は初期状態で折りたたみ、トグルの初期値はオンです。作成時にもオン／オフを選んで保存できます。オフにしてもプロジェクトメモリは更新しますが、そのプロジェクトだけへのストック追加・要約完了ではユーザーメモリを更新しません。ユーザーメモリの手動再生成や他プロジェクトからの更新でも、オフのプロジェクトの記事・メモ・所属情報を生成対象から外します。同じ記事がオンのプロジェクトにも保存されている場合は、オンの保存先の情報だけで1件として反映します。

変更は「保存」で確定し、既存のユーザーメモリも非同期で更新して対象の変更を反映します。`0018_project_user_memory.sql` で設定列を追加します。`GET /projects` は `include_in_user_memory` を真偽値で返し、`POST /projects` と `PATCH /projects/:id` は同じ真偽値を任意で受け付けます。作成時の省略はオン、編集時の省略は現在の値を維持します。

プロジェクトのタブは「ストック」「問い」「メモリ」「設定」の順です。「メモリ」タブでは、そのプロジェクトの興味の傾向・記事から得た知識・根拠記事を確認でき、再生成とテキスト保存も行えます。メモリ画面にも同じタブを表示し、プロジェクトを維持して他のタブへ切り替えられます。

「記事から得た知識」は1項目につき1〜3文・80〜120文字程度を目安にAIで簡潔に整理します。画面では既存の知識も最初の3行まで表示し、長い項目は「続きを読む」「閉じる」で切り替えます。根拠記事へのリンクは常に表示し、保存済みの全文やテキストのダウンロード内容は省略しません。生成の目安は次回の更新・全件再生成から反映し、既存データを一括で書き換えません。

ストックのフィルターは「すべて」「web」「ユーザー」「お気に入り」です。webはURLから保存した記事、ユーザーは入力したテキストです。ストック・問いの検索は入力中に結果を変えず、虫眼鏡ボタンまたはEnterで反映します。×ボタンは入力と検索条件を解除します。検索右側の更新ボタンは表示せず、処理状況は引き続き定期的に更新します。

## プロフィールとメモリへの反映

プロフィールの「表示設定」で「システムに合わせる」「ライト」「ダーク」を選べます。初期値は「システムに合わせる」です。変更は保存ボタンなしで即時反映し、このブラウザの `localStorage` に保存します。設定はアカウント間や端末間では同期しません。保存領域が利用できない場合も、そのページ内の切り替えは動作します。

システム設定の変更と同じブラウザの別タブでの選択にも追従します。Reactの起動前に背景とテーマを適用し、ブラウザのテーマ色・フォーム部品も切り替えます。プ譜は共通の設定をエディターの `dark` に渡し、切り替え時にエディターを再作成せず未保存の本文・コメントを保持します。MCP連携の許可画面には、非機密の表示設定Cookie `pufu_lens_theme` を使って手動選択を反映し、システム設定の場合はCSSのメディアクエリで追従します。許可画面のスクリプト禁止は維持します。

メニューの「プロフィール」で名前（必須・80文字まで）と自己紹介（任意・1,000文字まで）を編集できます。初回ログイン時にGoogleの名前を取り込み、以後はアプリに保存した名前を保持します。`PATCH /me` の本文は `{ "name": "表示名", "bio": "自己紹介" }` です。プロフィールの取得・更新は本人のWebセッションでのみ行えます。

要約済みの記事がある場合、自己紹介をユーザーメモリ生成の背景情報としてWorkers AIへ渡します。自己紹介だけの内容を記事由来の知識として扱いません。自己紹介を変更・削除するとユーザーメモリを非同期で更新し、同じ内容の再保存や名前だけの変更では再生成しません。プロジェクトメモリは従来どおりプロジェクト概要を参照します。既存メモリの一括再生成は行わず、次回の更新や画面の「再生成」から反映できます。

### メモリの差分更新と再生成

通常のメモリ更新は、現在のメモリに未反映の記事要約だけを統合します。「再生成」では確認ダイアログで「未反映分を反映」「全件から再生成」を選択でき、対象の反映済み・未反映・要約未完了の件数も確認できます。手動再生成は選択中のプロジェクトまたは「あなたのメモリ」だけを更新します。ストック追加時の自動更新は保存先プロジェクトに反映し、詳細設定がオンの場合は「あなたのメモリ」にも反映します。反映状況の件数もそれぞれの対象範囲で集計します。記事の削除・移動・メモや要約の変更、自己紹介やプロジェクト情報の変更がある場合は、古い情報を残さないため全件更新に切り替わります。既存メモリの初回更新も、反映履歴を確立するため全件更新します。

反映状況は根拠として画面に表示された記事数ではなく、生成に取り込んだ記事と入力内容から管理します。要約が未完了の記事は完了後に自動反映し、生成失敗・利用枠待ち・古い更新番号の結果では反映済みにしません。`0015_incremental_memory.sql` で取り込み履歴と更新方法の保存領域を追加します。

## 問い

問いはプロジェクトに所属し、ストックへの紐づけは任意です。所有者は `問い → プロジェクト → ユーザー` の関係で確認します。ストックの保存受付と同じトランザクションでAIの問いの生成待ちを登録し、要約ができた時点で1つ生成します。要約済みの記事を別プロジェクトへ保存した場合も、そのストック用の問いを生成します。再送・同じ保存先への重複保存・生成の再試行でAIの問いの件数は増えません。ストックに紐づいた問いは、そのストックの移動・削除に従います。独立した問いは所属プロジェクトの削除で削除されます。

問いの画面にある「問いを追加」から、プロジェクトを選び、500文字までの問いを手入力できます。関連するストックの選択は任意です。AIの問いは各ストック1件を保ち、ユーザーの問いは同じストックに複数追加できます。ストックの問いタブでは、紐づくAI・ユーザーの問いをすべて表示します。

`POST /questions` は `{ "project_id": "プロジェクトID", "stock_id": null, "text": "問いの本文", "request_id": "任意のUUID" }` を受け付け、`source=user`、`status=ready` で保存します。`stock_id` は省略またはnullで独立した問いとなり、指定する場合は同じプロジェクトのストックに限ります。従来の `stock_id` だけの入力も保存先を推定して受け付けます。REST APIは本人のWebセッションのみ利用でき、MCPでは別のOAuth認可で同じ処理を利用します。作成元はサーバーが決めます。フォームは同じ保存の再試行に同じ `request_id` を使い、重複を防ぎます。成功時は `201`、再送は `200`、同じIDで異なる内容は `409` です。`GET /stocks/:id/question` はAIの問いを `question`、紐づくすべての問いを `questions` で返します。

問いのラベルは作成元の「AI」「ユーザー」です。画面のフィルターは「AI」「ユーザー」「お気に入り」の3つで、選択中のフィルターを再度押すと解除して全件表示に戻ります。`GET /questions` は `project_id`、`q`、`source`（`all / ai / user`）、`favorite`（`true` のときお気に入りのみ）、`status`（`all / ready / processing / failed`）、`page` を受け付け、24件ずつ返します。既存の自動生成した問いの `source` は `ai` で、生成前・失敗時も同じ作成元です。内部の生成状態は `queued / generating / ready / failed` で保持し、生成待ちや失敗の状況は問い本文の領域で表示します。問いの生成失敗では記事の要約を保持し、問いだけを再試行できます。問いの生成は既存のArticleWorkflowで処理し、新しいCloudflareバインディングは不要です。本番では問い1件につきWorkers AIへの生成呼び出しが1回増えます（失敗時の再試行を除く）。

問いカードの日付横のスターで、お気に入りを登録・解除できます。未選択は背景透過の細い枠線、選択中は黄色の塗りつぶしです。`PATCH /questions/:id/favorite` に `{ "is_favorite": true }` または `false` を送り、保存した `id` と `is_favorite`（`0 / 1`）を返します。本人のWebセッションだけが変更でき、再読み込みやAI生成の再試行でも保持します。

問いの詳細画面下部の「問いを削除」で、確認後に問いと関連するすべてのプ譜を削除できます。`DELETE /questions/:id` は本人のWebセッションのみ利用でき、元のストックと記事、別の問いは保持します。関連する生成ジョブは終了扱いにし、削除したAIの問いは記事処理の完了や再試行でも自動的に作り直しません。ストックを削除して保存し直した場合は、新しいストックとしてAIの問いが生成されます。

## プ譜

問い一覧の本文、またはストックの問いタブから問いの詳細を開きます。下部の「問いの解決を考える」から課題を入力し、「プ譜を作成」を押します。課題は前後の空白を除いて、そのまま獲得目標になります。勝利条件・中間目的・施策・廟算八要素を、問い・プロジェクトの説明・ユーザーとプロジェクトのメモリから生成します。関連するストックがあれば、その要約とメモも使います。独立した問いでもプ譜を作成でき、生成時のスナップショットの `stock` はnullです。

生成は既存のArticleWorkflow内で非同期に処理し、画面を閉じても継続します。1つの問いに複数のプ譜を保存でき、再生成は新しい作成として行います。生成失敗時は同じ入力を使って再試行できます。新しい生成・明示的な再試行は利用量制限の対象です。ストックの移動では問いとともに所属が移動し、ストックやプロジェクトの削除では関連するプ譜も削除されます。

生成済み（`ready`）のプ譜が1つ以上ある問いには、AI／ユーザーラベルの横に「プ譜」を表示します。問いの取得APIは `has_pufu`（`0 / 1`）を返し、一覧・詳細・ストックの問いタブで共通の判定を使います。生成中・生成失敗だけの場合は表示しません。

表示・編集は `@goto-lab/pufu-editor@0.9.15` のReactコンポーネントを直接組み込んでいます。iframeは使用せず、同梱のTailwind CSSをビルド時に `.pufu-editor-root` 配下に限定しています。初期データを編集中に再取得して差し替えず、「保存」で `getScoreJson` の内容を取得します。未保存のまま画面を離れる際は確認し、別画面からの同時保存は更新番号で競合を検出します。JSONはエディター標準の `ProjectScoreModel` 形式でダウンロードできます。自己紹介は生成リクエストに直接含めず、ユーザーメモリを通じて間接的に反映します。

プ譜は第1局面から始まり、奇数局面は編集、偶数局面はフィードバック（本文の編集とコメントの追記）モードです。「局面を追加」は最新局面の編集内容を保存し、コメントを含めて次の局面へ引き継ぎます。AIの再生成は行いません。過去の局面も「◀」「▶」で移動して修正・保存でき、ほかの局面の内容は変更しません。矢印は移動先の局面がある場合だけ表示します。局面切り替え時にも未保存の変更を確認します。既存のプ譜は `0012_pufu_phases.sql` で、現在の編集内容を保持した第1局面として移行します。

ローカルデモでAIが未接続の場合は、問い・課題・メモリから定型の案を作成し、その旨を表示します。本物の生成にはWorkers AIバインディングが必要です。AIへの出力指示と検証はプ譜専用で、文章の案を生成させた後、UUIDと空のコメントをサーバーで補います。未確認の予算・担当者・期限を事実として埋めません。

| メソッド・パス                     | 用途                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/questions/:id`        | 問いの詳細と関連するプ譜の一覧                                                                          |
| `POST /api/v1/questions/:id/pufus` | `{ task, request_id }` で生成受付。作成時202、同じUUIDでの再送200、異なる入力での再利用409              |
| `GET /api/v1/pufus/:id`            | プ譜・状態・生成時の文脈と局面一覧 `phases`、最新局面番号 `current_phase` を取得                        |
| `PATCH /api/v1/pufus/:id`          | `{ revision, phase, score }` で指定局面を保存。更新競合409、存在しない局面404。`phase` 省略時は最新局面 |
| `POST /api/v1/pufus/:id/phases`    | `{ revision, phase, score }` で最新局面を保存して次局面を追加。201、更新競合409                         |
| `POST /api/v1/pufus/:id/retry`     | 生成失敗の再試行                                                                                        |

これらのAPIは本人のWebセッションのみ利用でき、変更時は同一Originが必要です。課題は1,000文字まで。プ譜保存は256KiBまでで、各文章1,200文字、各コメント600文字、中間目的12件・各施策12件までを検証します。UUIDの重複と不正な色・進捗値も拒否します。

`pufu_scores` に原案・最新の編集結果・入力時点の問いとメモリのスナップショット（内容・更新番号）・モデル・エディターのバージョン、`pufu_phases` に各局面の編集結果を保持します。メモリが後で変わっても、生成した案の根拠を確認できます。プ譜の作成・編集・局面追加で既存のメモリは更新しません。ライセンス文は [pufu-editor.txt](../public/licenses/pufu-editor.txt) に同梱しています。

## MCP連携（ChatGPTなど）

既存Workerの `/mcp` に、OAuth 2.1付きStreamable HTTPサーバーを追加しています。サイドメニューの「MCP連携」で接続URLと連携一覧を確認し、不要な連携を解除できます。

| ツール           | 用途                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `list_projects`  | 許可されたプロジェクトの一覧                                                                                   |
| `list_stocks`    | 軽量なストック一覧。検索・絞り込み・件数指定・保存日時順・ページ送り                                           |
| `get_stock`      | ストック詳細。`include_content: true` の場合だけ本文を20,000文字まで取得（超過時は `content_truncated: true`） |
| `add_stock`      | `type: url` と `url`、または `type: text` と `text` で保存。任意のタイトルとメモ                               |
| `list_questions` | 独立した問いを含む検索・絞り込み・ページ送り                                                                   |
| `get_question`   | 問いの詳細と任意の関連ストックID                                                                               |
| `add_question`   | プロジェクトに問いを追加。関連する `stock_id` は任意                                                           |

追加ツールには `project_id` と `request_id`（UUID）が必須です。同じ操作の通信再試行では同じUUIDを使います。ストックの要約・AIの問い・メモリは非同期で生成し、既存の保存件数・AI利用量制限を共通で適用します。

### ストック一覧の取得量と検索範囲

MCPの `list_stocks` は既定で `detail: "compact"` を使用します。検索対象はタイトル・要約全体（要点・トピックを含む）・メモです。記事本文・入力テキストは検索対象に含みません。抜粋はoverviewの先頭なので、一致語が要点やメモにある場合は抜粋に出ないことがあります。その場合は該当IDを `get_stock` で取得します。

| 引数      | 既定値       | 動作                                                                        |
| --------- | ------------ | --------------------------------------------------------------------------- |
| `limit`   | `24`         | 1〜24の整数。DB取得時の上限とページ幅。最新1件なら `1`                      |
| `sort_by` | `created_at` | ストックの保存日時。記事・動画の公開日時ではありません                      |
| `order`   | `desc`       | 新しい順。`asc` で古い順。同時刻は同じ方向のストックID順                    |
| `detail`  | `compact`    | ID・タイトル・短い要約・保存先・保存日時・記事状態を返す。`full` で従来形式 |
| `page`    | `1`          | 1〜5000。続きは同じ `limit`・並び順・フィルターでページを増やす             |

```json
{
  "limit": 5,
  "sort_by": "created_at",
  "order": "desc",
  "detail": "compact"
}
```

compactの各ストックは `id`、`title`、`project_id`、`project_name`、`created_at`、`status`、`summary_excerpt`、`summary_truncated` を返します。要約の抜粋は最大200文字（超過時は末尾の「…」を含む）です。`summary_truncated` はoverviewの先頭を切り詰めた場合に `true` となり、要約未生成時は抜粋が `null`、切り詰めが `false` になります。Unicodeコードポイント単位で切り詰め、サロゲートペアを分断しません。要約の要点・トピック・メモ・本文・URLなどは軽量一覧に含めません。

一覧の外側には `stocks`、フィルター後の総件数 `total`、`page`、実際のページ幅 `pageSize`、次ページの有無 `has_more`、`sort_by`、`order`、`detail` を返します。並び順の値は検証してから固定のSQL句を選び、件数・offsetはバインドします。プロジェクト限定・他ユーザーの除外・読み取り権限は、compact／fullの両方に適用します。

### 互換性と今回の改善範囲

- MCPで従来の一覧項目が必要なクライアントは `detail: "full"` を指定します。`get_stock` は従来の詳細を返し、本文は `include_content: true` の場合だけ取得します。
- Web画面が使うHTTP API `GET /stocks` の既定値は従来どおり24件・新しい順・fullです。HTTP APIでも上記の一覧オプションを指定できます。
- `content` のJSONテキストと `structuredContent` は同じデータを保持します。構造化結果を読めないクライアントのための互換性を残し、まず返す項目と件数を減らします。
- full／詳細の既存フィールド名（`summary.keyPoints`、`source_type`、`pageSize`など）と `is_favorite` の `0 / 1` は維持します。型・命名の一括変更は既存クライアントへの破壊的変更になるため、今回は行いません。
- 本文検索にはR2に保存した本文の検索索引と一致箇所の返却設計が必要です。全本文を取得して走査する方式は追加せず、検索対象をツール定義にも明示します。
- ストックの `status` は記事取得・要約の状態です。問いとメモリは別の非同期処理なので、記事が `ready` でもすべての処理が完了したことを意味しません。問いは `list_questions`／`get_question` で確認できます。複数記事をまとめるメモリ更新を1ストックの完了状態として返す設計は、今回の一覧改善から分けます。

### 本番の準備

このリポジトリの本番環境にはOAuth用KVを設定しています。別の環境へ構築する場合は、次の手順で専用のKVを作成・設定してください。

1. OAuth用KVを作成します。

   ```sh
   pnpm exec wrangler kv namespace create OAUTH_KV --env production
   ```

2. 返されたIDを本番ビルドの環境変数 `OAUTH_KV_ID` に設定します。GitHub Actionsでは `production` EnvironmentのSecretsに登録します。`wrangler.jsonc` のKV IDはゼロのプレースホルダーのままにします。ローカル開発もこのプレースホルダーでローカルKVを使えます。
3. `APP_URL` を末尾スラッシュなしの本番HTTPSオリジンに合わせます。既存GoogleログインのClient ID・Secretとコールバック設定を使います。MCPクライアントにGoogleのトークンやセッションCookieを渡す必要はありません。
4. [本番設定の手順](#cloudflareの本番設定)に従い、環境変数を指定して本番ビルド後にマイグレーション・デプロイを実行します。MCPには `0016_independent_questions.sql` 以降が必要です。0016は既存の問い・お気に入り・プ譜・局面を保全し、移行後も旧Workerのストック指定による問い生成を受け付けます。

`global_fetch_strictly_public` と、静的配信よりWorkerを先に処理する `/mcp`・`/oauth/*`・`/.well-known/*` のルートは設定済みです。通常の本番反映はmainの更新を受けたGitHub ActionsがDB移行とWorker公開を順に実行します。

### ChatGPTから接続

利用アカウント・ワークスペースでカスタムMCPが許可されていることを確認してください。[ChatGPT Plugins](https://chatgpt.com/plugins) で「Add custom MCP server」を選び、接続URL `https://実際のホスト/mcp` を登録してOAuthで接続します。Googleログイン後、Pufu Lensの認可画面で接続元・送信先・操作権限・対象プロジェクトを確認して許可します。接続したプラグインを会話で選択して利用します。[OpenAI公式の接続手順](https://developers.openai.com/plugins/deploy/connect-chatgpt)

認可画面では `projects:read`、`stocks:read`、`stocks:write`、`questions:read`、`questions:write` を個別に選択でき、1プロジェクトに限定することもできます。アクセストークンは1時間です。「連携を継続するためにトークンを更新」を許可した場合だけ30日有効の更新トークンを発行します。CIMD・DCR・PKCE（S256）・認可サーバー/保護リソースのメタデータ公開に対応しています。アプリの「MCP連携」から解除すると、その連携のアクセストークンと更新トークンを失効します。既存ショートカット用トークンの権限は拡大しません。

### ローカル検証

`pnpm run dev` を起動し、別ターミナルで `pnpm run test:smoke:mcp` を実行します。ローカルデモに対してOAuth・7ツール・再送・独立した問い・更新・失効を検証し、検証用プロジェクトと連携を削除します。Workers AIを使わずに検証する場合は `WORKERS_AI_ENABLED=false pnpm run dev` としてください。

クラウドから `localhost` には直接接続できません。ChatGPTでのローカル接続検証には適切なHTTPSトンネル等が必要です。本番準備後は本番HTTPS URLを使用してください。

## API

`/api/v1` は認証必須です。WebのCookie認証での変更操作には、`APP_URL` と一致する `Origin` が必要です。Bearer認証ではCookieに依存しません。

| メソッド・パス                    | 用途                                   | Bearer |
| --------------------------------- | -------------------------------------- | ------ |
| `GET /projects`                   | 自分のプロジェクト一覧                 | 可     |
| `POST /stocks`                    | URL／テキストの保存受付                | 可     |
| `GET /me`                         | ログイン中のユーザー                   | —      |
| `PATCH /me`                       | 自分の名前・自己紹介の更新             | —      |
| `POST /logout`                    | セッション終了                         | —      |
| `POST /projects`                  | プロジェクト作成                       | —      |
| `PATCH・DELETE /projects/:id`     | プロジェクト編集・削除                 | —      |
| `GET /stocks`                     | 検索・状態・プロジェクトで絞り込む一覧 | —      |
| `GET /stocks/:id`                 | 保存した記事の詳細                     | —      |
| `GET /questions`                  | 自分の問い一覧                         | —      |
| `POST /questions`                 | プロジェクトにユーザーの問いを追加     | —      |
| `PATCH /questions/:id/favorite`   | 問いのお気に入りを登録・解除           | —      |
| `DELETE /questions/:id`           | 問いと紐づくプ譜の削除                 | —      |
| `GET /stocks/:id/question`        | ストックに紐づく問い                   | —      |
| `POST /stocks/:id/question/retry` | 生成失敗した問いの再試行               | —      |
| `PATCH・DELETE /stocks/:id`       | メモ・所属の更新、保存の削除           | —      |
| `PATCH /stocks/:id/favorite`      | ストックのお気に入りを登録・解除       | —      |
| `PATCH /stocks/:id/title`         | ストックのタイトルを編集               | —      |
| `POST /stocks/:id/retry`          | 失敗した取得・要約の再試行             | —      |
| `GET /stocks/:id/content`         | 取得本文・入力テキストの閲覧           | —      |
| `GET /articles/:id`               | メモリの根拠記事を開く                 | —      |
| `GET /memory`                     | ユーザー／プロジェクトのメモリ         | —      |
| `POST /memory/rebuild`            | メモリの再生成受付                     | —      |
| `GET・POST /tokens`               | トークン一覧・発行                     | —      |
| `DELETE /tokens/:id`              | トークンの失効                         | —      |

`GET /stocks` は `project_id`、`q`、`source`（`all / web / user`）、`favorite`（`true` のときお気に入りのみ）、`page` を受け付け、既定は24件ずつ返します。`limit`（1〜24）、`sort_by=created_at`、`order=asc / desc`、`detail=compact / full` も指定でき、HTTP APIの既定は `full`・新しい順です。`source=web` は `source_type=url`、`source=user` は `source_type=text` に対応します。APIでは `status`（`all / ready / processing / failed`）も併用できます。`GET /memory` は `project_id` を省略するとユーザーメモリです。

ストックも日付横のスターでお気に入りを登録・解除でき、選択中は黄色で表示します。記事の詳細画面からも変更でき、一覧の「お気に入り」で絞り込めます。`PATCH /stocks/:id/favorite` に `{ "is_favorite": true }` または `false` を送り、保存した `id` と `is_favorite`（`0 / 1`）を返します。本人のWebセッションだけが変更でき、再読み込み・要約の再試行・保存先の移動でも保持します。同じ記事を別のプロジェクトに保存した場合や、記事に紐づく問いのお気に入りとは独立しています。

詳細画面のタイトル右の鉛筆から編集し、「保存」で確定、「キャンセル」またはEscapeで取り消せます。`PATCH /stocks/:id/title` は `{ "title": "新しいタイトル" }` を受け付け、前後の空白を除いた1〜200文字のタイトルと `id` を返します。本人のWebセッションだけが変更でき、一覧・詳細・問いの参照タイトル・MCP一覧・公開ページと検索に反映します。編集内容はストックごとに保持し、記事の再取得や別プロジェクトの同じ記事には影響しません。Worker更新前に `0021_stock_titles.sql` を適用してください。

`POST /stocks` のURL保存は `{ "type": "url", "project_id": "保存先ID", "url": "https://...", "note": "任意のメモ" }` です。`type` を省略した従来のショートカットのリクエストもURLとして受け付けます。テキスト保存は次の形式で、URLは送信しません。

URL・テキストとも `project_id` は省略できます。指定時は本人の指定プロジェクトだけに保存し、限定トークンと異なる指定は `403`、存在しない・他ユーザーの指定先は `404` になります。省略時は限定トークンの限定先、限定なしトークン・セッション認証では本人の現在の全プロジェクトに保存します。保存先が0件なら `400` を返します。空文字や `null` は無効です。全件保存は単一トランザクションで行い、利用上限は新規ストック件数ごとに数えます。残り枠が不足する場合は全体を取り消して `429` を返します。既存ストックのメモは保持し、記事本体と取得・要約処理は共有します。

```json
{
  "type": "text",
  "project_id": "保存先ID",
  "title": "任意のタイトル",
  "text": "ストックする本文",
  "note": "任意のメモ"
}
```

本文の前後の空白を除き、空白のみの入力を拒否します。同じタイトル・本文はユーザー内で記事本体を再利用し、同じプロジェクトへの二重保存を防ぎます。テキストでもBearerの保存先制限と `Idempotency-Key` を適用します。保存APIの送信上限は160KiB、本文は20,000文字です。一覧・詳細は `source_type`（`url / text`）を返し、テキストの `source_url` と `domain` は空文字です。

## 非同期処理とデータ整合性

- URL／テキスト受付と処理要求、メモリ更新要求を同一D1トランザクションで保存します。テキストの入力本文はD1へ保持し、WorkflowがR2へ保存して要約します。テキストでは外部URLの取得を行いません。Workflowの起動に失敗してもCronから再開できます。
- 記事の本文取得、R2保存、AI呼び出し、要約確定を工程に分けます。本文取得・R2保存・要約確定などの工程の再試行は2回までです。AIステップの形式エラーは初回を含め最大10試行、5秒固定間隔です。起動・枠待ちの試行数と待機期限は、[利用量制限](#利用量制限)に記載しています。
- 長い記事は本文を分割して要約し、全分割の要約を統合します。メモリは通常、現在のメモリと未反映の記事要約だけで更新します。全件更新が必要な場合は記事要約の全件を25件ずつ読み、中間要約を統合します。最近の記事だけに切り詰める実装ではありません。
- 要約が確定する際、トランザクション内で最新の保存先プロジェクトを読みます。要約中に別プロジェクトへ保存しても更新を取りこぼしません。
- メモリ生成前後で入力の更新番号を確認します。古い生成結果は保存せず、最新の更新要求を処理します。
- 保存した記事の主張をユーザー本人の信念として扱いません。知識には根拠の記事IDを保存し、入力に存在しないIDを除外します。
- 記事削除・移動・メモ更新・プロジェクト説明の変更でも関連メモリを再生成します。最後の保存を削除した記事はDBから除去し、非公開本文の削除要求を残します。

記事要約のJSONは `{ overview, keyPoints, topics }`、メモリは `{ interests, knowledge: [{ text, articleIds }], questions }` です。AIの応答はZodで検証します。

## 記事取得の範囲

YouTubeの動画内容は記録対象外です。`youtube.com`・`youtu.be`・`youtube-nocookie.com` とそのサブドメインのURLを追加すると、初期タイトル「YouTube」でURL・メモを保存します。記事取得・動画情報のAI処理の対象外として内部状態は `failed` としますが、画面では取得失敗を表示しません。動画・チャンネル・再生リストなどのパスにかかわらず外部取得しません。本文補完は保存せず、記事処理・自動の問い生成のジョブを作成しません。再試行APIは記録不可の案内を返し、処理待ちだったYouTube URLもWorkflowで取得・AI処理前に停止します。通常記事からYouTubeへのリダイレクトも接続前に拒否します。

利用者のメモがある場合だけ、YouTubeストックをメモリ更新の対象にします。空白だけのメモは対象外です。動画の旧タイトル・旧要約・本文・字幕を参照せず、入力タイトルは「YouTube」、入力内容は利用者が記入したメモだけとします。同じ動画を複数のプロジェクトに保存した場合は、対象の保存先に記入されたメモだけを集約し、ユーザーメモリではプロジェクトの設定も適用します。メモの追加・編集・削除・保存先の変更に合わせて更新し、メモのないURLの保存・変更・削除や、動画の表示・再生は更新を起動しません。メモのないYouTubeはメモリの取得待ち件数にも含めません。除外した記事があっても後続の更新対象を読み込めるよう、ページの終端は除外前の件数で判定します。

YouTube Data API連携・APIキー・動画情報専用の要約処理・サーバーによるサムネイル取得はありません。動画URLは通常・短縮・Shorts・ライブ・埋め込みのURLから11文字の動画IDを読み取り、詳細画面で `https://www.youtube-nocookie.com/embed/{videoId}` の固定ホストにiframeを表示します。任意の追加クエリは引き継がず、自動再生やJavaScriptのプレーヤーAPIは使いません。HTTPリファラーが必要なため `referrerPolicy="strict-origin-when-cross-origin"` を指定し、最小200pxの高さを確保します。一覧ではiframeを読み込まず、検証済みの動画IDから固定ホスト `https://i.ytimg.com/vi/{videoId}/mqdefault.jpg` の静止画像だけを表示します。画像は320×180で、`loading="lazy"`・`decoding="async"`・`referrerPolicy="no-referrer"` を指定します。画像やタイトルを押すと詳細を開き、その時点でプレーヤーを読み込みます。画像の取得失敗や動画を特定できないURLでも、詳細への導線を残します。公開ストックの一覧・詳細も同じ表示です。動画を特定できないURLは外部リンクとして扱います。ブラウザからYouTubeへの通信はプライバシーポリシーに記載します。`0019_youtube_metadata.sql` は適用済みDBとの移行履歴として残しますが、`youtube_json` 列を実行時の処理で読み書きせず、ストックAPIから `youtube` メタデータを返しません。過去に取得した同じURLを再保存・重複再送した場合も、既存記事を記録不可の状態と案内に切り替えます。過去の本文・要約は削除せず保持し、その本文や失敗状態の要約をストックAPIから返しません。保存済みデータの一括削除は行いません。

対象は、ログインせず読める公開HTML・テキスト記事です。HTTP(S)以外、内部・予約アドレス、認証情報入りURL、標準外ポートを拒否します。DNSのA・AAAAの全回答と各リダイレクト先を検査し、取得時にアプリのCookieやBearerトークンを送りません。

通常はHTMLを取得してReadabilityで本文を抽出します。本文が不足する場合はBrowser Runを使用します。ブラウザのHTTP要求も検証付き取得を通し、POST、ダウンロード、Service Worker、WebSocketを許可しません。ログイン・ペイウォール・アクセス制限の回避は行いません。ページ上の任意の対話操作には対応していません。

ページの取得上限は2MB、抽出本文は12万文字です。上限超過や取得失敗時はURLとエラーを保持します。プロジェクトは50件、保存はユーザーごとに直近24時間200件までに制限しています。本文・AI処理の時間と実記事の要約品質は、利用する記事で確認してください。

## 利用量制限

`0013_usage_limits.sql` と `0014_job_retry_limits.sql` をWorker更新前に順番に適用します。`0014` は既存ジョブを保持したまま起動試行の記録用テーブルを追加します。既存ジョブの試行数は次の起動から数えます。直近24時間の新規保存はユーザーごとに200件です。D1トリガーで保存と履歴を同時に確定し、削除しても履歴は減らず、URL/テキスト・Cookie/Bearerで枠は分離しません。別プロジェクトへの新規保存も同じユーザー枠で計上します。重複保存とIdempotency-Keyの再送は二重計上しません。移行前に削除済みの保存履歴は復元できないため、初期履歴には現存するストックを引き継ぎます。

AI処理はD1の利用枠を原子的に確保してからWorkflowを起動します。値は正の整数の環境変数で調整できます（未設定・不正値は下記の既定値）。ローカルは `.dev.vars`、本番は `wrangler.jsonc` の対象環境の `vars` に設定します。

| 環境変数                  | 既定値 | 集計対象（ユーザー単位）                                             |
| ------------------------- | -----: | -------------------------------------------------------------------- |
| `AI_PUFU_DAILY_LIMIT`     |     20 | プ譜生成・明示的な再試行／直近24時間                                 |
| `AI_MEMORY_DAILY_LIMIT`   |     48 | ユーザー/プロジェクトの手動・自動メモリ更新の合計／直近24時間        |
| `AI_ARTICLE_DAILY_LIMIT`  |    200 | 記事の要約ジョブ・再試行／直近24時間                                 |
| `AI_QUESTION_DAILY_LIMIT` |    200 | AIの問い生成・再試行／直近24時間                                     |
| `AI_CONCURRENT_JOBS`      |      5 | 受付済み・未完了のAIジョブ数（待機・実行を含む）                     |
| `AI_CALL_DAILY_LIMIT`     |    500 | 分割要約・統合・形式エラーの再試行を含む実AI呼び出し試行／直近24時間 |
| `AI_CONCURRENT_CALLS`     |      5 | 実AI呼び出しの同時実行数                                             |

小規模運用の暫定値として、プ譜は20件、メモリはユーザーとプロジェクトの更新を合わせて48件としています。分割や再試行による増幅は別の500回枠で抑えます。これはユーザーごとの呼び出し回数制限であり、アカウント全体の金額上限ではありません。

手動APIは上限時にジョブを起動せず `429`、`Retry-After`（秒）、JSONの `error` と `retry_at`（UTC ISO日時）を返し、画面に理由・再試行目安を表示します。同時数のみの上限は60秒後を目安に返しますが、実行中の完了や新たな利用状況により再度429となることがあります。`POST /memory/rebuild` は `{ project_id?, request_id?, mode? }` を受け付けます。`mode` は `incremental` または `full` で、省略時は従来どおり `full` です。同じrequest_idまたはIdempotency-Keyは再送しても同じ受付を返し、対象または更新方法が異なる再送は `409` です。プロジェクト指定時はそのプロジェクトのみ、省略時はユーザー全体のみの1ジョブ分を確保します。IDなしは新規要求です。

自動メモリ更新は上限時も `pending` として保持し、未開始の古い世代を最新世代へ集約します。毎分のCronが枠の回復後に処理を再開します。枠の確認・Workflowの起動・回復後の再起動は初回を含め同じジョブにつき10試行までです。枠待ちと起動失敗時は原則60秒後に再確認します。待機中のジョブが受付から30分、または10試行に達すると、理由を表示して失敗に移します。Workflowの受付後に未開始のまま起動を待つジョブにも30分の期限を適用します。再試行目安が翌日でも30分で停止し、失敗済みのジョブは自動再開しません。実行中の処理は受付からの経過時間だけでは中断しません。ローカルでCronを発火させない場合は自動再開・期限超過の反映が遅れるため、Workerのscheduledイベントを実行するか次の画面/API操作を待ってください。

同じジョブの利用枠は再計上せず、完了済みのAIステップはD1に保存した結果を再利用します。応答受領後の形式エラーは初回を含め同じステップにつき最大10試行で、再試行の間隔は5秒固定です。すべて実呼び出し枠を消費します。通信断など生成の成否が不明な場合は同じステップの自動再発行を禁止します。結果保存前に中断した記録は10分経過後、CronがWorkflowの終端状態を確認して失敗に移し、枠を解放します。Workflow状態を取得できない間は安全側で枠を保持します。失敗後の新しい再試行は再び利用枠を消費します。API受付時の予約は失敗でも返却しません。

保存履歴・実呼び出し履歴は30日で整理し、実行中の呼び出しと必要な再実行結果は保持します。生成結果・履歴にはユーザーの資料を含むためD1の既存のアクセス制御下で管理します。

`short-uuid@4.2.2` のAPIを保ち、依存する `uuid` だけをCommonJS対応の修正版 `11.1.1` 以上へoverrideしています。[GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq) の修正を取り込み、エディター `0.9.15` のID生成・編集データ形式を維持します。

## ローカル開発

Node.js 22.18以降の22系、または24.11以降（推奨24系）とpnpm 10.34.7を使用します。pnpmのバージョンは `package.json` の `packageManager` で固定しています。Cloudflare・Googleの認証情報なしでもローカルで動作確認できます。

Corepackを利用する場合は、初回に `corepack enable` を実行してpnpmを有効にしてください。

```sh
pnpm install --frozen-lockfile
pnpm run setup
pnpm run dev
```

<http://localhost:5173/> を開き、「ローカルデモを開く」を選択してください。`setup` は既存の `.dev.vars` を上書きせず、ローカルD1へマイグレーションを適用します。

デモには公開資料に基づくサンプル記事が4件含まれます。新しく保存した記事は、URLから取得した本文または入力したテキストの**文章の抜粋**を表示します。ローカルデモのメモリもトピックの集計と要点の抜粋です。AIによる要約と区別する表示を付けています。D1・R2・WorkflowsはローカルのCloudflareランタイムで動作します。

ローカルデモは `LOCAL_DEMO_ENABLED=true` かつ `APP_URL` がループバックホストの場合に有効です。ログイン先は同じプロトコル・ポートのループバックホスト、または明示したLAN用アドレスに限ります。本番設定では無効です。`.dev.vars`、`.wrangler`、`dist` はGit管理対象外です。

同じWi-Fiのスマホで試す場合は、MacのプライベートIPv4アドレスを確認し、`.dev.vars` に `LOCAL_DEMO_LAN_ORIGIN=http://MacのIPv4アドレス:5173` を追加して `pnpm run dev:lan` で起動します。`APP_URL` は `http://localhost:5173` のままにします。スマホからそのLAN用URLを開き、「ローカルデモを開く」を選択してください。Macの画面と同じデモデータを利用できます。IPv4アドレスが変わった場合は設定を更新して再起動します。

## ローカルでWorkers AIを使う

Cloudflareにログインしたうえで、`.dev.vars` に次を設定し、開発サーバーを再起動します。

```dotenv
LOCAL_DEMO_ENABLED=true
WORKERS_AI_ENABLED=true
AI_MODEL=@cf/qwen/qwen3-30b-a3b-fp8
```

```sh
pnpm exec wrangler login
pnpm run dev:lan
```

すでにWranglerでログイン済みなら、再ログインは不要です。`WORKERS_AI_ENABLED` は起動時のプロセス環境変数でも指定でき、`.dev.vars` より優先します。Cloudflare環境を指定している場合は `.dev.vars.<環境名>` を優先して読みます。モデルは `AI_MODEL` で変更できます。要約・問い・メモリでは保存形式の制約をJSON Schemaとして渡すため、[JSON Mode](https://developers.cloudflare.com/workers-ai/features/json-mode/) に対応したモデルを指定してください。

開発時だけ公式のリモートAIバインディングを追加し、D1・R2・Workflowsは引き続きローカルで動かします。AIを使うと、ストックの本文・要約・関連するメモリなどがCloudflareへ送信され、利用量に応じてWorkers AIの料金が発生します。APIトークンをアプリの入力欄や `VITE_` 付き変数に設定する必要はありません。[Cloudflareのローカル開発の説明](https://developers.cloudflare.com/workers/local-development/)

画面上部がWorkers AI利用中の案内に変わり、`GET /api/config` は `aiEnabled: true` と `aiModel` を返します。新しいストックを追加すると、要約・問い・プロジェクトとユーザーのメモリをAIで生成し、問いからプ譜も生成できます。生成結果の `model` で実際に使用したモデルを確認できます。既存のサンプル記事・問い・プ譜は自動的には再生成しません。AIを使わないデモに戻す場合は `WORKERS_AI_ENABLED=false` にして再起動してください。

## Cloudflareの本番設定

本番URLはビルド時の環境変数 `APP_URL` で指定します。以下は環境を新しく構築する場合の手順です。既存環境ではリソースを重複作成せず、設定と未適用マイグレーションを確認してください。

1. Cloudflareアカウントへログインし、D1・非公開R2バケット・OAuth用KVを作成します。

   ```sh
   pnpm exec wrangler login
   pnpm exec wrangler d1 create stock-db
   pnpm exec wrangler r2 bucket create pufu-lens-stock-content
   pnpm exec wrangler kv namespace create OAUTH_KV --env production
   ```

2. `wrangler.jsonc` の `env.production` を編集します。
   - D1・KVのIDはゼロのプレースホルダーのままにします。環境変数 `D1_DATABASE_ID`、`OAUTH_KV_ID` に実際のIDを設定すると、本番ビルドで生成設定へ注入されます。
   - `vars.APP_URL` の `https://app.example.invalid` はダミー値のままにします。本番ビルド時にプロセス環境変数 `APP_URL` から生成設定へ注入します。
   - 独自ドメインを使う場合はCloudflareのWorkerのルート／カスタムドメインを設定します。
   - `LOCAL_DEMO_ENABLED` は `false` のままにします。
   - R2は公開アクセスを有効にしません。

3. GoogleのSecretを登録します。値は対話入力してください。

   ```sh
   pnpm exec wrangler secret put GOOGLE_CLIENT_ID --env production
   pnpm exec wrangler secret put GOOGLE_CLIENT_SECRET --env production
   ```

4. 環境変数 `APP_URL` に実際のHTTPSオリジンを設定して、本番ビルドを先に検証し、マイグレーション適用とデプロイを実行します。

   ```sh
   export APP_URL="https://your-app.your-account.workers.dev" # 実際のURLに置き換える
   export D1_DATABASE_ID="実際のD1データベースUUID"
   export OAUTH_KV_ID="実際のOAuth KVの32桁ID"
   pnpm run build:production
   pnpm run db:migrate:production
   pnpm exec wrangler deploy --env production
   ```

`APP_URL` はパス・クエリ・フラグメント・認証情報を含まないHTTPSオリジンにします。末尾の `/` は除去されます。未設定、不正なURL、localhost、`.invalid` のダミー値では本番ビルドを停止します。`.dev.vars.production` の値は本番ビルドへ自動注入されません。`pnpm run deploy` も同じ環境変数が必要です。通常の `pnpm run build` とローカル開発には不要です。D1・KVも未設定・不正形式・ゼロのIDでは本番ビルドを停止します。生成された `dist` はGit管理対象外です。`db:migrate:production` は本番ビルドが生成した `dist/pufu_lens_stock/wrangler.json` を明示的に使うため、先に本番ビルドを成功させてください。

この設定はアプリのURL設定であり、Cloudflareのドメイン割り当てやGoogle側のOAuth設定は変更しません。URLは秘密情報として扱いません。Git履歴やActionsのログなどから既存URLが見える場合があります。

Workers AI、Browser Run、Workflowsの利用量に応じた費用が発生します。標準のモデルは `@cf/qwen/qwen3-30b-a3b-fp8` で、`AI_MODEL` から変更できます。モデルは、[仕様に示すJSON形式](#非同期処理とデータ整合性)を返せるテキスト生成モデルを指定してください。

`env.production` にAIとブラウザのバインディング、2つのWorkflows、毎分のCronを定義しています。Cronは未起動の処理要求を再送し、中断された処理の状態を回復します。本文削除の失敗は自動で再試行します。

環境構築後は、公開画面・Googleログイン・デモ無効化・未認証APIの拒否に加え、ログイン後の保存・Workers AIによる生成・Browser Runによる本文取得を確認してください。この文書は現在の本番環境の検証結果を保証するものではありません。

### GitHub Actionsによる自動デプロイ

[CI](../.github/workflows/ci.yml) は、`main` 向けPRの作成・更新時に検証のみを実行します。[Cloudflare Deploy](../.github/workflows/cloudflare-deploy.yml) は、PRのマージなどで `main` が更新されたときだけ起動し、検証成功後に既存の本番環境へデプロイします。PRの更新時はデプロイ用ワークフロー自体が起動しません。元リポジトリ `dyson-yamashita/pufu-lens-stock` の `main` 更新だけがデプロイ対象です。forkのPRや別ブランチからはデプロイしません。文書だけの変更でも、main更新時はデプロイ用ワークフローの対象です。

初期設定として、リポジトリの **Settings → Environments → New environment** で `production` を作成し、Environment secretsに次の2つを登録してください。値をIssue・PR・チャットや設定ファイルに貼り付けないでください。

| Environment secret      | 内容                                                 |
| ----------------------- | ---------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`  | この本番アカウントに範囲を限定したデプロイ用トークン |
| `CLOUDFLARE_ACCOUNT_ID` | 本番Worker・D1・R2を所有するアカウントID             |

同じ `production` Environmentの **Secrets** に次の3つを登録してください。Workflowはこれらを本番ビルドにだけ渡します。未設定・不正値ならビルドで停止し、本番DBやWorkerは変更しません。

| Environment secret | 内容                     |
| ------------------ | ------------------------ |
| `APP_URL`          | 実際のHTTPSオリジン      |
| `D1_DATABASE_ID`   | 本番D1データベースのUUID |
| `OAUTH_KV_ID`      | 本番OAuth KVの32桁ID     |

これら3つは認証情報ではありませんが、Actionsログで登録値をマスクするためSecretsで管理します。同名のVariablesから移す場合は、Secretsへの登録を確認してからVariablesを削除してください。マスクは変換後の値や過去のログ・Git履歴まで隠すものではありません。

APIトークンは [Cloudflare公式のCI/CD手順](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/) の「Edit Cloudflare Workers」テンプレートを基に作成し、このアプリが利用するリソースの権限だけを付けてください。D1マイグレーションにはアカウントの **D1: Edit** が必要です。既存のR2・AIなどのバインディングに必要な参照権限を維持し、別アカウント、不要なゾーン、Global API Keyへのアクセスは与えないでください。

`production` の **Deployment branches and tags** は **Selected branches and tags → Branch: main** に制限してください。マージ後すぐの自動実行にする場合はRequired reviewersを設定しません。GitHubのmainブランチ保護・RulesetでPR経由の変更と `Check` の成功を要求し、ワークフローや依存関係を含む変更をレビューしてください。ワークフロー内の条件だけでは、mainへ悪意ある変更を書き込める管理者からSecretsを保護できません。

### mainへの直接pushを禁止する

GitHubのRulesetは、PRのマージだけでは有効になりません。設定定義は [.github/main-ruleset.json](../.github/main-ruleset.json) にあります。`main` への更新にはPRを必須とし、force pushとブランチ削除を禁止します。管理者を含めてルールのバイパスを許可しません。個人で運用できるよう、他者による承認の必須件数は0件です。

この定義は直接pushの禁止を対象とし、必須ステータスチェックは含みません。上記の `Check` 成功もマージ条件にする場合は、GitHubでそのチェックを追加設定してください。

管理権限のあるアカウントで、リポジトリのルートから適用します。既存の同名Rulesetがある場合は新規作成せず、そのルールを更新してください。

```sh
gh api --method POST repos/{owner}/{repo}/rulesets --input .github/main-ruleset.json
gh api repos/{owner}/{repo}/rulesets
```

[GitHubの提供条件](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)により、Freeの非公開リポジトリでは利用できません。対応プランを使うか、公開化した後で適用します。設定ファイルの追加やローカルのGitフックだけでは、サーバー側の直接pushを禁止できません。適用後はSettingsのRulesetsで有効状態、対象 `main`、バイパスなしを確認してください。

### 自動デプロイの実行順

実行順は次のとおりです。

1. [共通の検証ワークフロー](../.github/workflows/validate.yml) をSecretsなしで実行します。型チェック・lint・整形チェック・ビルド・依存監査のジョブと、Vitestの全テストを2分割したジョブを並列実行します。各ジョブで `pnpm install --frozen-lockfile` を行い、テストの内容・分離設定・実行対象は変えません。片方のテストが失敗しても残りの分割は実行し、すべての検証が成功した場合だけ従来の必須チェック `Check` が成功します。失敗・キャンセル・スキップは成功扱いにしません。並列化により同時に使うランナー数は増えます。ローカルの `pnpm run check` は従来どおり全検証を実行します。
2. デプロイジョブの `pnpm install --frozen-lockfile` はSecretsを渡さず実行します。`pnpm run build:production` にだけEnvironment secretsの `APP_URL`、`D1_DATABASE_ID`、`OAUTH_KV_ID` を渡します。Cloudflareのデプロイ認証情報やGoogle OAuthのSecretはビルドに渡しません。
3. 最後のステップだけに `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` のSecretsを渡し、未設定なら値を表示せず停止します。未適用の本番D1マイグレーションを順に適用し、成功後にWorkerを更新します。

依存関係は `pnpm-lock.yaml` と `pnpm install --frozen-lockfile` で固定します。脆弱性対策のoverrideと依存パッケージのビルド許可は `pnpm-workspace.yaml` にまとめ、許可済みの `esbuild`・`sharp`・`workerd` のビルドスクリプトだけを実行します。開発用のWranglerも明示的な依存として固定しています。

同一mainのデプロイは直列実行し、実行中の処理は後続pushでキャンセルしません。待機中の古い実行はGitHubのconcurrencyにより最新の実行へ置き換わる場合があります。マイグレーション後にWorker更新が失敗しても、成功済みのDB変更は戻りません。マイグレーションは旧Workerとも動く追加的な変更にし、削除・破壊的な変更は別途手順を検討してください。再実行では適用済みのマイグレーションをスキップします。

Googleの `GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET` はCloudflareのWorker Secretに保持し、GitHubへ複製しません。古いActions実行を再実行すると当時のコミットがデプロイされるため、対象コミットを確認してください。`.dev.vars*`・`.env*`・`.wrangler/`・`dist/` は引き続きGit管理対象外です。D1のIDや公開URLは接続先を識別する情報で、アクセス権を与える認証情報ではありません。新しい秘密をWranglerの `vars` やViteの `VITE_*` に設定しないでください。

Actionsはcheckout/setup-node/pnpm/action-setupをコミットSHAで固定し、`GITHUB_TOKEN` は `contents: read` のみに制限しています。checkoutの認証情報保持と依存キャッシュを無効にし、ビルド成果物やログファイルをArtifactsへアップロードしません。PRの検証に本番Secretsは不要です。公開リポジトリではActionsログも公開される前提で、環境変数の一覧表示やshellのトレースを追加しないでください。[GitHubの安全な利用ガイド](https://docs.github.com/en/actions/reference/security/secure-use)

## iOSショートカット

1. Web画面にログインし、「ショートカット連携」でトークンを発行します。端末ごとに発行し、必要なら特定のプロジェクトに限定してください。
2. iPhoneのショートカットを作成し、共有シートに表示する設定と、入力の「URL」を有効にします。
3. 保存先を毎回選ぶ場合は「URLの内容を取得」で次をGETし、返された `projects` の名前から選択して `id` をJSON本文の `project_id` に指定します。固定のプロジェクトIDを登録しても構いません。`project_id` は任意で、省略時はプロジェクト限定トークンなら限定先、限定なしトークンなら自分の全プロジェクトに保存します。限定トークンの保存先と異なるIDを指定すると `403` になります。

   ```http
   GET https://実際のホスト/api/v1/projects
   Authorization: Bearer <発行したトークン>
   ```

4. 記事のURLへではなく、**アプリの保存APIへ**次のPOSTを送信します。本文形式はJSONです。

   ```http
   POST https://実際のホスト/api/v1/stocks
   Authorization: Bearer <発行したトークン>
   Content-Type: application/json
   Idempotency-Key: <この保存操作のUUID>

   {
     "url": "共有シートから受け取った記事のURL",
     "note": "任意のメモ"
   }
   ```

5. 受付結果の `id` を確認して通知を表示します。新規保存は `202`、すべて保存済みの場合や同じ保存の再送は `200` です。全プロジェクトへの保存では代表となる1件の `id` が返ります。要約とメモリは非同期で更新されます。

通信の再試行には同じUUIDを使います。同じキーで内容を変えた場合は `409` になります。キーは30日間保持します。全プロジェクトへの保存後にプロジェクトを追加しても、同じキーの再送では追加先に保存しません。同じプロジェクト・同じ記事の重複も別途防止します。

トークンには「プロジェクト一覧取得」「記事保存」のみを許可します。発行時以外にはトークン全体を表示しません。サーバーには256ビットのランダム秘密値のSHA-256ハッシュのみを保存します。発行可能な有効トークンは無期限を含めて20個です。有効期限は1〜365日または無期限で、無期限でも手動で失効できます。発行APIの `expires_days` は日数を指定し、`null` を指定すると無期限、省略すると90日になります。無期限の場合、一覧APIの `expires_at` は `null` です。

## 開発と検証

```sh
pnpm run check
```

型チェック、lint、Vitest、整形チェック、クライアント／Workerのビルドを実行します。テストはMiniflareのD1・R2と実際のアプリのルートを使用します。Workflow基底クラスとAI・記事HTTP応答はテスト内で差し替えます。Cloudflare Workflowsの永続化・リトライそのものはNodeテストの対象外で、ローカルWorkersでもデモの処理を確認します。

`pnpm audit` で依存関係を検査できます。開発用Miniflareの脆弱な間接依存を避けるため、`undici` と `sharp` に更新済みバージョンのoverrideを指定しています。

開発サーバーの起動中に `pnpm run test:smoke` を実行すると、MDNの公開記事を取得し、実際のローカルWorkers・Workflows・R2・D1を通して保存と問い・メモリの生成を確認します。この検証で作成したプロジェクトと記事は終了時に削除します。デモ環境専用で、本番には接続しません。

### 開発用スキル

このリポジトリには [Superpowers](https://github.com/obra/superpowers) v7.0.0の15スキルと、既存コード向けの最小限のテストを作る `pragmatic-testing` を `.agents/skills/` に同梱しています。`pragmatic-testing` は指定された本文のまま保存しています。

[AGENTS.md](../AGENTS.md) に開始時の読み込みとスキルの使い分けを記載しています。PR作成前に [requesting-code-review](../.agents/skills/requesting-code-review/SKILL.md) を使い、独立したレビュー担当エージェントが変更全体を確認します。対応が必要な指摘を修正した後は、必要な検証と再レビューを実施します。Superpowersの取り込み元コミット・スキル一覧は [.agents/superpowers-source.json](../.agents/superpowers-source.json)、MITライセンスは [.agents/SUPERPOWERS-LICENSE](../.agents/SUPERPOWERS-LICENSE) にあります。補助スクリプトを含むスキルの原文を維持するため、`.agents/skills/` はアプリ用のESLint・Prettierの対象外です。

## ソース構成

- `src/`：Reactの日本語管理画面
- `server/api.ts`：認証を必要とするAPIとアクセス制御
- `server/auth.ts`：Googleログイン、セッション、トークン認証

- `server/pufu.ts`：プ譜の生成

- `shared/`：クライアントとサーバーで共有する型・入力検証
- `server/workflows.ts`：記事・メモリの非同期処理
- `migrations/`：D1のスキーマ
- `tests/`：認証、二重保存、削除、メモリ競合、処理パイプラインの検証
