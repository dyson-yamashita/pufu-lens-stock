## アプリの構成

Web記事や入力テキストを保存し、要約・問い・メモリ・プ譜へつなげます。Google認証を使い、データをユーザーごとに管理します。

| 要素         | 役割                                                                                |
| ------------ | ----------------------------------------------------------------------------------- |
| ユーザー     | 名前・自己紹介、複数プロジェクト、ユーザーメモリを持つ                              |
| プロジェクト | ストックの保存先。概要とプロジェクトメモリを持つ                                    |
| 記事         | URLから取得した本文、または入力テキストと要約。同じユーザーの複数ストックで共有する |
| ストック     | 記事と保存先プロジェクトの対応。メモ・お気に入りを持つ                              |
| 問い         | ストックに紐づくAIまたはユーザーの問い                                              |
| プ譜         | 問いに紐づく課題の解決案。1つの問いに複数作成できる                                 |
| 局面         | 1つのプ譜内で編集結果や振り返りを保持する段階                                       |

| 技術                      | 用途                                             |
| ------------------------- | ------------------------------------------------ |
| React / Vite              | 日本語のWeb画面とビルド                          |
| Cloudflare Workers / Hono | Web配信、認証、API                               |
| D1                        | ユーザー・ストック・問い・プ譜・メモリ・利用履歴 |
| 非公開R2                  | 記事の本文、MCP画像の期限付き配信用PNG           |
| Workflows / Cron          | 取得・生成の非同期実行、再試行と未起動処理の回復 |
| Workers AI                | 要約、問い、メモリ、プ譜の生成                   |
| Browser Run / Readability | 通常取得で本文が不足するページへの対応、本文抽出 |
| @goto-lab/pufu-editor     | プ譜の表示・編集と標準データ形式                 |

- Google OpenID Connectログイン（PKCE、state、nonce、IDトークン署名検証）とセッションCookie
- ユーザーごとのプロジェクト作成・編集・削除
- URL／テキストを選んで保存、一覧、検索、web／ユーザーの作成元フィルター、ページ送り
- 保存時のメモ、プロジェクト間の移動、削除、取得失敗の再試行
- iOSショートカット用Bearerトークンの発行・失効・有効期限・保存先制限
- 本文抽出、R2保存、Workers AIによる記事要約
- 本文120文字未満はAI要約を省略し、推測を加えず原文を表示。ひとことメモから問いとメモリを更新
- ストックごとに1つのAIの問いの自動生成、ユーザーの問いの手入力、問い一覧・検索・プロジェクト別表示、生成失敗の再試行
- プロジェクトとユーザーのメモリ更新、根拠記事の閲覧、テキストのダウンロード
- Workflowsの工程ごとの再試行、D1の処理要求、Cronによる未起動処理の回復
- メモリの更新番号による古い結果の上書き防止

ユーザーメモリは各プロジェクトのメモリを再要約するのではなく、対象プロジェクトに保存した記事の要約から直接生成します。同じ記事を複数プロジェクトに保存しても、ユーザー全体では1件に集計します。データはユーザーごとに管理し、プロジェクト公開時は[公開対象の情報](#プロジェクトの公開)を公開します。MCPで取得したプ譜画像には、URLを知る人が1時間閲覧できる[期限付きリンク](#プ譜の取得)を発行します。メモリ・個人メモ・取得本文は公開しません。

## 画面と基本操作

`/manual` に、ログインなしで読めるユーザーマニュアルを用意します。トップページとログイン後のサイドメニューから開けます。ストック・問い・プ譜・メモリ・公開・連携の基本操作を案内し、機能や利用手順が変わる場合だけ更新します。文言や見た目の微調整、内部改善はマニュアルに記録しません。

「記事をストック」のフォームで種別を「URL」「テキスト」から選べます。テキストは本文20,000文字まで、任意のタイトル200文字までです。タイトル未入力時は本文の先頭行（80文字まで）を使います。テキストも要約・AIの問い・両方のメモリ更新の対象で、詳細の「入力した本文」タブから読み返せます。

「あなたのメモリ」の上にある「すべての問い」メニューで、ストックから生まれた問いを閲覧できます。ストック一覧と記事詳細にも「問い」タブがあります。ローカルでAI未接続の場合は、記事の要点とプロジェクト名から定型の問いを生成します。

全体のストック・問い・プ譜の画面にあるプロジェクトメニューは一覧の絞り込みです。選択しても画面とURLは維持し、ストック／問い／プ譜のタブ間で選択を引き継ぎます。追加フォームの保存先にも選択したプロジェクトを反映します。サイドメニューのプロジェクトからは専用画面を開き、専用画面のストック・問い・プ譜にはプロジェクト選択メニューを表示しません。

全体のストック・問い・プ譜・メモリ画面には「ストック」「問い」「プ譜」「メモリ」のタブを表示します。「メモリ」は一覧のプロジェクト絞り込みにかかわらず「あなたのメモリ」を開きます。メモリのタブを経由して一覧に戻っても、プロジェクトの絞り込みは保持します。

サイドメニューは右上の「×」ボタンで閉じられ、閉じている間はヘッダーのハンバーガーボタンから再表示できます。広い画面で折りたたむと本文領域が広がります。モバイルでは重ねて表示し、閉じるボタン・背景のタップ・Escapeキーで閉じられます。

「すべてのストック」「すべての問い」の件数は、全体一覧への表示がオンのプロジェクトだけを合計します。検索や一覧の絞り込みには依存しません。`GET /projects` の `count`・`question_count` と表示設定を使い、既存のプロジェクト取得・定期更新で反映します。サイドメニューの各プロジェクトとその件数は、オフでも表示します。

各プロジェクトの「メモリ」の右にある「設定」タブから、プロジェクト名・プロジェクト概要を編集できます。保存後も設定画面を維持します。プロジェクトの削除も設定タブから行えます。全体画面には設定タブを表示しません。

プロジェクト追加フォームと設定画面の「詳細設定」には「ストック追加時にユーザーのメモリを更新する」のトグルを置きます。詳細設定は初期状態で折りたたみ、トグルの初期値はオンです。作成時にもオン／オフを選んで保存できます。オフにしてもプロジェクトメモリは更新しますが、そのプロジェクトだけへのストック追加・要約完了ではユーザーメモリを更新しません。ユーザーメモリの手動再生成や他プロジェクトからの更新でも、オフのプロジェクトの記事・メモ・所属情報を生成対象から外します。同じ記事がオンのプロジェクトにも保存されている場合は、オンの保存先の情報だけで1件として反映します。

その上に「すべてのストック・問い・プ譜の一覧に表示する」のトグルを置きます。`show_in_all_lists` は新規・既存とも初期値オンで、作成時の省略はオン、編集時の省略は現在値を維持します。`GET /projects` は真偽値として返します。オフのプロジェクトはプロジェクト未指定のストック・問い・プ譜一覧から除外し、検索・お気に入り・ページングの結果と総件数にも反映します。ストックのkeyword・semantic・hybridの全方式と、同じAPIを使うMCP一覧にも適用します。プロジェクトIDの明示指定やMCP接続の対象プロジェクト指定時は表示します。個別詳細の閲覧、プロジェクト一覧、メモリ更新の対象、公開設定には影響しません。表示設定だけの変更ではメモリを再生成しません。`0024_project_list_visibility.sql` で列を追加します。

変更は「保存」で確定し、既存のユーザーメモリも非同期で更新して対象の変更を反映します。`0018_project_user_memory.sql` で設定列を追加します。`GET /projects` は `include_in_user_memory` を真偽値で返し、`POST /projects` と `PATCH /projects/:id` は同じ真偽値を任意で受け付けます。作成時の省略はオン、編集時の省略は現在の値を維持します。

プロジェクトのタブは「ストック」「問い」「プ譜」「メモリ」「設定」の順です。「メモリ」タブでは、そのプロジェクトの興味の傾向・記事から得た知識・根拠記事を確認でき、再生成とテキスト保存も行えます。メモリ画面にも同じタブを表示し、プロジェクトを維持して他のタブへ切り替えられます。

「記事から得た知識」は1項目につき1〜3文・80〜120文字程度を目安にAIで簡潔に整理します。画面では既存の知識も最初の3行まで表示し、長い項目は「続きを読む」「閉じる」で切り替えます。根拠記事へのリンクは常に表示し、保存済みの全文やテキストのダウンロード内容は省略しません。生成の目安は次回の更新・全件再生成から反映し、既存データを一括で書き換えません。

ストックのフィルターは「すべて」「web」「ユーザー」「お気に入り」です。webはURLから保存した記事、ユーザーは入力したテキストです。ストック・問いの検索は入力中に結果を変えず、虫眼鏡ボタンまたはEnterで反映します。×ボタンは入力と検索条件を解除します。検索右側の更新ボタンは表示せず、処理状況は引き続き定期的に更新します。

## プロフィールとメモリへの反映

プロフィールの「表示設定」で「システムに合わせる」「ライト」「ダーク」を選べます。初期値は「システムに合わせる」です。変更は保存ボタンなしで即時反映し、このブラウザの `localStorage` に保存します。設定はアカウント間や端末間では同期しません。保存領域が利用できない場合も、そのページ内の切り替えは動作します。

システム設定の変更と同じブラウザの別タブでの選択にも追従します。Reactの起動前に背景とテーマを適用し、ブラウザのテーマ色・フォーム部品も切り替えます。プ譜は共通の設定をエディターの `dark` に渡し、切り替え時にエディターを再作成せず未保存の本文・コメントを保持します。MCP連携の許可画面には、非機密の表示設定Cookie `pufu_lens_theme` を使って手動選択を反映し、システム設定の場合はCSSのメディアクエリで追従します。許可画面のスクリプト禁止は維持します。

初回ログイン後はニックネーム（表示名・必須・80文字まで）を入力し、利用規約・プライバシーポリシーそれぞれへの同意にチェックして「OK」を押すと利用を開始できます。本名の入力は不要です。未完了の状態はDBで管理し、再ログイン・画面更新後も登録画面を表示します。通常API・ショートカット・MCPも登録完了まで利用できません。未登録でも本人情報の取得・ログアウト・退会は可能です。

`POST /api/v1/onboarding` は本人のWebセッションと同一Originのみ許可し、`name`、`terms_accepted: true`、`privacy_accepted: true`、`terms_version`、`privacy_version` を受け取ります。文書の版は `shared/legal.ts` で画面・検証・法的文書に共通化します。ニックネーム、完了日時、同意文書の版を同じ更新で保存し、完了後の再送では変更しません。MCP接続から開始した場合、ブラウザに紐づく10分以内の認可要求が残っていれば登録後に認可画面へ戻ります。期限切れの場合は接続先から再接続してください。ログアウト時は保留中の認可要求も解除します。

メニューの「プロフィール」でニックネームと自己紹介（任意・1,000文字まで）を編集できます。`PATCH /me` の本文は `{ "name": "表示名", "bio": "自己紹介" }` です。プロフィールの取得・更新は本人のWebセッションでのみ行えます。

要約済みの記事がある場合、自己紹介をユーザーメモリ生成の背景情報としてWorkers AIへ渡します。ニックネームはユーザーメモリの入力に使用しません。自己紹介だけの内容を記事由来の知識として扱いません。自己紹介を変更・削除するとユーザーメモリを非同期で更新し、同じ内容の再保存やニックネームだけの変更では再生成しません。プロジェクトメモリは従来どおりプロジェクト概要を参照します。

Worker更新前に `0033_privacy_onboarding.sql` を適用します。メール列を削除し、由来を判別できない旧表示名とGoogleプロフィール画像を消去して、既存利用者にも登録・同意を求めます。内部ユーザーID・セッション・プロジェクト等を維持し、Google名を入力に使ったユーザーメモリは破棄します。旧世代のユーザーメモリ処理を無効化し、登録完了時に保存済みコンテンツからの再生成を予約します。自由入力された本文の個人情報や、過去の基盤ログ・バックアップの消去はこのマイグレーションの対象外です。

AI生成結果のD1キャッシュも削除し、旧ユーザーメモリのWorkflow状態は永続キュー `privacy_cleanup_jobs` を使って毎分のCronで10件ずつ削除します。外部削除の失敗時は要求を残し、次回再試行します。ローカルデモではMiniflareの制約によりWorkflowの停止まで行います。古いAI処理が後から終了しても、世代と登録状態を確認して結果をDBへ書き戻しません。

続けて `0034_pufu_memory_privacy.sql` を適用し、プ譜生成用の内部入力に複製された旧ユーザーメモリも消去します。旧Workflowのキャッシュから再開する場合も、AI呼び出し直前にDBの移行後の最小世代を読み、それより古いユーザーメモリを入力から除外します。完成済みのプ譜本文・局面や、利用者自身の補足は保持します。

旧メモリを使って生成中だったプ譜は世代を進めて停止し、初回登録後に「再試行」で作り直せます。対応する旧プ譜のAI結果キャッシュとArticleWorkflow状態も削除対象にし、古いキャッシュからの再開・生成結果の遅延保存は現行世代と削除キューで防ぎます。

0033はメール列を削除するため旧Workerとは互換性がありません。本番反映時はメンテナンス枠でマイグレーションとWorker更新を連続実施し、更新失敗時は修正版のWorkerを適用してください。旧Workerへ戻すだけでは復旧しません。

### 退会

プロフィールの退会欄は初期状態では閉じています。「退会するには？」で開閉し、「退会する」から削除対象を確認して、「すべて削除して退会する」で確定します。プロフィール・プロジェクト（公開分を含む）・ストック・入力本文・メモ・独立した問い・プ譜の全局面・メモリ・利用履歴・Xの登録トークンを削除します。全端末のセッションとショートカット連携トークンを無効にし、MCPの認可・トークンも削除します。Googleアカウント自体は削除しません。削除したデータは復元できません。

Worker更新前に `0022_account_deletion.sql` を適用してください。`DELETE /api/v1/me` は同一Originの本人のWebセッションのみ許可します。D1のユーザー削除と後処理要求を原子的に確定し、R2の本人のプレフィックスにある旧本文とWorkflowの保存状態も削除します。全削除の完了時は `200 { ok: true, cleanup_pending: false }`、一時障害または処理量が多い場合は `202 { ok: true, cleanup_pending: true }` を返し、毎分のCronで削除を継続します。後処理には内部IDだけを残し、完了後にその要求も削除します。再度Googleログインした場合は新規ユーザーとして登録され、以前のデータは引き継ぎません。

現行MiniflareのローカルWorkflowは保存状態の削除APIを未実装のため、ローカルデモでは処理の停止までを行います。D1・R2・MCPの認可とトークンはローカルでも削除します。ローカルでCronを実行していない場合、残った削除は次回のデモログインでも進めます。デモの再登録では各IDを新しくし、旧データの後処理が新しいデータを削除しないよう分離します。

### メモリの差分更新と再生成

通常のメモリ更新は、現在のメモリに未反映の記事要約だけを統合します。「再生成」では確認ダイアログで「未反映分を反映」「全件から再生成」を選択でき、対象の反映済み・未反映・要約未完了の件数も確認できます。手動再生成は選択中のプロジェクトまたは「あなたのメモリ」だけを更新します。ストック追加時の自動更新は保存先プロジェクトに反映し、詳細設定がオンの場合は「あなたのメモリ」にも反映します。反映状況の件数もそれぞれの対象範囲で集計します。記事の削除・移動・メモや要約の変更、自己紹介やプロジェクト情報の変更がある場合は、古い情報を残さないため全件更新に切り替わります。既存メモリの初回更新も、反映履歴を確立するため全件更新します。

反映状況は根拠として画面に表示された記事数ではなく、生成に取り込んだ記事と入力内容から管理します。要約が未完了の記事は完了後に自動反映し、生成失敗・利用枠待ち・古い更新番号の結果では反映済みにしません。`0015_incremental_memory.sql` で取り込み履歴と更新方法の保存領域を追加します。

## 問い

問いはプロジェクトに所属し、ストックへの紐づけは任意です。所有者は `問い → プロジェクト → ユーザー` の関係で確認します。ストックの保存受付と同じトランザクションでAIの問いの生成待ちを登録し、要約ができた時点で1つ生成します。要約済みの記事を別プロジェクトへ保存した場合も、そのストック用の問いを生成します。再送・同じ保存先への重複保存・生成の再試行でAIの問いの件数は増えません。同じプロジェクトのストックを複数関連付けられます。ストックを削除しても問いは保持し、その関連だけを解除します。単一の生成元に連なる問い・プ譜はストックの移動に追随しますが、共有関連がプロジェクト境界をまたぐ移動は409で拒否します。所属プロジェクトの削除では問いも削除されます。

問いの画面にある「問いを追加」から、プロジェクトを選び、500文字までの問いを手入力できます。関連するストックは複数選択でき、省略も可能です。AIの問いは各ストック1件を保ち、ユーザーの問いは同じストックに複数追加できます。ストックの問いタブでは、紐づくAI・ユーザーの問いをすべて表示します。

`POST /questions` は `{ "project_id": "プロジェクトID", "stock_id": null, "text": "問いの本文", "request_id": "任意のUUID" }` を受け付け、`source=user`、`status=ready` で保存します。`stock_id` は省略またはnullで独立した問いとなり、指定する場合は同じプロジェクトのストックに限ります。複数関連には `stock_ids` を指定します。`PATCH /questions/:id` の `stock_ids` で関連全体を置き換え、空配列で解除できます。従来の `stock_id` だけの入力も保存先を推定して受け付けます。REST APIは本人のWebセッションのみ利用でき、MCPでは別のOAuth認可で同じ処理を利用します。作成元はサーバーが決めます。フォームは同じ保存の再試行に同じ `request_id` を使い、重複を防ぎます。成功時は `201`、再送は `200`、同じIDで異なる内容は `409` です。`GET /stocks/:id/question` はAIの問いを `question`、紐づくすべての問いを `questions` で返します。

問いのラベルは作成元の「AI」「ユーザー」です。画面のフィルターは「AI」「ユーザー」「お気に入り」の3つで、選択中のフィルターを再度押すと解除して全件表示に戻ります。`GET /questions` は `project_id`、`q`、`source`（`all / ai / user`）、`favorite`（`true` のときお気に入りのみ）、`status`（`all / ready / processing / failed`）、`page` を受け付け、24件ずつ返します。既存の自動生成した問いの `source` は `ai` で、生成前・失敗時も同じ作成元です。内部の生成状態は `queued / generating / ready / failed` で保持し、生成待ちや失敗の状況は問い本文の領域で表示します。問いの生成失敗では記事の要約を保持し、問いだけを再試行できます。問いの生成は既存のArticleWorkflowで処理し、新しいCloudflareバインディングは不要です。本番では問い1件につきWorkers AIへの生成呼び出しが1回増えます（失敗時の再試行を除く）。

問いカードの日付横のスターで、お気に入りを登録・解除できます。未選択は背景透過の細い枠線、選択中は黄色の塗りつぶしです。`PATCH /questions/:id/favorite` に `{ "is_favorite": true }` または `false` を送り、保存した `id` と `is_favorite`（`0 / 1`）を返します。本人のWebセッションだけが変更でき、再読み込みやAI生成の再試行でも保持します。

問いの詳細画面下部の「問いを削除」で、確認後に問いとそのコメントを削除できます。関連するプ譜・局面・ストックは保持します。`DELETE /questions/:id` は本人のWebセッションのみ利用でき、元のストックと記事、別の問いは保持します。問い自身の生成ジョブは終了扱いにし、関連するプ譜の生成は継続します。削除したAIの問いは記事処理の完了や再試行でも自動的に作り直しません。ストックを削除して保存し直した場合は、新しいストックとしてAIの問いが生成されます。

## プ譜

サイドメニューに「すべてのプ譜」、全体と各プロジェクトの「問い」の隣に「プ譜」タブを表示します。プ譜カードの右矢印は表示しません。課題・関連する問いとストック・プロジェクト名・生成状況・現在の局面・作成日を一覧で確認し、選んだプ譜を既存の編集画面で開けます。関連する問いとストックはそれぞれ先頭1件を表示し、2件以上あれば「(他N件)」で残り件数を示します。詳細画面は「問い・気づき」のラベル1つの下に全件を箇条書きで表示します。生成待ち・生成中・失敗も含め、作成日時の降順（同時刻はID降順）で24件ずつ表示します。全体画面のプロジェクト絞り込みはストック・問いと共通です。`GET /api/v1/pufus` は本人のWebセッションから利用し、`project_id` と `page` を受け付けます。未指定時は全体一覧で非表示にしたプロジェクトを除外し、指定時は本人の該当プロジェクトだけを返します。生成時の文脈とプ譜本文は一覧APIに含めません。

「プ譜」一覧の「プ譜を追加」から、保存先のプロジェクトと獲得目標を入力して、問いを紐付けずにプ譜を生成できます。保存先は選択中のプロジェクト（全体表示では先頭のプロジェクト）を初期値にし、変更できます。

問い一覧の本文、またはストックの問いタブから問いの詳細を開きます。下部の「問いの解決を考える」から課題を入力し、「プ譜を作成」を押します。課題は前後の空白を除いて、そのまま獲得目標になります。勝利条件・中間目的・施策・廟算八要素を、問い・プロジェクトの説明・ユーザーとプロジェクトのメモリから生成します。関連するストックがあれば、その要約とメモも使います。独立した問いでもプ譜を作成でき、生成時のスナップショットの `stock` はnullです。問いなしの生成では `question` と `stock` がnullです。問いから生成する場合は作成元1問を設定し、その問いに関連する全ストックをプ譜の関連と `context.stocks` に引き継ぎます。大量資料ではIDをすべて保持し、保存用の資料JSONは128,000文字、AIへ渡す資料JSONは14,000文字以内に抜粋します。

一覧・問いからの生成は共通フォームを使い、獲得目標の下に「廟算八要素・取り組む予定の施策」の任意テキストエリア（4,000文字まで）を表示します。補足は前後の空白を除き、受付時の `context.details` に保存してAIへ資料として渡し、八要素と施策の生成に利用します。補足だけ変更した場合も新しいリクエストIDを使い、同じIDで異なる補足が送られた場合は409を返します。既存の生成上限・ジョブ・再試行処理を共用します。

生成は既存のArticleWorkflow内で非同期に処理し、画面を閉じても継続します。1つの問いに複数のプ譜を保存でき、再生成は新しい作成として行います。生成失敗時は同じ入力を使って再試行できます。新しい生成・明示的な再試行は利用量制限の対象です。単一の生成元に連なるプ譜はストックの移動に追随します。複数関連がプロジェクト境界をまたぐ移動は409で拒否します。ストックや問いの削除ではプ譜と局面を保持し、プロジェクトの削除ではプ譜も削除します。

プ譜の「問い・気づきとストックの関連を編集」で、同じプロジェクトの問いとストックを複数選べます。`PATCH /api/v1/pufus/:id/relations` は `{ revision, question_ids, stock_ids }` を受け取り、競合時は409を返します。各関連配列は最大100件で、保存済みの関連本文・タイトルは `questions`・`stocks`、IDは `question_ids`・`stock_ids` で返します。本文編集と同時には関連を保存できません。

生成済み（`ready`）のプ譜が1つ以上ある問いには、AI／ユーザーラベルの横に「プ譜」を表示します。問いの取得APIは `has_pufu`（`0 / 1`）を返し、一覧・詳細・ストックの問いタブで共通の判定を使います。生成中・生成失敗だけの場合は表示しません。

通常画面は選択中の局面の保存済みSVGを表示し、画像を押すとピンチ拡大・ドラッグ移動ができるモーダルを開きます。画像右下の「編集する」で `@goto-lab/pufu-editor@0.9.19` のReactコンポーネントを組み込んだ編集モーダルを開きます。狭い表示領域ではエディター標準の全体マップで横並びのプ譜を移動・閲覧します。iframeは使用せず、同梱のTailwind CSSをビルド時に `.pufu-editor-root` 配下に限定しています。初期データを編集中に再取得して差し替えず、「保存」で `getScoreJson` の内容を取得して画像を更新します。未保存のまま編集画面を閉じる・画面を離れる際は確認し、別画面からの同時保存は更新番号で競合を検出します。JSONは保存済みの局面をエディター標準の `ProjectScoreModel` 形式でダウンロードできます。自己紹介は生成リクエストに直接含めず、ユーザーメモリを通じて間接的に反映します。

「ダウンロード」を押すと形式選択のダイアログを開き、JSONまたは画像（PNG）を選べます。選択中の局面の保存済み内容を出力します。PNGはプレビューと同じ画像生成処理・日本語フォント・テーマを使用し、ブラウザ内のWASMで生成します。WASMとフォントはPNG出力時に読み込み、画像・プ譜を外部サービスへ送信せず、AIやサーバー側の画像保存を使用しません。

プ譜は第1局面から始まり、すべての局面で本文と各項目のコメントを編集できます。「局面を追加」は最新局面の編集内容を保存し、コメントを含めて次の局面へ引き継ぎます。AIの再生成は行いません。過去の局面も「◀」「▶」で移動して修正・保存でき、ほかの局面の内容は変更しません。矢印は移動先の局面がある場合だけ表示します。局面切り替え時にも未保存の変更を確認します。既存のプ譜は `0012_pufu_phases.sql` で、現在の編集内容を保持した第1局面として移行します。

ローカルデモでAIが未接続の場合は、問い・課題・メモリから定型の案を作成し、その旨を表示します。本物の生成にはWorkers AIバインディングが必要です。AIへの出力指示と検証はプ譜専用で、文章の案を生成させた後、UUIDと空のコメントをサーバーで補います。未確認の予算・担当者・期限を事実として埋めません。

| メソッド・パス                                           | 用途                                                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/questions/:id`                              | 問いの詳細と関連するプ譜の一覧                                                                          |
| `GET /api/v1/questions/:id/pufu`                         | 問いに紐づく最新の完成済みプ譜の最新局面を読み取り専用で取得。MCPでも利用可                             |
| `GET /api/v1/questions/:question_id/pufu/:pufu_id`       | 指定した問いに紐づくプ譜の最新局面をEditor互換JSONで取得。MCPでも利用可                                 |
| `GET /api/v1/questions/:question_id/pufu/:pufu_id/image` | 指定したプ譜の最新局面からPNGをリクエスト時に生成。MCPでも利用可                                        |
| `POST /api/v1/questions/:id/pufus`                       | `{ task, request_id }` で生成受付。作成時202、同じUUIDでの再送200、異なる入力での再利用409              |
| `GET /api/v1/pufus/:id`                                  | プ譜・状態・生成時の文脈と局面一覧 `phases`、最新局面番号 `current_phase` を取得                        |

`pufu_scores` に原案・最新の編集結果・入力時点の問いとメモリのスナップショット（内容・更新番号）・モデル・エディターのバージョン、`pufu_phases` に各局面の編集結果を保持します。メモリが後で変わっても、生成した案の根拠を確認できます。プ譜の作成・編集・局面追加で既存のメモリは更新しません。ライセンス文は [pufu-editor.txt](../public/licenses/pufu-editor.txt) に同梱しています。

## 時系列コメント

ストック詳細の「コメント」タブ、問いの詳細、およびプ譜の表示中の局面に、共通のコメント欄を表示します。ストックではタブを往復しても未投稿の下書きや送信中の状態を保持します。本文は前後の空白を除いて1〜2,000文字で、改行を保ちます。作成元（本人／AI連携）・作成者・日時とともに古い順に50件ずつ表示し、「更新」と「続きを読み込む」で履歴を取得できます。

プ譜の局面切り替えでは、対象・局面ごとの未投稿の下書きと再送IDを画面内で保持し、送信成功時に該当下書きだけを消します。送信中に別局面へ移動して戻っても、二重送信を防ぎます。画面を閉じたり再読み込みした場合の下書き保存は行いません。

コメントは対象の所有ユーザー内で共有します。同じユーザーのWebと複数のMCP接続は、許可されたプロジェクト・操作の範囲で、互いが残したコメントを参照・追記できます。作成元や接続の違いはアクセス制限に使いません。他ユーザーへの共有・通知・コメント単体の編集や削除は提供しません。

D1の`comments`テーブルに`target_type`（`stock / question / pufu`）、`target_id`、`phase`、`body`、`author_id`、`author_kind`（`user / agent`）、`created_at`を保存します。プ譜だけは実在する局面番号`phase`が必須で、それ以外の対象には指定できません。プ譜エディターの各要素のコメントとは独立し、局面追加時も引き継ぎません。対象・プロジェクト・ユーザーの削除では、外部キーと削除トリガーで関連コメントを同時に削除します。Worker更新前に`0026_comments.sql`を適用してください。

`GET /api/v1/comments`は`target_type`・`target_id`、プ譜では`phase`、任意の`page`（既定1、1〜5000）を受け取り、`comments`と`has_more`を返します。`POST /api/v1/comments`は対象指定に`body`と`request_id`（UUID）を加え、保存した`comment`を返します。新規作成は201、同じID・対象・本文の再送は200、同じIDを異なる内容で再利用すると409です。作成者・作成元はサーバーが認証情報から決めます。

本人のセッションとMCPだけが利用できます。MCPではストックに`stocks:read / stocks:write`、問い・プ譜に`questions:read / questions:write`を適用し、接続のプロジェクト制限も検証します。対象が存在しない・他ユーザー所有・許可対象外のプロジェクト・存在しない局面は404です。公開API・画像・ダウンロード・AIメモリ・プ譜生成入力にコメントを追加しません。

## プロジェクトの公開

プロジェクトの「設定」→「公開設定」で公開できます。初期状態は非公開です。公開すると `/p/<公開ID>` の参照URLが発行され、ログイン前のトップページにも掲載されます。

- 公開する内容：プロジェクト名・公開用の紹介文、ストックのタイトル・URL・要約・要点・トピック、問い、紐づくプ譜の各局面と振り返り。公開プ譜の関連ストックと問い・気づきは初期状態で閉じ、見出しで開閉できます。局面は最新から表示し、「◀」「▶」で前後へ移動できます。公開詳細APIは `?phase=N` で指定局面を返し、省略時は最新局面を返します。レスポンスの `phase` は表示局面、`current_phase` は最新局面です。不正な指定は400、存在しない局面・非公開プ譜は404です。
- 公開しない内容：内部用のプロジェクト概要、ユーザー／プロジェクトのメモリ、ストックの個人メモ・取得本文、生成時のコンテキスト。
- 公開ページはストック・問い・気づき・プ譜の3タブで切り替えられます。`GET /api/public/projects/:key/pufus` は、既存の公開詳細と同じ条件を満たす公開可能な問いに紐づく完成済みプ譜を12件ずつ返します。個別プロジェクトの `pufu_count` も同じ条件で数えます。プ譜件数は目録キャッシュに追加しません。
- プ譜そのものに記載した内容は公開されます。公開前に各内容を確認してください。
- 公開後の追加・編集も反映されます。非公開にするとトップ掲載とURLからの参照が停止します。再公開時は同じURLを使います。
- 公開ページと `/api/public/projects` 以下のAPIは参照専用です。公開設定は所有者のログインセッションからのみ変更でき、MCPやショートカットのトークンでは変更できません。

トップページの公開一覧（`GET /api/public/projects`）だけは、ページごとのJSONをWorkers Cache APIに60秒保存します。各取得でD1の最新revisionを1行確認し、キャッシュがあれば一覧の取得・件数集計を省きます。公開プロジェクトの追加・公開設定・名前・紹介文・削除と、公開プロジェクト内のストック・問いの追加・削除・所属・公開件数の変更は、DBトリガーが同じトランザクションでrevisionを更新します。非公開化や退会後の取得では、他拠点に残る旧revisionのキャッシュも再利用しません。キャッシュ投入が更新より遅れても旧revisionにだけ保存します。

共有するのは従来の公開フィールドだけです。Cookieや認証情報をキャッシュキー・保存レスポンスに含めず、キーにはサーバー設定のorigin・revision・正規化したページ番号だけを使います。ブラウザ向けは引き続き`Cache-Control: no-store`です。個別の公開ページAPIと認証済みAPIはキャッシュしません。Cache APIが利用できない環境や読み書き障害時はDBから取得し、revisionを確認できない場合は旧キャッシュを返さずエラーにします。追加Secret・bindingは不要です。

[本番環境の設定](#cloudflareの本番設定)に沿って本番ビルドを行った後、デプロイ前に `pnpm run db:migrate:production` で `0020_public_projects.sql`・`0035_public_directory_cache.sql` を含む未適用のマイグレーションを適用してください。既存プロジェクトも非公開のまま移行します。

## X連携

「外部連携」からX公式APIの **Bearer Token** を登録・更新・削除できます。MCP接続も同じ画面から利用できます。Xの開発者契約・読み取り権限・利用枠が必要です。登録時は保存のみ行い、実際の投稿取得で認証を確認します。

「記事をストック」でXの投稿URLを入力すると本文を取得します。短い投稿と長文投稿に対応します。取得できない場合もURLは残り、詳細画面から本文を貼り付けて補完し、再試行できます。既に保存したURLへの再保存は重複扱いとなるため、取得失敗後の補完には詳細画面を使ってください。

### X連携の管理者設定

管理者は[本番環境の設定](#cloudflareの本番設定)に沿って、本番DBへマイグレーション `0017_external_integrations.sql` を適用してください。`INTEGRATION_ENCRYPTION_KEY` を64文字のランダムな16進数として生成し、Cloudflare Workers Secretに設定します。

```sh
openssl rand -hex 32
corepack pnpm exec wrangler secret put INTEGRATION_ENCRYPTION_KEY --env production
```

生成した値をSecretの登録時に対話入力してください。値はログ・Git・チャットへ貼らず、安全に保管してください。キーを変更すると既存のトークンを復号できなくなるため、各ユーザーの再登録が必要です。ローカルではGit管理対象外の `.dev.vars` に設定します。

### 認証情報の保護

認証情報はユーザーIDに結び付けたAES-256-GCMで暗号化し、サーバー側のDBに保存します。APIには登録状態だけを返し、MCP・共有用トークンによる管理アクセスを拒否します。復号したトークンは固定の `https://api.x.com/2/tweets/{id}` にだけ送信し、リダイレクトを拒否します。

`add_pufu_phase` は `pufu_id`・最新の `revision`・操作ごとの `request_id`（UUID）を受け取り、最新局面の次の番号へ追加します。`projectScore` 省略時は最新局面を複製し、指定時は取得したJSONを土台に変更箇所だけを差し替えた完全なProjectScoreModelを保存します。既存局面の本文・コメント・日時・問いとストックの関連は変更しません。`reason`（任意、1〜2,000文字）は新局面の最初の時系列コメントとして、局面・本体・再送記録と同じD1トランザクションで保存します。AI生成は行いません。古いrevision・同じrequest_idで異なる入力は409、同じ入力の再送は局面を重複させず元の `phase`・`revision`・`updated_at` と `created: false` を返します。再送結果の `current_phase` も当該操作で作成した番号です。現在の最新状態は `get_pufu` で再取得します。新規作成時は `created: true`、理由ありの場合は `comment_id` も返します。`pufus:write` が必要で、再送時にも現在の所有者と接続のプロジェクト制限を検証します。入力・保存サイズの上限は256KiBです。再送記録はプ譜・アカウントの削除時に連鎖削除します。Webの局面追加は従来の保存・複製動作を維持します。

`get_pufu_guideline` はバージョン管理する静的な日本語ガイドラインを返します。`section` は `all / principles / goals / purposes / measures / elements / review`（既定 `all`）、`detail` は `summary / full`（既定 `full`）です。未知の引数・不正値を拒否し、JSONの `version: "1.0.0"`・`language: "ja"`・`section`・`detail`・`guidelines`・`sources`・`attribution` を返します。`goals` は獲得目標と勝利条件、`all` は全項目を含みます。要約は定義と要点、詳細は例・チェック観点・基本原則の推奨作成手順も含みます。呼び出し時にScrapboxへ通信せず、共通の認証・所有権確認を除いて利用者データを読み書きしません。既存MCP認証内で追加scopeなしに取得できます。`create_pufu` / `update_pufu` の説明とサーバーinstructionsで事前参照を案内し、取得・レビューだけでの自動修正は行いません。JSONの形式は既存の作成・編集スキーマを正とし、記述内容や参照の有無で保存を拒否しません。原著の公式仕様そのものではなく、Pufu Lens向けの再構成である旨と参照元URLを返します。

`update_pufu` は `pufu_id`・`revision`・`projectScore` を受け取り、既存の局面保存処理で編集します。`phase` 省略は最新局面、指定時は既存の局面を更新します。局面は追加しません。`question_ids`・`stock_ids` は省略で維持、空配列で解除し、同一プロジェクト内の関連全体を置き換えます。互換用 `question_id` は省略で維持、nullで問いの関連をすべて解除し、IDで1問に置き換えます。既存の関連はAI問いの再生成中や失敗中も維持できます。最新局面の編集では一覧の課題も獲得目標に合わせます。古いrevisionは409、他人・許可外保存先・紐付け先の不一致は404です。作成・編集の本文上限は256KiBです。`get_pufu` で内容とrevisionを取得してから編集してください。作成・編集には新規の `pufus:write` が必要で、既存の許可には追加せず、再認可が必要です。

反映前に `0029_independent_pufus.sql` を適用します。既存のプ譜・局面・コメント・期限付き画像リンクを保全し、プ譜に保存先 `project_id` を追加、`question_id` をnullableにします。現在の複数関連への反映には続けて `0030_multiple_relations.sql` を適用します。関連テーブルへ既存の関係を引き継ぎ、ストック・問いの削除で関連先の本体を保持するよう外部キーを更新します。問いなしのプ譜はプロジェクト削除時に削除されます。Webの一覧・編集・コメント、MCPの取得・画像・ビューアーは問いなしでも利用できます。公開ページには従来どおり問いに紐づくプ譜だけを表示します。追加のSecretやbindingはありません。

`add_stock`・`add_question`には `project_id` と `request_id`（UUID）が必須です。`add_comment`は対象IDからプロジェクトを確認するため`project_id`は指定しません。同じ操作の通信再試行では同じUUIDを使います。ストックの要約・AIの問い・メモリは非同期で生成し、既存の保存件数・AI利用量制限を共通で適用します。

### 会話内のプ譜ビューアー

「プ譜を表示して」という依頼には `show_pufu` を使います。入力は `get_pufu_image` と同じ `pufu_id`、任意の `question_id` です。`pufu_id` 省略時は `question_id` を必須として最新の完成済みプ譜を選びます。`structuredContent` のタイトル・対象ID・局面・revision・更新日時・PNGのURLと寸法を、宣言した `outputSchema` に従って返します。`show_pufu` はBase64を返さず、未作成を `status: "not_created"` で区別し、URL発行に失敗した場合はMCPエラーにします。JSON取得・Base64画像取得の既存ツールと認証方式は維持します。`get_pufu_image` には表示用タイトルを追加します。

`@modelcontextprotocol/ext-apps` 2.0.3（既存の `@modelcontextprotocol/server` 2.3.1と互換）の公式ヘルパーで、`ui://pufu/viewer-v1.html` を `text/html;profile=mcp-app` のリソースとして登録します。ツールの `_meta.ui.resourceUri` と紐づけ、CSPの `resourceDomains` は `APP_URL` のオリジンに限定します。JS・CSSはHTMLに同梱し、画像は通常の `img` で読み込みます。直接APIへfetchせず、`connectDomains` は空です。回答本文のMarkdown画像を表示するためのCSP設定ではなく、Markdownで表示できなかった初回原因も有効期限だけと断定しません。

ビューアーは画像のload成功後に表示成功とし、未作成・生成中・取得失敗・閲覧不可を区別します。初期表示と「横幅に合わせる」では横幅100%で縦横比を保ち、画像全体の高さに枠を伸ばします。画像高に合わせたカードの高さをMCP Apps SDKのautoResizeでホストへ通知し、通常表示では高さを固定しません。ただし実際のカード高はホストの制約を受けます。拡大時は横幅100%時の枠高を維持し、枠内をスクロールできます。リサイズ時も横幅に合わせて画像高を再計算します。拡大は枠幅の最大6倍、パンはタッチのスクロールやマウスのドラッグで行います。全画面はホストが対応を通知した場合のみ要求し、画面の高さに合わせた枠内でスクロールします。非対応時はカード内の拡大と外部PNGリンクを使います。

画像URLは引き続き1時間有効です。初回表示・表示復帰・再マウント・PNG保存時に残り時間を確認し、期限切れまたは残り60秒未満なら、ホストの `tools/call` から `get_pufu_image` を呼びます。選択確定後は必ず同じ `pufu_id` だけを指定し、問いへの紐付け変更・解除後も同じプ譜を取得します。別のプ譜へ切り替えません。このツールは `_meta.ui.visibility: ["model", "app"]` とし、表示リソースは紐づけず、再取得による新しいカードを作りません。OAuthはホストのMCP経路に任せ、UIは認証トークンを取得・永続保存しません。

画像エラーを期限切れと決めつけず、自動再取得は最大1回です。同時要求をまとめ、古い応答を破棄します。失敗が続くと手動の「再取得」を案内し、定期ポーリングは行いません。表示済みの画像を時間経過だけで再読み込みせず、UIを起動しないホストでの自動復旧も保証しません。同じプ譜の最新完成局面へ変わった場合は「プ譜が更新されたため最新の内容を表示しています」と案内します。再発行と画像配信の両方で、既存の所有権・プロジェクト・紐づき・削除・生成状態を確認します。

反映後は接続先のツール・リソース情報を再読み込みしてください。ホストに再読み込み操作がない場合はMCP接続を再接続します。プ譜の作成・編集を利用する場合は前述の追加OAuthスコープとDB移行が必要です。追加のSecretはありません。Web版ChatGPTとiPhone版ChatGPTではそれぞれ、会話内表示、拡大・保存、期限切れ・更新後の再取得、削除後の拒否を実機で確認してください。自動テストやブラウザのエミュレーションと、ChatGPT実機の確認結果は分けて記録します。

### プ譜の取得

`get_question` は問いと紐づくプ譜の一覧 `pufus` を返します。取得するプ譜の `pufus[].id` を選び、`get_pufu` または `get_pufu_image` に、`pufu_id` を指定します。`question_id` は任意で、両方指定すると紐付けを検証します。`pufu_id` を省略する場合は `question_id` が必須です。複数登録されていても保存済みIDで選べます。閲覧権限は既存の `questions:read` を使い、問いとプ譜の紐づき、本人と認可されたプロジェクトをサーバー側で確認します。

`get_pufu_image` はリクエストのたびに、指定したプ譜の最新局面からPNGをその場で生成します。MCPの `content` 内に `type: "image", mimeType: "image/png", data: "Base64文字列"` の画像要素を返し、structuredContentにはプ譜ID・幅・高さ・バイト数・局面・更新番号等と、`image_url`・`download_url`・`expires_at` を返します。PNGのBase64をJSONにも重複させません。ユーザーへの表示は `show_pufu` を案内し、MCP Apps非対応環境では外部画像・ダウンロードリンクやBase64を使えます。URL発行の上限・一時障害時は `image_url_error` とBase64画像を返し、PNGファイルへの保存を案内します。未作成の場合はURLも発行しません。Base64へのフォールバック時も元データを再確認し、更新・削除競合やDB障害で現在の権限を確認できない場合はエラーとして画像を返しません。

画像URLは `GET /api/pufu-images/:token.png`、ダウンロードURLは同じURLの `?download=1` です。ログインや認証ヘッダーを持たないチャットの画像プロキシも取得できます。URLを知る人が閲覧できる期限付きの権限で、有効期限は発行から1時間です。256ビットの乱数を使い、DBにはそのハッシュだけを保存します。発行元はサーバーの `APP_URL` です。本番ではHTTPSのURLを設定してください。GET/HEADは `image/png`、`Cache-Control: no-store`、`Referrer-Policy: no-referrer`、外部画像表示用の `Cross-Origin-Resource-Policy: cross-origin`・`Access-Control-Allow-Origin: *`、`X-Robots-Tag: noindex, nofollow, noarchive` を返します。ダウンロード時は `Content-Disposition: attachment` です。リンクを知る人が取得済みの画像やチャット側の保存画像を後から回収することはできません。

MCPで生成したPNGだけを非公開R2のユーザー配下に一時保存し、D1の `pufu_image_links` に期限・所有者・問い/プ譜ID・プロジェクト・局面・更新番号を登録します。保存完了後にリンクを有効化します。未完了分を含めユーザーあたり同時50件までとし、PNG 2MiBの既存上限と合わせて保存量を制限します。アクセス時は期限と現在の所有権・プロジェクト・処理状態・局面・更新番号をD1で再確認し、期限切れ、移動、更新、削除、退会後は404です。期限切れ判定は削除処理と独立して行います。既存の毎分Cronで期限切れ画像と登録情報を最大100件ずつ削除し、削除に失敗した場合は次回再試行します。退会時のユーザー配下R2削除にも含めます。

プ譜の作成・保存・局面追加時には画像を生成しません。画像取得ではAI・ブラウザを使わず、保存済みの本文・コメント・更新日時を変更しません。認証済みPNG APIは毎回生成し、一時保存しません。MCPの画像URLへのアクセスは保存済みPNGを返すだけで、画像生成・AI・Workflowを起動しません。画像の準備をCronやWorkflowへ依頼することもありません。

認証済みAPIは `GET /api/v1/questions/:question_id/pufu/:pufu_id`（JSON）と `GET /api/v1/questions/:question_id/pufu/:pufu_id/image`（PNG）です。両方とも `Cache-Control: no-store` とし、PNGは `Content-Type: image/png` で返します。本人の認可範囲だけを取得し、公開設定だけでは他ユーザーのMCPに公開しません。指定したIDが存在しない・別の問いに紐づく場合は404、作成未完了（queued/generating/failed）は409です。別の完成済みプ譜へ置き換えて返しません。描画中の削除・別の問いや認可範囲外への移動は404、対象プ譜の更新競合は409として古い画像を返しません。描画中に同じ問いへ別の新しいプ譜が追加されても、指定したプ譜の取得は継続できます。APIキー・入力コンテキストも返しません。

互換用に `/api/v1/questions/:question_id/pufu` と `/api/v1/questions/:question_id/pufu/image`、MCPの `pufu_id` 省略も残します。省略時は既存の一覧順（作成日時の降順、同時刻はID降順）で最新の完成済みプ譜を選びます。完成済みがない場合は、JSON取得が `projectScore: null`、画像取得が `status: "not_created"` となり、画像を生成しません。

PNGはresvg WASM、日本語フォントは同梱の静的アセットを使います。文章合計30,000 UTF-16コード単位、600万画素、PNG 2MiBが上限です。上限超過は413、描画できない制御文字等は422、WASM/フォントの一時障害は503を返し、黙って切り詰めません。保存JSONの破損は既存のJSON取得と同じく500です。画像生成に失敗しても保存済みのプ譜は維持し、次のリクエストで再生成できます。Workers AIの利用枠は消費しません。画像生成ライブラリは [packages/pufu-image](../packages/pufu-image/README.md) にあります。

Worker更新前に `0025_pufu_image_links.sql` を適用してください。追加のSecretやbindingは不要です。既存の非公開 `CONTENT` R2とD1を使います。ViteビルドしたWorkerと静的アセット（`fonts/pufu-jp.otf` を含む）を一緒に反映してください。`ASSETS` bindingは設定済みです。

```json
{ "question_id": "保存した問いのID", "pufu_id": "get_questionのpufusから選んだID" }
```

ID指定時の返却項目は `question_id`（紐付けなしはnull）、`pufu_id`、`project_id`、`updated_at`、`revision`、`phase`、`projectScore` です。互換用のID省略時は従来のJSON形式を維持し、`pufu_id` を追加しません。`projectScore` はJSON文字列ではなく、利用中の `@goto-lab/pufu-editor@0.9.19` の [ProjectScoreModel](https://github.com/goto-lab/pufu-editor/blob/main/src/lib/models.ts) と同じJSONオブジェクトです。既存の保存用 `pufuScoreSchema` で形式を検証し、保存済みのJSONをそのまま返します。Editorの `getScoreJson`／JSONエクスポートと同じ構造で、`purposes[].measures`、全要素のUUID・文章・コメント・色と任意の施策ID・進捗を保持します。未設定の進捗を追加せず、配列の並べ替えや補完もしません。

`updated_at` は指定したプ譜の更新日時で、読み取れない日時は `null` です。問いが存在しない・他人の問い・許可プロジェクト外は既存詳細取得と同じ404、scope不足は403です。

旧データの第1局面は、本体の保存済みJSONを移行せず参照します。第2局面以降の局面欠落、完成済みプ譜のJSON欠落・破損・形式不整合は500、保存済みJSONのUTF-8サイズが256KiBを超える場合は413を返します。エラーを未作成として扱わず、内容も切り詰めません。MCPの `content`／`structuredContent` は既存ツールと同じ組み立てです。

この取得処理はSELECTのみを実行し、プ譜・局面・更新日時を変更しません。ジョブの起動、AI呼び出し、要約・生成・編集は行いません。生成時のメモリや文脈、モデル、原案は返却しません。

### ストック一覧の取得量と検索範囲

MCPの `list_stocks` は既定で `detail: "compact"` を使用します。検索対象はタイトル・要約全体（要点・トピックを含む）・メモです。記事本文・入力テキストは検索対象に含みません。抜粋はoverviewの先頭なので、一致語が要点やメモにある場合は抜粋に出ないことがあります。その場合は該当IDを `get_stock` で取得します。

| 引数      | 既定値       | 動作                                                                        |
| --------- | ------------ | --------------------------------------------------------------------------- |
| `limit`   | `24`         | 1〜24の整数。DB取得時の上限とページ幅。最新1件なら `1`                      |
| `sort_by` | `created_at` | ストックの保存日時。記事・動画の公開日時ではありません                      |
| `order`   | `desc`       | 新しい順。`asc` で古い順。同時刻は同じ方向のストックID順                    |
| `detail`  | `compact`    | ID・タイトル・短い要約・保存先・保存日時・記事状態を返す。`full` で従来形式 |
| `page`    | `1`          | 1〜5000。続きは同じ `limit`・並び順・フィルターでページを増やす             |

```json
{
  "limit": 5,
  "sort_by": "created_at",
  "order": "desc",
  "detail": "compact"
}
```

compactの各ストックは `id`、`title`、`project_id`、`project_name`、`created_at`、`status`、`summary_excerpt`、`summary_truncated` を返します。要約の抜粋は最大200文字（超過時は末尾の「…」を含む）です。`summary_truncated` はoverviewの先頭を切り詰めた場合に `true` となり、要約未生成時は抜粋が `null`、切り詰めが `false` になります。Unicodeコードポイント単位で切り詰め、サロゲートペアを分断しません。要約の要点・トピック・メモ・本文・URLなどは軽量一覧に含めません。

一覧の外側には `stocks`、フィルター後の総件数 `total`、`page`、実際のページ幅 `pageSize`、次ページの有無 `has_more`、`sort_by`、`order`、`detail` を返します。並び順の値は検証してから固定のSQL句を選び、件数・offsetはバインドします。プロジェクト限定・他ユーザーの除外・読み取り権限は、compact／fullの両方に適用します。

### 意味検索・ハイブリッド検索の設定

`list_stocks` と本人用 `GET /api/v1/stocks` では `mode` に `keyword`（既定）、`semantic`、`hybrid` を指定できます。qがない場合は従来の一覧を返し、AIやVectorizeは呼び出しません。Web画面は引き続きkeywordを使い、問いの検索方式も変わりません。

```json
{ "q": "AIに開発を任せるときの品質管理", "mode": "hybrid", "limit": 5, "detail": "compact" }
```

`q`は最大200文字で、日本語の長い検索文も使用できます。部分一致では英字の大文字・小文字を区別せず、`%`・`_`も通常の文字として検索します。D1のLIKEパターンの50バイト制限を受けない方式を使い、検索文をバイト数で切り詰めません。

semanticは意味の近さ、hybridはキーワード順位と意味検索順位のRRF（k=60）で並べます。この2方式では`order`/`sort_by`による保存日時順より関連度を優先し、応答は`sort_by: "relevance"`、`order: "desc"`です。`min_score`は0〜1、既定0.35で意味候補の最小類似度を調整します。初期値の検索精度は実データで評価してください。検索対象は現在のタイトル、正常な要約（概要/要点/トピック）、メモです。記事本文・入力テキストは対象外で、新たな要約生成も行いません。

両方式は各検索の上位100候補の範囲で結果を返します。`total`/`has_more`は候補集合に対する値です。`search.total_scope: "candidates"`、`candidate_limit: 100`、`candidates_truncated`を確認してください。全件を列挙するときはkeywordを使います。`search.indexed_count`/`pending_count`は同じ所有者・プロジェクト・絞り込み範囲の索引状態です。保存・編集後の索引更新やVectorize内部の反映には時間がかかります。

hybridが未設定・索引準備中・障害・利用上限で意味検索を実行できなければkeywordへ戻り、`search.mode`と`search.fallback_reason`（`not_configured`/`index_pending`/`service_error`/`rate_limited`）で明示します。semanticを明示した場合は503または429です。空のqは`empty_query`としてkeywordの一覧を返します。keywordの応答形式・正確な総件数・保存日時順は維持します。

#### 管理者の準備

既存環境は追加設定なしで動作します。有効化する場合だけ、Cloudflareで環境ごとにVectorize V2インデックスを作成してください。次は本番用の例で、開発用は別名を使用します。

```sh
pnpm exec wrangler vectorize create pufu-search-production --dimensions=1024 --metric=cosine
pnpm exec wrangler vectorize create-metadata-index pufu-search-production --property-name=project_id --type=string
```

metadata indexは最初の登録より先に作成します。Workers AIは既存の`AI` bindingを使い、埋め込みには生成用Qwenとは別に`@cf/baai/bge-m3`を固定で使用します。APIキーをクライアントやMCPへ渡す必要はありません。

- 本番ビルド時に`VECTORIZE_INDEX_NAME=pufu-search-production`を指定します。Viteが`SEARCH_INDEX` bindingを追加します。GitHub Actionsではproduction Environmentの**Variables**に同名を登録します。インデックスは事前に作成し、デプロイ資格情報にVectorizeの利用権限も必要です。
- ローカルは`.dev.vars`の`WORKERS_AI_ENABLED=true`と、作成済みの開発用`VECTORIZE_INDEX_NAME`を設定して再起動します。AI/Vectorizeは実Cloudflareへ接続し料金対象です。未設定のローカル開発では接続しません。
- `0023_stock_search.sql`をD1へ適用します。既存ストックも索引要求へ入ります。新規追加・タイトル/メモ/保存先の変更・記事要約の更新・削除はSQLトリガーで同期対象になります。既存の毎分Cronが1回最大10要求を処理します。
- 検索embeddingは初期上限`AI_SEARCH_DAILY_LIMIT=100`回/ユーザー/直近24時間、索引embeddingは`AI_INDEX_DAILY_LIMIT=200`回です。既存のAI全体回数・同時実行枠も共有し、失敗も回数に含めます。大規模な初回索引は日をまたいで進む場合があります。各入力は最大8000文字に制限します。

索引はVectorizeのユーザーnamespaceとproject_idフィルターを使い、結果はD1の現行索引ID・本人・現在のプロジェクト・全フィルターで再確認します。古い編集世代や削除済みの候補は検索から即時除外します。Vectorizeには本文・メモの平文をmetadataとして保存せず、埋め込みとプロジェクトIDだけを保存します。退会・プロジェクト削除時も外部削除要求を保持し、削除失敗はCronから再試行します。

索引の進行確認（管理者用のD1 SQL）：

```sql
SELECT SUM(current=1 AND ready=1) AS indexed,
       SUM(current=1 AND ready=0) AS pending,
       SUM(current=0) AS cleanup_pending
FROM stock_search_entries;
```

外部障害時は要求を残して再試行します。通常は約1分、利用枠待ちは約1時間後に再確認します。書き込みは送信前に`write_pending=1`を保存し、タイムアウト・中断後は同じ索引IDを再利用せず新しい要求に切り替えます。未確定の旧書き込みは、削除APIが成功しても追跡情報を残し、約1時間ごとに削除を続けます。遅れて完了を観測できた場合は、その後の削除が成功してから要求を除去します。Worker終了などで完了を観測できない場合、この最小限のID記録と削除再試行が残ります。`cleanup_pending`にはこの保留分も含みます。

インデックスを作り直す場合や管理者が即座に再試行する場合は、接続設定を確認したうえで次を実行します。

```sql
UPDATE stock_search_entries SET ready=0,next_attempt_at=strftime('%Y-%m-%dT%H:%M:%fZ','now')
WHERE current=1;
```

索引設定を無効にすると意味検索は利用できなくなります。外部削除の後処理には`SEARCH_INDEX` bindingが必要なので、未完了の削除がある間はbindingとCronを維持してください。検索語・メモ・ベクトル・外部例外の詳細はログへ出しません。

参考：[Vectorize client API](https://developers.cloudflare.com/vectorize/reference/client-api/)、[metadata filtering](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/)、[BGE-M3](https://developers.cloudflare.com/workers-ai/models/bge-m3/)。

### 互換性と今回の改善範囲

- MCPで従来の一覧項目が必要なクライアントは `detail: "full"` を指定します。`get_stock` は従来の詳細を返し、本文は `include_content: true` の場合だけ取得します。
- Web画面が使うHTTP API `GET /stocks` の既定値は従来どおり24件・新しい順・fullです。HTTP APIでも上記の一覧オプションを指定できます。
- `content` のJSONテキストと `structuredContent` は同じデータを保持します。構造化結果を読めないクライアントのための互換性を残し、まず返す項目と件数を減らします。
- full／詳細の既存フィールド名（`summary.keyPoints`、`source_type`、`pageSize`など）と `is_favorite` の `0 / 1` は維持します。型・命名の一括変更は既存クライアントへの破壊的変更になるため、今回は行いません。
- 本文検索にはR2に保存した本文の検索索引と一致箇所の返却設計が必要です。全本文を取得して走査する方式は追加せず、検索対象をツール定義にも明示します。
- ストックの `status` は記事取得・要約の状態です。問いとメモリは別の非同期処理なので、記事が `ready` でもすべての処理が完了したことを意味しません。問いは `list_questions`／`get_question` で確認できます。複数記事をまとめるメモリ更新を1ストックの完了状態として返す設計は、今回の一覧改善から分けます。

### 本番の準備

このリポジトリの本番環境にはOAuth用KVを設定しています。別の環境へ構築する場合は、次の手順で専用のKVを作成・設定してください。

1. OAuth用KVを作成します。

   ```sh
   pnpm exec wrangler kv namespace create OAUTH_KV --env production
   ```

2. 返されたIDを本番ビルドの環境変数 `OAUTH_KV_ID` に設定します。GitHub Actionsでは `production` EnvironmentのSecretsに登録します。`wrangler.jsonc` のKV IDはゼロのプレースホルダーのままにします。ローカル開発もこのプレースホルダーでローカルKVを使えます。
3. `APP_URL` を末尾スラッシュなしの本番HTTPSオリジンに合わせます。既存GoogleログインのClient ID・Secretとコールバック設定を使います。MCPクライアントにGoogleのトークンやセッションCookieを渡す必要はありません。
4. [本番設定の手順](#cloudflareの本番設定)に従い、環境変数を指定して本番ビルド後にマイグレーション・デプロイを実行します。MCPには `0016_independent_questions.sql` 以降が必要です。0016は既存の問い・お気に入り・プ譜・局面を保全し、移行後も旧Workerのストック指定による問い生成を受け付けます。

`global_fetch_strictly_public` と、静的配信よりWorkerを先に処理する `/mcp`・`/oauth/*`・`/.well-known/*` のルートは設定済みです。通常の本番反映はmainの更新を受けたGitHub ActionsがDB移行とWorker公開を順に実行します。

`POST /oauth/register` の事前登録は、Cloudflareの `OAUTH_REGISTRATION_RATE_LIMITER` で接続元IPごとに1分10回までに制限します。超過時は登録を保存せず `429` と `Retry-After: 60` を返します。Cloudflareが付ける `CF-Connecting-IP` のハッシュをキーにし、`X-Forwarded-For` などの自己申告は使いません。IPがないローカル要求は共通の枠を使います。バインディングが未設定・障害の場合は `503` にし、制限を迂回して登録を続けません。レート制限はCloudflareの拠点ごとの近似制限で、全拠点を厳密に合算するものではありません。

修正後に作成される動的登録の保存期限は90日です。有効期間の半分を過ぎた登録は、トークンの取得・更新に成功するとSDKが90日へ延長します。変更前の期限なしレコードには遡及適用しません。ログイン・同意・トークン更新・MCPの利用には登録回数制限を適用しません。`wrangler.jsonc` の通常環境と本番環境にレート制限のバインディングを設定しており、追加のSecretやDB移行は不要です。

### ChatGPTから接続

利用アカウント・ワークスペースでカスタムMCPが許可されていることを確認してください。[ChatGPT Plugins](https://chatgpt.com/plugins) で「Add custom MCP server」を選び、接続URL `https://実際のホスト/mcp` を登録してOAuthで接続します。Googleログイン後、Pufu Lensの認可画面で接続元・送信先・操作権限・対象プロジェクトを確認して許可します。接続したプラグインを会話で選択して利用します。[OpenAI公式の接続手順](https://developers.openai.com/plugins/deploy/connect-chatgpt)

認可画面では `projects:read`、`stocks:read`、`stocks:write`、`questions:read`、`questions:write` を個別に選択でき、1プロジェクトに限定することもできます。アクセストークンは1時間です。「連携を継続するためにトークンを更新」を許可した場合だけ30日有効の更新トークンを発行します。CIMD・DCR・PKCE（S256）・認可サーバー/保護リソースのメタデータ公開に対応しています。アプリの「MCP連携」から解除すると、その連携のアクセストークンと更新トークンを失効します。既存ショートカット用トークンの権限は拡大しません。

### ローカル検証

`pnpm run dev` を起動し、別ターミナルで `pnpm run test:smoke:mcp` を実行します。ローカルデモに対してOAuth・ツール一覧・プ譜の取得・再送・独立した問い・更新・失効を検証し、検証用プロジェクトと連携を削除します。Workers AIを使わずに検証する場合は `WORKERS_AI_ENABLED=false pnpm run dev` としてください。

## API

`/api/v1` は認証必須です。WebのCookie認証での変更操作には、`APP_URL` と一致する `Origin` が必要です。Bearer認証ではCookieに依存しません。

| メソッド・パス                    | 用途                                         | Bearer |
| --------------------------------- | -------------------------------------------- | ------ |
| `GET /projects`                   | 自分のプロジェクト一覧                       | 可     |
| `POST /stocks`                    | URL／テキストの保存受付                      | 可     |
| `GET /me`                         | ログイン中のユーザー                         | —      |
| `PATCH /me`                       | 自分の名前・自己紹介の更新                   | —      |
| `DELETE /me`                      | 本人の退会と登録データの削除                 | —      |
| `POST /logout`                    | セッション終了                               | —      |
| `POST /projects`                  | プロジェクト作成                             | —      |
| `PATCH・DELETE /projects/:id`     | プロジェクト編集・削除                       | —      |
| `GET /stocks`                     | 検索・状態・プロジェクトで絞り込む一覧       | —      |
| `GET /stocks/:id`                 | 保存した記事の詳細                           | —      |

`GET /stocks` は `project_id`、`q`、`source`（`all / web / user`）、`favorite`（`true` のときお気に入りのみ）、`page` を受け付け、既定は24件ずつ返します。`limit`（1〜24）、`sort_by=created_at`、`order=asc / desc`、`detail=compact / full` も指定でき、HTTP APIの既定は `full`・新しい順です。`source=web` は `source_type=url`、`source=user` は `source_type=text` に対応します。APIでは `status`（`all / ready / processing / failed`）も併用できます。`GET /memory` は `project_id` を省略するとユーザーメモリです。

ストックも日付横のスターでお気に入りを登録・解除でき、選択中は黄色で表示します。記事の詳細画面からも変更でき、一覧の「お気に入り」で絞り込めます。`PATCH /stocks/:id/favorite` に `{ "is_favorite": true }` または `false` を送り、保存した `id` と `is_favorite`（`0 / 1`）を返します。本人のWebセッションだけが変更でき、再読み込み・要約の再試行・保存先の移動でも保持します。同じ記事を別のプロジェクトに保存した場合や、記事に紐づく問いのお気に入りとは独立しています。

詳細画面のタイトル右の鉛筆から編集し、「保存」で確定、「キャンセル」またはEscapeで取り消せます。`PATCH /stocks/:id/title` は `{ "title": "新しいタイトル" }` を受け付け、前後の空白を除いた1〜200文字のタイトルと `id` を返します。本人のWebセッションだけが変更でき、一覧・詳細・問いの参照タイトル・MCP一覧・公開ページと検索に反映します。編集内容はストックごとに保持し、記事の再取得や別プロジェクトの同じ記事には影響しません。Worker更新前に `0021_stock_titles.sql` を適用してください。

`POST /stocks` のURL保存は `{ "type": "url", "project_id": "保存先ID", "url": "https://...", "note": "任意のメモ" }` です。`type` を省略した従来のショートカットのリクエストもURLとして受け付けます。テキスト保存は次の形式で、URLは送信しません。

URL・テキストとも `project_id` は省略できます。指定時は本人の指定プロジェクトだけに保存し、限定トークンと異なる指定は `403`、存在しない・他ユーザーの指定先は `404` になります。省略時は限定トークンの限定先、限定なしトークン・セッション認証では本人の現在の全プロジェクトに保存します。保存先が0件なら `400` を返します。空文字や `null` は無効です。全件保存は単一トランザクションで行い、利用上限は新規ストック件数ごとに数えます。残り枠が不足する場合は全体を取り消して `429` を返します。既存ストックのメモは保持し、記事本体と取得・要約処理は共有します。

```json
{
  "type": "text",
  "project_id": "保存先ID",
  "title": "任意のタイトル",
  "text": "ストックする本文",
  "note": "任意のメモ"
}
```

本文の前後の空白を除き、空白のみの入力を拒否します。同じタイトル・本文はユーザー内で記事本体を再利用し、同じプロジェクトへの二重保存を防ぎます。テキストでもBearerの保存先制限と `Idempotency-Key` を適用します。保存APIの送信上限は160KiB、本文は20,000文字です。一覧・詳細は `source_type`（`url / text`）を返し、テキストの `source_url` と `domain` は空文字です。

## 非同期処理とデータ整合性

- URL／テキスト受付と処理要求、メモリ更新要求を同一D1トランザクションで保存します。テキストの入力本文はD1へ保持し、WorkflowがR2へ保存して要約します。テキストでは外部URLの取得を行いません。Workflowの起動に失敗してもCronから再開できます。
- 記事の本文取得、R2保存、AI呼び出し、要約確定を工程に分けます。本文取得・R2保存・要約確定などの工程の再試行は2回までです。AIステップの形式エラーは初回を含め最大10試行、5秒固定間隔です。起動・枠待ちの試行数と待機期限は、[利用量制限](#利用量制限)に記載しています。
- 長い記事は本文を分割して要約し、全分割の要約を統合します。メモリは通常、現在のメモリと未反映の記事要約だけで更新します。全件更新が必要な場合は記事要約の全件を25件ずつ読み、中間要約を統合します。最近の記事だけに切り詰める実装ではありません。
- 前後の空白を除いた本文がUnicodeコードポイントで120文字未満なら、要約用AIを呼び出さず、原文をoverviewと1つのkeyPointsへ保存します。topicsは空配列、`shortSource: true`、modelは`source-extract`です。通常のAI要約でも、本文にない情報や情報不足の指摘を補わず、要点は1個からとし、文字数・個数を水増ししません。
- 短文の詳細では原文表示の説明と、メモ未入力時の「ひとことメモを残す」を表示します。メモの追加・変更・削除時には同じDB batchでAIの問いの世代を進めて再生成し、メモリも更新します。同じメモの再送では問いを再生成しません。生成中にメモが変わった場合は古い問いを確定しません。利用枠がないときもメモは保存し、生成は既存の待機・再試行制限に従います。ユーザーが書いた問いと削除済みAIの問いは変えません。
- メモ本文は直接公開しませんが、メモをもとに作った問いはプロジェクト公開時に公開対象となることを、メモの入力欄とマニュアルに明記します。AIにはメモや個人情報をそのまま引用しないよう指示し、デモの定型問いにもメモ本文を埋め込みません。AIの問いの再生成中・失敗時も、最後に確定した問いと既存プ譜は公開ページで閲覧できます。初回生成の未完成の問いは公開しません。
- 記事の要約は同じ記事を保存したプロジェクト間で共通のため、私的なメモを混ぜて再要約しません。メモを含めた文脈は保存先ごとの問いとメモリの入力へ渡します。新しい短文判定は今回以降の要約処理で適用し、保存済みの要約や本番メモリの一括書き換えは行いません。
- 要約が確定する際、トランザクション内で最新の保存先プロジェクトを読みます。要約中に別プロジェクトへ保存しても更新を取りこぼしません。
- メモリ生成前後で入力の更新番号を確認します。古い生成結果は保存せず、最新の更新要求を処理します。
- 保存した記事の主張をユーザー本人の信念として扱いません。知識には根拠の記事IDを保存し、入力に存在しないIDを除外します。
- 記事削除・移動・メモ更新・プロジェクト説明の変更でも関連メモリを再生成します。最後の保存を削除した記事はDBから除去し、非公開本文の削除要求を残します。

記事要約のJSONは `{ overview, keyPoints, topics, shortSource? }`、メモリは `{ interests, knowledge: [{ text, articleIds }], questions }` です。`shortSource` は本文からサーバーが判定し、AI出力には要求しません。AIの応答はZodで検証します。

## 記事取得の範囲

YouTubeの詳細画面の「動画」タブで埋め込みプレーヤーを表示します。タイトルは手動で変更できます。チャンネル・再生リストなどの動画を特定できないURLは元のページへのリンクを残します。埋め込みが禁止された動画などは「YouTubeで開く」からご覧ください。

YouTubeの動画内容は記録対象外です。`youtube.com`・`youtu.be`・`youtube-nocookie.com` とそのサブドメインのURLを追加すると、初期タイトル「YouTube」でURL・メモを保存します。記事取得・動画情報のAI処理の対象外として内部状態は `failed` としますが、画面では取得失敗を表示しません。動画・チャンネル・再生リストなどのパスにかかわらず外部取得しません。本文補完は保存せず、記事処理・自動の問い生成のジョブを作成しません。再試行APIは記録不可の案内を返し、処理待ちだったYouTube URLもWorkflowで取得・AI処理前に停止します。通常記事からYouTubeへのリダイレクトも接続前に拒否します。

利用者のメモがある場合だけ、YouTubeストックをメモリ更新の対象にします。空白だけのメモは対象外です。動画の旧タイトル・旧要約・本文・字幕を参照せず、入力タイトルは「YouTube」、入力内容は利用者が記入したメモだけとします。同じ動画を複数のプロジェクトに保存した場合は、対象の保存先に記入されたメモだけを集約し、ユーザーメモリではプロジェクトの設定も適用します。メモの追加・編集・削除・保存先の変更に合わせて更新し、メモのないURLの保存・変更・削除や、動画の表示・再生は更新を起動しません。メモのないYouTubeはメモリの取得待ち件数にも含めません。除外した記事があっても後続の更新対象を読み込めるよう、ページの終端は除外前の件数で判定します。

YouTube Data API連携・APIキー・動画情報専用の要約処理・サーバーによるサムネイル取得はありません。動画URLは通常・短縮・Shorts・ライブ・埋め込みのURLから11文字の動画IDを読み取り、詳細画面で `https://www.youtube-nocookie.com/embed/{videoId}` の固定ホストにiframeを表示します。任意の追加クエリは引き継がず、自動再生やJavaScriptのプレーヤーAPIは使いません。HTTPリファラーが必要なため `referrerPolicy="strict-origin-when-cross-origin"` を指定し、最小200pxの高さを確保します。一覧ではiframeを読み込まず、検証済みの動画IDから固定ホスト `https://i.ytimg.com/vi/{videoId}/mqdefault.jpg` の静止画像だけを表示します。画像は320×180で、`loading="lazy"`・`decoding="async"`・`referrerPolicy="no-referrer"` を指定します。画像やタイトルを押すと詳細を開き、その時点でプレーヤーを読み込みます。画像の取得失敗や動画を特定できないURLでも、詳細への導線を残します。公開ストックの一覧・詳細も同じ表示です。動画を特定できないURLは外部リンクとして扱います。ブラウザからYouTubeへの通信はプライバシーポリシーに記載します。`0019_youtube_metadata.sql` は適用済みDBとの移行履歴として残しますが、`youtube_json` 列を実行時の処理で読み書きせず、ストックAPIから `youtube` メタデータを返しません。過去に取得した同じURLを再保存・重複再送した場合も、既存記事を記録不可の状態と案内に切り替えます。過去の本文・要約は削除せず保持し、その本文や失敗状態の要約をストックAPIから返しません。保存済みデータの一括削除は行いません。

YouTubeのプレーヤーはプライバシー強化モードの `youtube-nocookie.com` を使いますが、サムネイルやプレーヤーの表示・再生時にはブラウザからYouTubeへ通信します。[公式の埋め込み案内](https://support.google.com/youtube/answer/171780?hl=ja)も参照してください。

対象は、ログインせず読める公開HTML・テキスト・PDF記事です。HTTP(S)以外、内部・予約アドレス、認証情報入りURL、標準外ポートを拒否します。DNSのA・AAAAの全回答と各リダイレクト先を検査し、取得時にアプリのCookieやBearerトークンを送りません。

通常はHTMLを取得してReadabilityで本文を抽出します。本文が不足する場合はBrowser Runを使用します。ブラウザのHTTP要求も検証付き取得を通し、POST、ダウンロード、Service Worker、WebSocketを許可しません。ログイン・ペイウォール・アクセス制限の回避は行いません。ページ上の任意の対話操作には対応していません。

`application/pdf` と `application/octet-stream` の応答は、本文ストリームを `PDF_PARSER` サービスバインディングで専用Worker `pufu-lens-pdf-parser` へ渡し、unpdf（Mozilla PDF.js）で解析します。本体WorkerはPDF.jsをロードせず、PDF全体をバッファしません。各ページの文字情報を順番に読み取り、既存の本文保存・要約・問い・メモリ更新へ渡します。タイトルはPDFメタデータ、本文の先頭行、ドメインの順で補います。PDF内のJavaScriptを実行せず、外部のフォント等を取得しません。日本語などの組み込みCMapは、PDF.jsと同じバージョンのpdfjs-distからライセンスとともに解析Workerのバンドルへ同梱します。CMap以外の外部資源要求や不正なファイル名は拒否します。解析後や失敗時には解析資源を破棄します。文字情報のないスキャンPDF・パスワード保護・破損したPDFは理由と本文補完の案内を表示します。OCRやパスワード解除は行いません。HTMLページがリンクするPDFの自動巡回は行わず、PDFそのものの公開URLを保存してください。過去に失敗したPDFは、詳細から取得を再試行できます。

PDF専用Workerは公開URL・preview URLを持たず、DB・R2・AI・OAuthのバインディングやSecretを持ちません。`secrets.required` を空配列にし、ローカル開発でも本体用 `.dev.vars` のSecretを注入しません。メモリはCloudflareの128MB/isolate制限、CPUはWorkers Paidの5,000ms上限を利用します。同じisolateでは一度に一つのPDFだけを受け付け、混雑時は503を返してWorkflowの既存リトライに戻します。資源超過・サービス未設定・異常応答・待機超過時には、本体内での解析へフォールバックせず、URLとエラーを残して本文補完を案内します。20秒の期限やサービス呼び出しの中断では、取得元ストリームとPDF解析を中止して受付枠を解放します。専用Workerの `enable_request_signal` を有効にし、本体からの中断通知を受け取ります。メモリ制限の本番での適用挙動はローカルMiniflareの成功だけでは保証できません。

HTML・テキストの取得上限は2MB、PDFは10MB・100ページ、PDF解析の待機時間は20秒、抽出本文は共通で12万文字です。本文の文字情報はストリームで読み、12万文字超で早期停止しますが、これをPDF内の圧縮データの展開量制限として扱いません。Content-Lengthの有無にかかわらず取得中の実バイト数も検査します。上限超過や取得失敗時はURLとエラーを保持します。プロジェクトは50件、保存はユーザーごとに直近24時間200件までに制限しています。本文・AI処理の時間と実記事の要約品質は、利用する記事で確認してください。

## 利用量制限

`0013_usage_limits.sql` と `0014_job_retry_limits.sql` をWorker更新前に順番に適用します。`0014` は既存ジョブを保持したまま起動試行の記録用テーブルを追加します。既存ジョブの試行数は次の起動から数えます。直近24時間の新規保存はユーザーごとに200件です。D1トリガーで保存と履歴を同時に確定し、削除しても履歴は減らず、URL/テキスト・Cookie/Bearerで枠は分離しません。別プロジェクトへの新規保存も同じユーザー枠で計上します。重複保存とIdempotency-Keyの再送は二重計上しません。移行前に削除済みの保存履歴は復元できないため、初期履歴には現存するストックを引き継ぎます。

AI処理はD1の利用枠を原子的に確保してからWorkflowを起動します。値は正の整数の環境変数で調整できます（未設定・不正値は下記の既定値）。ローカルは `.dev.vars`、本番は `wrangler.jsonc` の対象環境の `vars` に設定します。

| 環境変数                  | 既定値 | 集計対象（ユーザー単位）                                             |
| ------------------------- | -----: | -------------------------------------------------------------------- |
| `AI_PUFU_DAILY_LIMIT`     |     20 | プ譜生成・明示的な再試行／直近24時間                                 |
| `AI_MEMORY_DAILY_LIMIT`   |     48 | ユーザー/プロジェクトの手動・自動メモリ更新の合計／直近24時間        |
| `AI_ARTICLE_DAILY_LIMIT`  |    200 | 記事の要約ジョブ・再試行／直近24時間                                 |
| `AI_QUESTION_DAILY_LIMIT` |    200 | AIの問い生成・再試行／直近24時間                                     |
| `AI_CONCURRENT_JOBS`      |      5 | 受付済み・未完了のAIジョブ数（待機・実行を含む）                     |
| `AI_CALL_DAILY_LIMIT`     |    500 | 分割要約・統合・形式エラーの再試行を含む実AI呼び出し試行／直近24時間 |
| `AI_CONCURRENT_CALLS`     |      5 | 実AI呼び出しの同時実行数                                             |

小規模運用の暫定値として、プ譜は20件、メモリはユーザーとプロジェクトの更新を合わせて48件としています。分割や再試行による増幅は別の500回枠で抑えます。これはユーザーごとの呼び出し回数制限であり、アカウント全体の金額上限ではありません。

手動APIは上限時にジョブを起動せず `429`、`Retry-After`（秒）、JSONの `error` と `retry_at`（UTC ISO日時）を返し、画面に理由・再試行目安を表示します。同時数のみの上限は60秒後を目安に返しますが、実行中の完了や新たな利用状況により再度429となることがあります。`POST /memory/rebuild` は `{ project_id?, request_id?, mode? }` を受け付けます。`mode` は `incremental` または `full` で、省略時は従来どおり `full` です。同じrequest_idまたはIdempotency-Keyは再送しても同じ受付を返し、対象または更新方法が異なる再送は `409` です。プロジェクト指定時はそのプロジェクトのみ、省略時はユーザー全体のみの1ジョブ分を確保します。IDなしは新規要求です。

自動メモリ更新は上限時も `pending` として保持し、未開始の古い世代を最新世代へ集約します。毎分のCronが枠の回復後に処理を再開します。枠の確認・Workflowの起動・回復後の再起動は初回を含め同じジョブにつき10試行までです。枠待ちと起動失敗時は原則60秒後に再確認します。待機中のジョブが受付から30分、または10試行に達すると、理由を表示して失敗に移します。Workflowの受付後に未開始のまま起動を待つジョブにも30分の期限を適用します。再試行目安が翌日でも30分で停止し、失敗済みのジョブは自動再開しません。実行中の処理は受付からの経過時間だけでは中断しません。ローカルでCronを発火させない場合は自動再開・期限超過の反映が遅れるため、Workerのscheduledイベントを実行するか次の画面/API操作を待ってください。

同じジョブの利用枠は再計上せず、完了済みのAIステップはD1に保存した結果を再利用します。応答受領後の形式エラーは初回を含め同じステップにつき最大10試行で、再試行の間隔は5秒固定です。すべて実呼び出し枠を消費します。通信断など生成の成否が不明な場合は同じステップの自動再発行を禁止します。結果保存前に中断した記録は10分経過後、CronがWorkflowの終端状態を確認して失敗に移し、枠を解放します。Workflow状態を取得できない間は安全側で枠を保持します。失敗後の新しい再試行は再び利用枠を消費します。API受付時の予約は失敗でも返却しません。

保存履歴・実呼び出し履歴は30日で整理し、実行中の呼び出しと必要な再実行結果は保持します。生成結果・履歴にはユーザーの資料を含むためD1の既存のアクセス制御下で管理します。

`short-uuid@4.2.2` のAPIを保ち、依存する `uuid` だけをCommonJS対応の修正版 `11.1.1` 以上へoverrideしています。[GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq) の修正を取り込み、エディター `0.9.19` のID生成・編集データ形式を維持します。

## ローカル開発

Node.js 22.22.3以降の22系、または24.11以降（推奨24系）とpnpm 11.28.6を使用します。開発・CI・監査・デプロイで使うpnpmのバージョンは、`package.json` の `packageManager` で一元的に固定しています。Cloudflare・Googleの認証情報なしでもローカルで動作確認できます。

設定値の例は [.dev.vars.example](../.dev.vars.example) にあります。APIキーなどの秘密情報は `.dev.vars` やサービス側のSecretsで管理し、Gitへ追加しないでください。

Corepackを利用する場合は、初回に `corepack enable` を実行してpnpmを有効にしてください。

```sh
pnpm install --frozen-lockfile
pnpm run setup
pnpm run dev
```

<http://localhost:5173/> を開き、「ローカルデモを開く」を選択してください。`setup` は既存の `.dev.vars` を上書きせず、ローカルD1へマイグレーションを適用します。

デモには公開資料に基づくサンプル記事が4件含まれます。新しく保存した記事は、URLから取得した本文または入力したテキストの**文章の抜粋**を表示します。ローカルデモのメモリもトピックの集計と要点の抜粋です。AIによる要約と区別する表示を付けています。D1・R2・WorkflowsはローカルのCloudflareランタイムで動作します。

ローカルデモは `LOCAL_DEMO_ENABLED=true` かつ `APP_URL` がループバックホストの場合に有効です。ログイン先は同じプロトコル・ポートのループバックホスト、または明示したLAN用アドレスに限ります。本番設定では無効です。`.dev.vars`、`.wrangler`、`dist` はGit管理対象外です。

同じWi-Fiのスマホで試す場合は、MacのプライベートIPv4アドレスを確認し、`.dev.vars` に `LOCAL_DEMO_LAN_ORIGIN=http://MacのIPv4アドレス:5173` を追加して `pnpm run dev:lan` で起動します。`APP_URL` は `http://localhost:5173` のままにします。スマホからそのLAN用URLを開き、「ローカルデモを開く」を選択してください。Macの画面と同じデモデータを利用できます。IPv4アドレスが変わった場合は設定を更新して再起動します。

## ローカルでWorkers AIを使う

Cloudflareにログインしたうえで、`.dev.vars` に次を設定し、開発サーバーを再起動します。

```dotenv
LOCAL_DEMO_ENABLED=true
WORKERS_AI_ENABLED=true
AI_MODEL=@cf/qwen/qwen3-30b-a3b-fp8
```

```sh
pnpm exec wrangler login
pnpm run dev:lan
```

すでにWranglerでログイン済みなら、再ログインは不要です。`WORKERS_AI_ENABLED` は起動時のプロセス環境変数でも指定でき、`.dev.vars` より優先します。Cloudflare環境を指定している場合は `.dev.vars.<環境名>` を優先して読みます。モデルは `AI_MODEL` で変更できます。要約・問い・メモリでは保存形式の制約をJSON Schemaとして渡すため、[JSON Mode](https://developers.cloudflare.com/workers-ai/features/json-mode/) に対応したモデルを指定してください。

開発時だけ公式のリモートAIバインディングを追加し、D1・R2・Workflowsは引き続きローカルで動かします。AIを使うと、ストックの本文・要約・関連するメモリなどがCloudflareへ送信され、利用量に応じてWorkers AIの料金が発生します。APIトークンをアプリの入力欄や `VITE_` 付き変数に設定する必要はありません。[Cloudflareのローカル開発の説明](https://developers.cloudflare.com/workers/local-development/)

画面上部がWorkers AI利用中の案内に変わり、`GET /api/config` は `aiEnabled: true` と `aiModel` を返します。新しいストックを追加すると、要約・問い・プロジェクトとユーザーのメモリをAIで生成し、問いからプ譜も生成できます。生成結果の `model` で実際に使用したモデルを確認できます。既存のサンプル記事・問い・プ譜は自動的には再生成しません。AIを使わないデモに戻す場合は `WORKERS_AI_ENABLED=false` にして再起動してください。

Google Cloud ConsoleでOAuthクライアントを「ウェブアプリケーション」として作成し、以下を設定します。

| 設定            | ローカル                                         | 本番                                 |
| --------------- | ------------------------------------------------ | ------------------------------------ |
| アプリのURL     | `http://localhost:5173`                          | `APP_URL` に指定したHTTPSオリジン    |
| リダイレクトURI | `http://localhost:5173/api/auth/google/callback` | `<APP_URL>/api/auth/google/callback` |

スコープは `openid` のみです。署名・issuer・audience・期限・nonceを検証したGoogleの `sub` とアプリのユーザーIDを関連付けます。メールアドレス・名前・プロフィール画像を要求せず、以前の許可などで認証応答に含まれても保存・利用しません。Googleのアクセストークンやリフレッシュトークンは保存しません。想定外のAPI・MCPエラーは固定コードだけをログに記録し、例外やリクエスト内容を出力しません。

OAuth同意画面の「アプリのドメイン」には、次のURLを登録できます。ポリシーページはログイン不要で、トップページ・アプリ内メニュー・マニュアルから参照できます。

| 項目                           | 本番URL             |
| ------------------------------ | ------------------- |
| アプリケーションのホームページ | `<APP_URL>`         |
| プライバシーポリシー           | `<APP_URL>/privacy` |
| 利用規約                       | `<APP_URL>/terms`   |

本文の編集元は `src/LegalPage.tsx` です。ビルド時に同じコンポーネントから `dist/client/privacy/index.html` と `dist/client/terms/index.html` を生成するため、JavaScriptを実行しない取得でも本文を読めます。トップの初期HTMLにもサービス説明と両ページへのリンクを含めます。開発サーバーでは従来どおりReactで表示します。

Googleから取得する識別子の用途・保存・削除はプライバシーポリシーの「Googleユーザーデータの取り扱い」に記載しています。自己紹介はユーザーメモリ生成時にWorkers AIへ送信します。Googleアカウントの識別子とニックネームはユーザーメモリ生成の入力に使用しません。

運営者表記は「Pufu Lens 運営者」、問い合わせ先はGoogleログイン同意画面のユーザーサポート窓口としています。Google Cloud側のアプリ名・サポートメール・ドメイン設定を実際の運用と一致させてください。

### Googleのブランド確認・プライバシーポリシー審査

`pufu-lens.dev` を使う本番環境では、Google Auth Platformの「ブランディング」で次の値を登録します。URL欄に引用符、日本語の説明、Markdownのリンク記法を含めないでください。

| 項目                           | 設定値                                        |
| ------------------------------ | --------------------------------------------- |
| アプリケーションのホームページ | `https://pufu-lens.dev`                       |
| プライバシーポリシー           | `https://pufu-lens.dev/privacy`               |
| 利用規約                       | `https://pufu-lens.dev/terms`                 |
| 承認済みドメイン               | `pufu-lens.dev`（プロトコルやパスは付けない） |

ドメインがHTTP 200で応答することと、Googleに所有権が確認されていることは別です。「ドメインが無効」と指摘された場合は、次を確認します。

1. [Google Search Console](https://search.google.com/search-console)で `pufu-lens.dev` のドメインプロパティを追加し、指定されたDNS TXTレコードで所有権を確認します。既存の確認済みプロパティがあれば再利用します。
2. 所有権を確認したGoogleアカウントが、対象Google Cloudプロジェクトのオーナーまたは編集者であることを確認します。承認済みドメイン・ホームページ・ポリシー・規約・OAuthクライアントのリダイレクトURIを同じ本番ドメインに揃えます。
3. 修正版の本番反映後、ログアウト状態でトップ・ポリシー・規約を開き、リンクと本文を確認します。JavaScriptを無効にしても本文が読めること、ログイン・アクセス制限・ボット対策の認証画面で遮られていないことも確認します。
4. 「コンテンツ不足」が解消しない場合は、`curl -L https://pufu-lens.dev/privacy` のHTMLにポリシー本文が含まれるかを確認します。Cloudflare側のチャレンジなどが返る場合は、配信側の設定も調査します。
5. Google Auth Platformで審査を再実行します。審査チームからメールで修正を依頼された場合は、その案内に従って更新完了を返信します。

DNS・Google Cloud設定と審査状態はコード変更だけでは確認・更新できません。本番反映、所有権確認、再申請をそれぞれ確認してください。[Googleのプライバシーポリシー要件](https://support.google.com/cloud/answer/13806988?hl=en)、[ドメイン所有権と公開ホームページの要件](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance)を参照してください。

ローカルでは `.dev.vars` の `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET` を設定して開発サーバーを再起動します。本番ではWorkerのSecretとして登録します。認証ライブラリはWorkersに対応した `openid-client` を使用しています。

本番用のClient IDとClient Secretは、Git管理対象外の `.dev.vars.production` に記入できます。Google Cloud Consoleでは「承認済みのリダイレクトURI」に上記の本番URIを登録してください。Google側はURIの完全一致を要求します。[GoogleのOpenID Connect仕様](https://developers.google.com/identity/openid-connect/openid-connect#authenticatingtheuser)

## Cloudflareの本番設定

本番URLはビルド時の環境変数 `APP_URL` で指定します。以下は環境を新しく構築する場合の手順です。既存環境ではリソースを重複作成せず、設定と未適用マイグレーションを確認してください。

1. Cloudflareアカウントへログインし、D1・非公開R2バケット・OAuth用KVを作成します。

   ```sh
   pnpm exec wrangler login
   pnpm exec wrangler d1 create stock-db
   pnpm exec wrangler r2 bucket create pufu-lens-stock-content
   pnpm exec wrangler kv namespace create OAUTH_KV --env production
   ```

2. `wrangler.jsonc` の `env.production` を編集します。
   - D1・KVのIDはゼロのプレースホルダーのままにします。環境変数 `D1_DATABASE_ID`、`OAUTH_KV_ID` に実際のIDを設定すると、本番ビルドで生成設定へ注入されます。
   - `vars.APP_URL` の `https://app.example.invalid` はダミー値のままにします。本番ビルド時にプロセス環境変数 `APP_URL` から生成設定へ注入します。
   - 独自ドメインを使う場合はCloudflareのWorkerのルート／カスタムドメインを設定します。
   - `LOCAL_DEMO_ENABLED` は `false` のままにします。
   - R2は公開アクセスを有効にしません。

3. GoogleのSecretを登録します。値は対話入力してください。

   ```sh
   pnpm exec wrangler secret put GOOGLE_CLIENT_ID --env production
   pnpm exec wrangler secret put GOOGLE_CLIENT_SECRET --env production
   ```

4. 環境変数 `APP_URL` に実際のHTTPSオリジンを設定して、本番ビルドを先に検証し、マイグレーション適用とデプロイを実行します。

   ```sh
   export APP_URL="https://your-app.your-account.workers.dev" # 実際のURLに置き換える
   export D1_DATABASE_ID="実際のD1データベースUUID"
   export OAUTH_KV_ID="実際のOAuth KVの32桁ID"
   pnpm run build:production
   pnpm run db:migrate:production
   pnpm run deploy:workers
   ```

`APP_URL` はパス・クエリ・フラグメント・認証情報を含まないHTTPSオリジンにします。末尾の `/` は除去されます。未設定、不正なURL、localhost、`.invalid` のダミー値では本番ビルドを停止します。`.dev.vars.production` の値は本番ビルドへ自動注入されません。`pnpm run deploy` も同じ環境変数が必要です。通常の `pnpm run build` とローカル開発には不要です。D1・KVも未設定・不正形式・ゼロのIDでは本番ビルドを停止します。生成された `dist` はGit管理対象外です。`db:migrate:production` は本番ビルドが生成した `dist/pufu_lens_stock/wrangler.json` を明示的に使うため、先に本番ビルドを成功させてください。`deploy:workers` は `dist/pufu_lens_pdf_parser/wrangler.json` のPDF専用Workerを先に配置し、成功後に `dist/pufu_lens_stock/wrangler.json` の本体を配置します。PDF専用Workerは `wrangler.pdf.jsonc`、本体の接続先は `wrangler.jsonc` の `services` で定義します。ローカル開発もViteのauxiliary Workerとして同じ構成を使用し、別プロセスの起動操作は不要です。Workers Observability（logs / traces / issues）は両 `wrangler` 設定の `observability` で有効化しており、ダッシュボードだけの有効化は次のデプロイで上書きされます。

この設定はアプリのURL設定であり、Cloudflareのドメイン割り当てやGoogle側のOAuth設定は変更しません。URLは秘密情報として扱いません。Git履歴やActionsのログなどから既存URLが見える場合があります。

Workers AI、Browser Run、Workflowsの利用量に応じた費用が発生します。標準のモデルは `@cf/qwen/qwen3-30b-a3b-fp8` で、`AI_MODEL` から変更できます。モデルは、[仕様に示すJSON形式](#非同期処理とデータ整合性)を返せるテキスト生成モデルを指定してください。

`env.production` にAIとブラウザのバインディング、2つのWorkflows、毎分のCronを定義しています。Cronは未起動の処理要求を再送し、中断された処理の状態を回復します。本文削除の失敗は自動で再試行します。

環境構築後は、公開画面・Googleログイン・デモ無効化・未認証APIの拒否に加え、ログイン後の保存・Workers AIによる生成・Browser Runによる本文取得を確認してください。この文書は現在の本番環境の検証結果を保証するものではありません。

### GitHub Actionsによる自動デプロイ

[CI](../.github/workflows/ci.yml) は、`main` 向けPRの作成・更新時に検証のみを実行します。[Cloudflare Deploy](../.github/workflows/cloudflare-deploy.yml) は、PRのマージなどで `main` が更新されたときだけ起動し、検証成功後に既存の本番環境へデプロイします。PRの更新時はデプロイ用ワークフロー自体が起動しません。元リポジトリ `dyson-yamashita/pufu-lens-stock` の `main` 更新だけがデプロイ対象です。forkのPRや別ブランチからはデプロイしません。文書だけの変更でも、main更新時はデプロイ用ワークフローの対象です。

初期設定として、リポジトリの **Settings → Environments → New environment** で `production` を作成し、Environment secretsに次の2つを登録してください。値をIssue・PR・チャットや設定ファイルに貼り付けないでください。

| Environment secret      | 内容                                                 |
| ----------------------- | ---------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`  | この本番アカウントに範囲を限定したデプロイ用トークン |
| `CLOUDFLARE_ACCOUNT_ID` | 本番Worker・D1・R2を所有するアカウントID             |

同じ `production` Environmentの **Secrets** に次の3つを登録してください。Workflowはこれらを本番ビルドにだけ渡します。未設定・不正値ならビルドで停止し、本番DBやWorkerは変更しません。

| Environment secret | 内容                     |
| ------------------ | ------------------------ |
| `APP_URL`          | 実際のHTTPSオリジン      |
| `D1_DATABASE_ID`   | 本番D1データベースのUUID |
| `OAUTH_KV_ID`      | 本番OAuth KVの32桁ID     |

これら3つは認証情報ではありませんが、Actionsログで登録値をマスクするためSecretsで管理します。同名のVariablesから移す場合は、Secretsへの登録を確認してからVariablesを削除してください。マスクは変換後の値や過去のログ・Git履歴まで隠すものではありません。

APIトークンは [Cloudflare公式のCI/CD手順](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/) の「Edit Cloudflare Workers」テンプレートを基に作成し、このアプリが利用するリソースの権限だけを付けてください。D1マイグレーションにはアカウントの **D1: Edit** が必要です。既存のR2・AIなどのバインディングに必要な参照権限を維持し、別アカウント、不要なゾーン、Global API Keyへのアクセスは与えないでください。

`production` の **Deployment branches and tags** は **Selected branches and tags → Branch: main** に制限してください。マージ後すぐの自動実行にする場合はRequired reviewersを設定しません。GitHubのmainブランチ保護・RulesetでPR経由の変更と `Check` の成功を要求し、ワークフローや依存関係を含む変更をレビューしてください。ワークフロー内の条件だけでは、mainへ悪意ある変更を書き込める管理者からSecretsを保護できません。

### mainへの直接pushを禁止する

GitHubのRulesetは、PRのマージだけでは有効になりません。設定定義は [.github/main-ruleset.json](../.github/main-ruleset.json) にあります。`main` への更新にはPRを必須とし、force pushとブランチ削除を禁止します。管理者を含めてルールのバイパスを許可しません。個人で運用できるよう、他者による承認の必須件数は0件です。

この定義は直接pushの禁止を対象とし、必須ステータスチェックは含みません。上記の `Check` 成功もマージ条件にする場合は、GitHubでそのチェックを追加設定してください。

管理権限のあるアカウントで、リポジトリのルートから適用します。既存の同名Rulesetがある場合は新規作成せず、そのルールを更新してください。

```sh
gh api --method POST repos/{owner}/{repo}/rulesets --input .github/main-ruleset.json
gh api repos/{owner}/{repo}/rulesets
```

[GitHubの提供条件](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)により、Freeの非公開リポジトリでは利用できません。対応プランを使うか、公開化した後で適用します。設定ファイルの追加やローカルのGitフックだけでは、サーバー側の直接pushを禁止できません。適用後はSettingsのRulesetsで有効状態、対象 `main`、バイパスなしを確認してください。

### 自動デプロイの実行順

実行順は次のとおりです。

1. [共通の検証ワークフロー](../.github/workflows/validate.yml) をSecretsなしで実行します。型チェック・lint・整形チェック・ビルド・依存監査のジョブと、Vitestの全テストを2分割したジョブを並列実行します。各ジョブで `pnpm install --frozen-lockfile` を行い、テストの内容・分離設定・実行対象は変えません。片方のテストが失敗しても残りの分割は実行し、すべての検証が成功した場合だけ従来の必須チェック `Check` が成功します。失敗・キャンセル・スキップは成功扱いにしません。並列化により同時に使うランナー数は増えます。ローカルの `pnpm run check` は従来どおり全検証を実行します。
2. デプロイジョブの `pnpm install --frozen-lockfile` はSecretsを渡さず実行します。`pnpm run build:production` にだけEnvironment secretsの `APP_URL`、`D1_DATABASE_ID`、`OAUTH_KV_ID` を渡します。Cloudflareのデプロイ認証情報やGoogle OAuthのSecretはビルドに渡しません。
3. 最後のステップだけに `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` のSecretsを渡し、未設定なら値を表示せず停止します。未適用の本番D1マイグレーションを順に適用し、成功後に `pnpm run deploy:workers` でPDF専用Worker、本体Workerの順に更新します。PDF専用Workerの配置が失敗したら本体の更新を行いません。

依存関係は `pnpm-lock.yaml` と `pnpm install --frozen-lockfile` で固定します。脆弱性対策のoverrideと依存パッケージのビルド許可は `pnpm-workspace.yaml` にまとめ、許可済みの `esbuild`・`sharp`・`workerd` のビルドスクリプトだけを実行します。従来から実行していない `core-js-pure` のインストールスクリプトは、pnpm 11でも実行しないよう明示しています。開発用のWranglerも明示的な依存として固定しています。

pnpm 11の公開後24時間の待機設定を維持しつつ、ロックファイルに固定・検証済みの `@goto-lab/pufu-editor@0.9.19` と `@napi-rs/canvas@1.0.13` およびそのOS別パッケージの同じバージョンだけを `minimumReleaseAgeExclude` に列挙しています。別バージョンや新しい依存は、この例外の対象になりません。

同一mainのデプロイは直列実行し、実行中の処理は後続pushでキャンセルしません。待機中の古い実行はGitHubのconcurrencyにより最新の実行へ置き換わる場合があります。マイグレーション後にWorker更新が失敗しても、成功済みのDB変更は戻りません。マイグレーションは旧Workerとも動く追加的な変更にし、削除・破壊的な変更は別途手順を検討してください。再実行では適用済みのマイグレーションをスキップします。

Googleの `GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET` はCloudflareのWorker Secretに保持し、GitHubへ複製しません。古いActions実行を再実行すると当時のコミットがデプロイされるため、対象コミットを確認してください。`.dev.vars*`・`.env*`・`.wrangler/`・`dist/` は引き続きGit管理対象外です。D1のIDや公開URLは接続先を識別する情報で、アクセス権を与える認証情報ではありません。新しい秘密をWranglerの `vars` やViteの `VITE_*` に設定しないでください。

Actionsはcheckout/setup-node/pnpm/action-setupをコミットSHAで固定し、`GITHUB_TOKEN` は `contents: read` のみに制限しています。checkoutの認証情報保持と依存キャッシュを無効にし、ビルド成果物やログファイルをArtifactsへアップロードしません。PRの検証に本番Secretsは不要です。公開リポジトリではActionsログも公開される前提で、環境変数の一覧表示やshellのトレースを追加しないでください。[GitHubの安全な利用ガイド](https://docs.github.com/en/actions/reference/security/secure-use)

## iOSショートカット

「ショートカット連携」画面の送信先URLは、`/api/config` の `appUrl` に返すサーバー設定 `APP_URL` のオリジンから生成します。許可されたローカルデモのLAN接続では、その端末から届くオリジンを返し、iPhone向けの設定例にlocalhostが混ざらないようにします。保存先を選ぶと、取得済みの本人のプロジェクトIDをJSON例へ反映します。トークンの全文は再取得せず、発行時にコピーした値を利用者が設定します。

1. Web画面にログインし、「ショートカット連携」でトークンを発行します。端末ごとに発行し、必要なら特定のプロジェクトに限定してください。
2. iPhoneのショートカットを作成し、「共有シートに表示」をオンにして「URL」と「SafariのWebページ」を受け取るようにします。
3. 「入力からURLを取得」を追加し、入力を「ショートカットの入力」にします。記事は1件ずつ共有し、複数のURLがある場合は先頭の1件を選びます。
4. 保存先を毎回選ぶ場合は「URLの内容を取得」で次をGETし、返された `projects` の名前から選択して `id` をJSON本文の `project_id` に指定します。固定のプロジェクトIDを登録しても構いません。`project_id` は任意で、省略時はプロジェクト限定トークンなら限定先、限定なしトークンなら自分の全プロジェクトに保存します。限定トークンの保存先と異なるIDを指定すると `403` になります。

   ```http
   GET https://実際のホスト/api/v1/projects
   Authorization: Bearer <発行したトークン>
   ```

5. 「URLの内容を取得」の送信先に**アプリの保存API**を指定し、方法をPOST、本文形式をJSONにします。`url` はテキスト型の値に手順3で取得した記事URLのマジック変数（複数時は先頭の1件を選んだ結果）を指定し、説明文をそのまま送らないようにします。

   ```http
   POST https://実際のホスト/api/v1/stocks
   Authorization: Bearer <発行したトークン>
   Content-Type: application/json
   Idempotency-Key: <この保存操作のUUID>

   {
     "url": "共有シートから受け取った記事のURL",
     "note": "任意のメモ"
   }
   ```

6. 受付結果の `id` を確認して通知を表示します。新規保存は `202`、すべて保存済みの場合や同じ保存の再送は `200` です。全プロジェクトへの保存では代表となる1件の `id` が返ります。要約とメモリは非同期で更新されます。

通信の再試行には同じUUIDを使います。同じキーで内容を変えた場合は `409` になります。キーは30日間保持します。全プロジェクトへの保存後にプロジェクトを追加しても、同じキーの再送では追加先に保存しません。同じプロジェクト・同じ記事の重複も別途防止します。

トークンには「プロジェクト一覧取得」「記事保存」のみを許可します。発行時以外にはトークン全体を表示しません。サーバーには256ビットのランダム秘密値のSHA-256ハッシュのみを保存します。発行可能な有効トークンは無期限を含めて20個です。有効期限は1〜365日または無期限で、無期限でも手動で失効できます。発行APIの `expires_days` は日数を指定し、`null` を指定すると無期限、省略すると90日になります。無期限の場合、一覧APIの `expires_at` は `null` です。

## 開発と検証

変更は最新のmainから作成したブランチで行います。検証と独立エージェントによるレビューを完了してからPRを作成します。具体的な手順は [AGENTS.md](../AGENTS.md) と[開発用スキル](#開発用スキル)を参照してください。

```sh
pnpm run check
```

型チェック、lint、Vitest、整形チェック、クライアント／Workerのビルドを実行します。テストはMiniflareのD1・R2と実際のアプリのルートを使用します。Workflow基底クラスとAI・記事HTTP応答はテスト内で差し替えます。Cloudflare Workflowsの永続化・リトライそのものはNodeテストの対象外で、ローカルWorkersでもデモの処理を確認します。

各テスト環境は独立したMiniflare・D1・R2・KVを作成します。初期化では実際の移行SQLをファイル順にWorker内で適用し、SQLの準備によるNode／Worker間の同期RPCを減らします。各ファイルのトランザクション境界と、旧スキーマからの移行テストで使う `applyMigration` は維持します。共有するのは移行SQLの読み込み結果だけで、DBや保存データは共有しません。

`pnpm run audit` で依存関係を検査できます。インストール・ビルドと同じpnpm 11.28.6で `pnpm audit --audit-level=high` を実行し、Bulk Advisory APIを使用します。監査用に別のpnpmを取得する処理はありません。high以上の脆弱性と監査APIのエラーは引き続きCIを失敗させます。開発用Miniflareの脆弱な間接依存を避けるため、`undici` と `sharp` に更新済みバージョンのoverrideを指定しています。

開発サーバーの起動中に `pnpm run test:smoke` を実行すると、MDNの公開記事を取得し、実際のローカルWorkers・Workflows・R2・D1を通して保存と問い・メモリの生成を確認します。この検証で作成したプロジェクトと記事は終了時に削除します。デモ環境専用で、本番には接続しません。

### ブラウザーE2E

`e2e@0.21.3` と `@e2e-dev/web@0.15.3` を開発用workspaceに固定します。`pnpm run e2e:ci` は実際のビルド済みアプリ、ローカルWorker、使い捨てD1・R2・KVで、テキスト保存と再読込、実Editorでのプ譜編集・局面履歴、公開確認と匿名アクセス・非公開化を確認します。desktopとphoneの画面幅で同じシナリオを実行します。

`pnpm run e2e:record` はローカルCodexで操作を選択し、`expect` が確認した記録を保存します。CIはその記録をread-only/strictで再生し、欠損や再生失敗でもAIへ切り替えません。既存Vitestを維持し、権限・入力・競合の検証をE2Eへ移しません。CIは全ケースを品質チェック・Vitestと並列実行し、全件実行・skipなし・AI利用ゼロも確認します。

`packages/e2e/scenarios.json` に検証観点と担当ソースを記録し、`e2e:check` で実テストと照合します。`e2e:related` は変更に関連するケースを選び、共通・未分類のアプリ変更は全件へ広げます。台帳は初期3ケースの対応表で、全APIの網羅率を表しません。外部認証・外部AI・実機Safariは対象外です。実行後はGit管理外の `packages/e2e/.e2e/runs/<実行ID>/index.html` に静的HTMLレポートを生成します。保存済みJSONからは `pnpm run e2e:report` で再生成でき、テストやAIは起動しません。セットアップ、CLIアダプターの前提、記録の更新、結果の確認は [E2Eの説明](../packages/e2e/README.md) を参照してください。

### 開発用スキル

このリポジトリには [Superpowers](https://github.com/obra/superpowers) v7.0.0の15スキルと、既存コード向けの最小限のテストを作る `pragmatic-testing` を `.agents/skills/` に同梱しています。`pragmatic-testing` は指定された本文のまま保存しています。

セキュリティ診断・脆弱性レビュー向けに、[Cloudflare security-audit-skill](https://github.com/cloudflare/security-audit-skill) の `security-audit` を参照資料・レポート用JSONスキーマ・検証スクリプトとともに同梱しています。スキル本文と補助ファイルは原文のまま保存し、取り込み元コミットは [.agents/security-audit-source.json](../.agents/security-audit-source.json)、MITライセンスは [.agents/SECURITY-AUDIT-LICENSE](../.agents/SECURITY-AUDIT-LICENSE) に記録しています。付属バリデーターのテストは `node --test .agents/skills/security-audit/*.test.cjs` で実行できます。

[AGENTS.md](../AGENTS.md) に開始時の読み込みとスキルの使い分けを記載しています。PR作成前に `security-audit` の `standard` プロファイルでscoped runを実行します。最新の `origin/main` と作業ブランチの共通祖先からの修正差分（未コミットの変更・追加ファイルを含む）と、差分が依存する呼び出し元・権限制御を必要に応じて確認し、対象範囲・結果・未確認事項をPRに記載します。対応が必要な指摘を修正した後は、必要な検証と再監査を実施します。続いて [requesting-code-review](../.agents/skills/requesting-code-review/SKILL.md) を使い、独立したレビュー担当エージェントが変更全体を確認します。対応が必要な指摘を修正した後は、必要な検証と再レビューを実施します。Superpowersの取り込み元コミット・スキル一覧は [.agents/superpowers-source.json](../.agents/superpowers-source.json)、MITライセンスは [.agents/SUPERPOWERS-LICENSE](../.agents/SUPERPOWERS-LICENSE) にあります。補助スクリプトを含むスキルの原文を維持するため、`.agents/skills/` はアプリ用のESLint・Prettierの対象外です。

## ソース構成

- `src/`：Reactの日本語管理画面
- `server/api.ts`：認証を必要とするAPIとアクセス制御
- `server/auth.ts`：Googleログイン、セッション、トークン認証
- `server/ingest.ts`：URL検証付きの取得、本文抽出、ブラウザ対応
- `server/ai.ts`：記事要約、問い、根拠付きメモリの生成
- `server/pufu.ts`：プ譜の生成
- `server/usage.ts`：保存・AI処理の利用量制限
- `shared/`：クライアントとサーバーで共有する型・入力検証
- `server/workflows.ts`：記事・メモリの非同期処理
- `migrations/`：D1のスキーマ
- `tests/`：認証、二重保存、削除、メモリ競合、処理パイプラインの検証
