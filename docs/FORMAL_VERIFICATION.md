# 境界処理の形式検証

MCP・iOSショートカット・SNS連携など、外部入力・認証主体・権限・公開範囲・処理世代が切り替わる場所で、守るべき条件をLean 4のモデルと実装のテストで確認する。開発時の必須ルールは [AGENTS.md](../AGENTS.md#境界処理の形式検証) に置く。

この文書は、必須となる変更の判断方法と、各対象のモデル・実装・テストの対応を記録する。現在の最小モデルはB00〜B16。

## 適用する変更

| 変更                                                                       | 必要な対応                                                                                     |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| MCPツール、ショートカット用API、SNS連携などの入口を新設する                | 許可・拒否・状態遷移をモデル化し、証明・変異検出・実経路の照合テストを追加する                 |
| 認証、スコープ、所有者、許可プロジェクト、期限、失効、公開条件を変更する   | 影響する入口を列挙し、共通モデルを更新する。各入口が同じ条件を使うことを実装のテストで確認する |
| revision、request_id、再送、非同期ジョブの世代、削除後の書込条件を変更する | 成功・拒否・再送・競合の状態遷移と、守るデータの範囲を更新する                                 |
| 共通ヘルパー、SQL、DBトリガー、キャッシュキー等を通じて上記条件を変える    | 入口のファイルを変えなくても適用する。モデル・テストへの影響を調査する                         |
| 説明文、レイアウト、表示だけのキーボード操作を変更する                     | 新しい形式証明は対象外。判断理由と通常の確認結果をPRに記載する                                 |
| このルールや対象一覧を更新する                                             | 参照先・記述の整合性を確認する。新しい製品モデルの証明は不要                                   |

「ショートカット」は本サービスのiPhone共有シート連携を指す。キーボードショートカットという名前だけを根拠に検証対象にはしない。ただし保存・削除・権限判断の経路を変える操作は適用対象となる。

変更しない既存境界を一度にすべて証明することは要求しない。一方、既存境界の許可条件や遷移を今回変更する場合は、その対象が未着手でも検証を追加する。既存モデルを再利用できる場合は、同じ証明を入口ごとに複製せず、モデルの適用範囲と各実装の照合を追加する。

## 各対象で残すもの

1. **仕様の根拠:** 対象一覧のID、操作、実際の入口、認証・認可、DB/ストレージ/外部通信までの経路。コードと既存テストを確認してから性質を確定する。
2. **最小モデル:** 認証主体、必要な権限、許可・拒否、保護する状態と遷移。暗号や外部サービス、SQLトランザクション等を抽象化する場合は、その前提を明示する。新しい権限ルールや正常系の仕様を作らない。安全性を左右する認証・権限・世代等の条件は個別に表現し、単一のvalidフラグに隠さない。抽象化した前提の正しさは証明対象外として明示し、正常系・拒否系に到達できる具体例または存在証明を追加して前提の矛盾による空虚な成立を避ける。
3. **定理と変異検出:** 正常系、権限不足、期限・世代・revision等の不一致を、対象に応じて証明する。`sorry` / `admit` を残さず、検証する結論を公理として導入しない。安全条件を除いたモデルでも同じ定理が通る場合は、モデル・定理を見直す。環境・依存取得・構文の失敗だけでは、意図した証明失敗の確認としない。全対象の定理について推移的な公理依存をCIで調べる。許可リストはpropext・Classical.choice・Quot.soundとし、sorryAx・未承認の独自公理・native_decide等によるコンパイラ評価公理は拒否する。方針を変えるときは、追加する信頼対象と理由をレビューする。
4. **実装の照合:** 既存のVitest・Miniflare等を使い、実際のHTTP/MCP入口とローカルDB等を通す。正常系・拒否系・再送を観測し、モデルの条件が実装でも使われているか確認する。外部サービスはダミー応答や送信直前の観測で代替し、実サービスの安全性まで保証したとは書かない。
5. **CIと結果:** 新設・変更した全モデルの対象ID・モジュール・ビルド・変異検出・照合テストを [登録表](../formal/targets.json) に記録する。共通ランナーが未登録ソースを拒否し、証明・公理監査・変異検出を実行する。関連テストも共通workflowで実行し、必須 `Check` へ失敗を伝える。モデルをファイルとして追加するだけで、既存のビルドや変異検出から漏らさない。対象のREADMEとPRにコマンド、結果、未検証事項を記載する。

実行環境が用意できない、証明が失敗する、テストが中断される等の場合は、実施した範囲と阻害要因を記録し、検証完了・マージ可能とは報告しない。既存実装の問題は修正案とともに報告し、無断の仕様変更や期待値の緩和で解消しない。

### 拒否時の不変性を定義する注意点

拒否時に守る状態を「DB全体」と一括指定せず、操作に応じて列挙する。

- [authenticate](../server/features/auth/auth.ts) は有効なショートカットトークンを認証すると `api_tokens.last_used_at` の更新を予約する。その後にAPIの許可判定で拒否されても、利用記録は業務データと区別する必要がある。
- [ストック保存](../server/api/routes/stock-collection.ts) は、保存先を指定しない全プロジェクト許可の要求を本人の全プロジェクトへ保存する。単一プロジェクトへの保存だけを正常系と仮定しない。`Idempotency-Key` も任意であり、省略時に同じ再送規則を仮定しない。
- [MCP接続設定](../server/mcp/oauth.ts) は、スコープを元の認可との積集合で制限する一方、対象プロジェクトは本人が接続設定で選び直せる。「初回に選んだプロジェクトから拡張できない」という規則を追加しない。実際の制約と最新設定の適用を調べる。
- [既存update_pufuモデル](../formal/verification/specs/mcp-update.md) の任意の拒否時不変性は、局面が初期化・同期済みという前提を持つ。権限のある要求のrevision競合でも旧局面の同期が走る既存挙動を、ほかの境界へ無条件に一般化しない。

### 失効・削除・非公開化の判定時点

各対象で、変更がDBへ確定する時点、認証・状態を読む時点、保存が確定する時点、応答を開始する時点を区別する。逐次モデルの「失効後は拒否」を、既に認証を終えた要求の取消しまで保証するものとして扱わない。

| 対象                 | 現行実装が確認する時点                                                    | 別に検証・仕様決定する範囲                                                                      |
| -------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| B02 ショートカット   | authenticateのトークンDB照会時に失効・期限を確認する                      | 認証後の失効・期限切れと保存確定の競合。保存直前の再確認や実行中要求の取消しは保証しない        |
| B03 MCP              | handleMcpの接続設定読込時、refreshのtokenExchangeCallbackで設定を確認する | 設定読込後に失効・権限変更された実行中要求。発行済みの認可情報の利用と新規refreshの拒否を分ける |
| B06 匿名公開         | 公開条件やキャッシュ世代をDB照会する時点で判定する                        | その後の非公開化と読込・送信の競合。応答済みデータの回収や送信中の中断は保証しない              |
| B07/B12 共有画像/SNS | 画像はR2読込後にも再確認。SNSは外部取得前に資格情報を読む                 | 最後の確認後の変更、SNSの読込済み資格情報による要求の取消し等は各対象で明示する                 |

これらの強い取消し保証を新設する場合は、実装を調べて遷移・条件付き書込・テストを追加する。文書上の言い換えだけで既存実装にその保証があるとは扱わない。

## 既存の対象と優先順位

調査基準は `d77cf52`（PR #264を取り込んだmain）。以下は主な境界の候補一覧であり、全機能の網羅的なセキュリティ監査や、不具合の認定ではない。

- **P0:** 複数入口に共通する権限、外部・匿名から本人データに届く条件、外部サービスの資格情報の所有者と利用条件。最初に整備する。
- **P1:** 再送・競合・旧結果・削除・資源予約など、条件の組合せで状態が壊れ得る境界。P0のモデルを使って段階的に追加する。
- **P2:** ほかの境界にも対象を広げる候補。関連仕様を変更するときは、優先度に関係なく必須ルールを適用する。

`B00`を維持し、`B01`〜`B12`とP2候補を採番した`B13`/`B14`に**最小モデル・証明・変異検出・照合テストを追加**した。各IDの全実装を完全検証したという意味ではない。証明した個別条件、定理と実装/テストの対応、残る未検証範囲は[モデル別の仕様一覧](../formal/verification/README.md#対象と対応表)を参照する。TypeScriptテストの成功は数学的証明とは区別する。

B04はLeanで安全条件と成功・拒否への到達を証明し、作成・局面追加・再送・競合・権限変更の操作列をVitestで照合する。 [B04の仕様とMBT](../formal/verification/specs/mcp-writes.md#操作順序のmbt)

SNSはB12として主要対象に含める。現行のX連携は利用者がBearer Tokenを登録する方式であり、SNS用OAuth認可・refreshや投稿機能はこの調査では仮定しない。`configured` はローカルの登録状態で、X側でのトークンの有効性を保証しない。暗号方式自体の正しさ、X側の失効、削除前に読み出し済みの資格情報を使う実行中リクエストの取消しは未検証として分ける。ほかのSNSを導入するときは、プロバイダーごとの所有者・必要権限・失効・取得/投稿等の操作範囲を調べ、同じルールで対象一覧を更新する。

P2の追加候補も次のIDで最小モデルを追加した。

- **B13 / P2 — Pushの登録・解除・配信:** セッションに結び付く同意と購読の所有者、解除・ログアウト後の配信判定、再試行時の二重配信条件を検証する。[配信](../server/features/announcements/push-delivery.ts)、[pushテスト](../tests/push.test.ts)、[push-delivery](../tests/push-delivery.test.ts)。外部Pushサービスへ渡った通知の回収や厳密な一度だけの到達は仮定しない。
- **B14 / P2 — 添付画像/PDF・AI出力の取込み:** 所有者、入力サイズ・形式・状態、ストレージ保存を確定する条件を先にモデル化する。画像/PDFパーサーやLLMの内容全体の正しさを小さなモデルで証明したとは書かない。[stock-images](../server/features/stocks/stock-images.ts)、[PDF](../server/features/stocks/pdf/pdf.ts)、[stock-imagesテスト](../tests/stock-images.test.ts)。
- **B15 / P1 — テキストストックの本文編集**。本人のWebセッション、現在の記事参照と世代、テキスト種別を確認し、拒否や同文再送では本文・関連・世代・ジョブを維持する。共有中は編集したストックだけを付け替え、公開先の別コピーを保持する。本文編集は関連メモリの旧世代を失効させる。要約の世代確定はB08で検証する。[仕様と実装の対応](../formal/verification/specs/text-stock.md)、[本文テスト](../tests/text-stocks.test.ts)。

- **B16 / P1 — 期間の振り返り**。本人のWebセッション、周期設定の所有者、再生成の世代と利用枠、自動追加の締めと未回答の扱いを確認する。生成結果と回答は現在の世代と所属を照合して確定する。プロジェクト削除後に遅れた生成結果を確定しない。[モデルと実装の対応](../formal/verification/specs/reflections.md) [照合テスト](../tests/reflections.test.ts)

## 今回の実施範囲と今後の拡張

B00〜B16の証明対象と限界は[モデル別の詳細仕様](../formal/verification/README.md#対象と対応表)に記載する。共通CIは登録したすべてのモデルをビルドし、公理依存・安全条件の変異検出を行う。登録テストは既存のVitestジョブに含まれる。

今後は境界の仕様を変更する際に、今回の抽象化から外れる条件・状態・判定時点を追加する。たとえば失効後の実行中要求を止める保証、DBとR2をまたぐ全並行性、全ツールの応答情報量、外部Pushの重複配送は、最小モデルの成功だけで検証済みにしない。実装の問題を見つけた場合は問題と修正案を報告し、仕様を無断で変更しない。

## 既存の実行基盤と保証の限界

Leanの固定バージョン、配置方針、ビルド・変異検出の実行対象、CIへの登録方法は [形式検証の共通README](../formal/README.md) を参照する。新しい対象を追加するときは、[モデルの対応表](../formal/verification/README.md#対象と対応表)と対象固有の仕様、本書の対象一覧を更新する。外部Leanライブラリを増やす前に、既存の最小構成で表現できるか確認する。

B00〜B16は[同じLakeプロジェクト](../formal/verification/README.md)で管理する。

Leanが証明するのは、明示した前提の下の抽象モデルの性質である。TypeScript/SQLとの自動的な同値性、暗号・OAuthライブラリ、DNSと実接続、D1/R2の障害・原子性、外部サービスやブラウザー/OSの挙動は、モデルに含めて証明しない限り保証されない。実装との照合、実環境の設定確認、通常のテスト・レビュー・セキュリティ監査を引き続き行う。
