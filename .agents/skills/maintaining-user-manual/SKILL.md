# ユーザーマニュアルのメンテナンス

基本操作を短く案内するマニュアルを、実際の機能と一致させる。修正履歴は掲載しない。

## 参照先

- 本文の唯一の編集元：`src/UserManual.tsx`（公開URLは `/manual`）。同じ説明を別のMarkdownなどへ複製しない。
- 導線：`src/main.tsx`、`src/App.tsx`。表示：`src/styles.css` の `manual-*`。
- 実装・画面を確認し、必要に応じて `docs/SPEC.md` と照合する。設計書だけを根拠に未実装の機能を案内しない。

## 更新するかの判断

「この変更後も、利用者は今の説明で同じ操作・判断ができるか」で決める。変更行数や「バグ修正」という分類では決めない。

| 変更の影響 | 判断 |
| --- | --- |
| 機能の追加・削除、基本の操作手順や入口の変更 | 該当箇所を更新 |
| 利用条件、連携に必要な設定、取得できる情報の範囲の変更 | 該当箇所を更新 |
| メモリの対象、公開範囲、閲覧・編集の権限の変更 | 該当箇所を更新 |
| 変更後に既存の説明が誤りになる | 修正規模にかかわらず更新 |
| 文言・名称・アイコン・色・余白・レイアウトの微調整で操作は同じ | 更新しない |
| 性能・安定性・セキュリティ・依存ライブラリ・内部実装の改善で、利用者の手順と既存説明は同じ | 更新しない |

例：公開設定を新設したら、設定の場所・保存・URL共有と公開対象を追加する。カードを小さくしただけなら本文も更新日も変えない。1行の修正でも公開対象が変われば説明を直す。

## 手順

1. 最終的な差分と関連する画面・処理を確認し、上の基準で判断する。基本操作も説明の意味も変わらない場合は、マニュアルを変更せず終了する。
2. 更新が必要な場合だけ、該当する節を最小限で追加・修正・削除する。操作は短い手順で、利用条件や公開範囲は必要な補足にまとめる。専門用語や内部API、細かな表示値を増やさない。
3. 現在の機能を説明する。変更履歴、リリースごとの節、全修正の一覧を追記しない。無関係な節や日付だけの更新もしない。
4. 変更した説明を実装と照合する。特に公開対象・メモリ対象・取得範囲を確認する。画面や目次を変えた場合は、`/manual` の表示・リンク・スマホとダークモードを確認する。検証はリポジトリの既存コマンドを使い、文章をそのまま照合するだけのテストを増やさない。
5. PRの検証欄に、更新した内容、または「マニュアル更新なし：基本操作・利用条件・既存説明に変更なし」のように判断理由を1行で記載する。
