# 境界処理の形式検証: 共通基盤

MCP、iOSショートカット、SNS連携、匿名公開、非同期ジョブなどの形式検証に共通する、環境・配置・実行対象・CIへの登録方法を案内する。

必須ルールは [AGENTS.md](../AGENTS.md#境界処理の形式検証)、適用条件・検証候補・優先順位は [検証方針と対象一覧](../docs/FORMAL_VERIFICATION.md) を参照する。モデルの前提・定理・実装との対応・照合テスト・未検証事項は、各対象のREADMEで管理する。

## 環境と配置

- 現在の固定Leanバージョンは **4.24.0**。実装済みプロジェクトの [lean-toolchain](mcp-verification/lean-toolchain) に指定している。新しいプロジェクトも同じ固定版から始め、変更する場合は影響するプロジェクトとCIを確認する。
- elanのbinディレクトリをPATHに含める。現行の変異検出スクリプトはPython 3、TypeScriptの照合テストはリポジトリ所定のNode.js/pnpmを使う。CIのelanは4.1.2に固定している。
- 外部Leanライブラリを増やす前に、既存の最小構成で表現できるか確認する。現在のプロジェクトはMathlib等に依存しない。
- 対象の責務に応じて `formal/` 配下にモデル・証明・変異検出・READMEを配置する。既存の共有コードは再利用し、他の境界のモデルをMCP専用として扱わない。新しいプロジェクトにはLake設定と固定版の `lean-toolchain` を含める。

## 実装済みの対象と実行方法

以下のコマンドはリポジトリルートから実行する。現在、実装済みのモデルは **B00: MCP update_pufuのみ**。この実行でショートカット・SNS等まで検証したことにはならない。未着手の候補は [対象一覧](../docs/FORMAL_VERIFICATION.md#既存の対象と優先順位) で管理する。

| ID / 対象               | プロジェクト・固有仕様                         | 証明のビルド                               | 証明と変異検出                             |
| ----------------------- | ---------------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| B00 / MCP `update_pufu` | [mcp-verification](mcp-verification/README.md) | `cd formal/mcp-verification && lake build` | `python3 formal/mcp-verification/check.py` |

実装の照合テストのコマンドと結果は各対象のREADMEを参照する。B00では [MCP PoCの実行手順](mcp-verification/README.md#実行) に記載している。

## 新しい対象を追加するとき

1. 対象一覧のIDと責務を確認し、対象のモデル・証明・変異検出・実経路の照合テストを追加する。既存モデルを使える場合も、適用できる前提と実装との対応を確認する。
2. この共通READMEの実装済み対象表に、対象のREADMEと実行コマンドを登録する。各対象のREADMEには固有の仕様・証明範囲・テスト・限界を記載する。検証方針の対象一覧の状態とリンクも更新する。MCP以外の対象を追加しただけでMCP PoC READMEの適用範囲を広げる必要はない。
3. 既存のLakeプロジェクトにモデルを加える場合は、importやビルド対象への登録を確認する。変異検出も対象の性質に合わせて追加する。Leanファイルが増えただけでは、ビルド・変異検出に含まれるとは限らない。
4. 次のCI登録を行い、登録した対象の証明・変異検出・関連テストのいずれかが失敗したら、必須 `Check` も失敗することを確認する。

## CIへの登録

[共通validate workflow](../.github/workflows/validate.yml) の `formal` ジョブは、現在は `python3 formal/mcp-verification/check.py` だけを実行する。対象表への追記だけでCIに自動登録される仕組みではない。

対象を増やしたときは、このジョブへ実行コマンドを追加するか、全登録対象を実行する共通の入口を実装し、workflowから呼び出す。現在の `check.py` の変異対象はupdate_pufu専用であり、他の対象の変異検出を代行する汎用ランナーではない。CIのジョブ名・実行内容も対象に合わせて更新する。

TypeScriptの照合テストは、現在のVitest設定が読み込む `tests/**/*.test.ts` に追加すれば、既存の4分割テストジョブに含まれる。別の場所や別の実行環境を使う場合は、CIで実行するコマンドも登録する。

Leanの証明は、明示した前提の下での抽象モデルの保証である。実装のテスト結果や実環境で確認したこと、未検証事項とは分けて記録する。現在のプロジェクト名やディレクトリ名を一般化するだけで、検証範囲が広がるわけではない。
