# 境界処理の形式検証: 共通基盤

MCP、iOSショートカット、SNS連携、匿名公開、非同期ジョブなどの形式検証に共通する、環境・登録・実行・CIの入口を案内する。

必須ルールは [AGENTS.md](../AGENTS.md#境界処理の形式検証)、適用条件・検証候補・優先順位は [検証方針と対象一覧](../docs/FORMAL_VERIFICATION.md) を参照する。固有の前提・定理・実装との対応・照合テスト・未検証事項は各対象のREADMEで管理する。

## 固定バージョンと更新方針

Leanは **4.36.0** に固定する。バージョンの正本は [targets.json](targets.json) のtoolchainで、各プロジェクトの `lean-toolchain` と一致しなければ共通ランナーが失敗する。elanのbinディレクトリをPATHに含め、Python 3とリポジトリ所定のNode.js/pnpmを用意する。CIのelanは4.1.2に固定している。

4.24.0を採用した初回PoCから、公式の [4.32.2](https://github.com/leanprover/reference-manual/blob/main/Manual/Releases/v4_32_2.lean)・[4.34.0](https://github.com/leanprover/reference-manual/blob/main/Manual/Releases/v4_34_0.lean) の健全性修正を考慮し、確認時点の最新安定版 [4.36.0](https://github.com/leanprover/lean4/releases/tag/v4.36.0) へ更新した。旧PoCの証明が誤っていたという判定ではない。

カーネル健全性の修正や依存関係の問題が公表されたとき、または新しい対象の標準バージョンを決めるときに、安定版の更新を評価する。更新時は登録した全対象のビルド・公理監査・変異検出・関連テストを再実行して固定する。更新できない場合は影響する対象、理由、再評価条件を記録する。外部Leanライブラリを増やす前に、現在のMathlib等に依存しない最小構成で表現できるか確認する。

## 対象の登録と配置

機械的な登録表は [targets.json](targets.json)。対象ID、プロジェクトのディレクトリ、全Leanモジュール、ビルド・変異検出のコマンド、実装の照合テストを一緒に管理する。共通コードを共有する複数の対象IDは同じプロジェクトの `ids` に記録できる。

現在の実装済み対象は **B00〜B15の最小モデル**。B00は[MCP update_pufu](mcp-verification/README.md)、B01〜B15は[認証・ショートカット・SNS等の境界処理](boundary-verification/README.md)に仕様と検証範囲を記載する。

新しい対象は、その責務に応じて `formal/` 配下へ配置する。固定版の `lean-toolchain` とLake設定を含め、共有できるコードは再利用する。MCP以外を追加したためにMCP PoCの適用範囲を広げる必要はない。

登録時には次を確認する。

- そのプロジェクトの全ソースモジュールを `modules` に登録する。共通ランナーは各モジュールを明示的にビルドし、ルートからimportされていない登録モジュールも対象にする。
- `formal/` に未登録のプロジェクトやLeanファイルがあれば失敗する。生成物の `.lake/` とLake設定用の `lakefile.lean` はモデルのソース一覧から除く。
- 照合テストは現行Vitestが読み込む `tests/**/*.test.ts` に登録する。ファイルの存在も検査する。別のテスト環境を使う場合は、登録形式とCI実行も合わせて拡張する。
- 変異検出の `mutations` は対象の性質に合わせたコマンドを登録する。現行の `mcp-verification/check.py` はupdate_pufu専用である。
- 登録表、対象自身のREADME、検証方針の対象一覧を一緒に更新する。登録漏れ検査は性質の網羅性や実装との同値性の証明ではない。

## 証明の公理依存

[verify.py](verify.py) は、登録モジュール由来の全定理（private宣言と生成された補助定理を含む）と公理を、宣言の名前空間ではなく定義元のモジュールで選択する。Leanの `collectAxioms`（`#print axioms` と同じ依存収集）で、補助定理・外部ライブラリを経由した間接依存も検査する。

許可する標準公理は **propext、Classical.choice、Quot.sound** のみ。`sorryAx`、独自公理、`native_decide` 等が導入するコンパイラ評価の公理はCIで拒否する。依存のない独自公理も、対象モジュールに宣言されていれば拒否する。許可リストの変更には、追加する信頼対象と必要性のレビューを伴わせる。

この検査はカーネルの健全性自体の証明ではない。Lean本体や標準ライブラリの更新・レビューも必要であり、カーネル以外への信頼が増える証明を黙って採用しない。

## 実行方法

以下はリポジトリルートから実行する。

```sh
# 登録漏れ・バージョン・照合テストのパスだけを確認
python3 formal/verify.py --check-only

# 全登録モジュールのビルド、公理監査、登録した変異検出
python3 formal/verify.py

# 上記に加え、登録したVitestの照合テストも実行（2 worker、上限30分）
python3 formal/verify.py --tests

# 検査機構自体の回帰テスト（Leanを使用）
python3 -m unittest discover -s formal -p 'test_*.py' -v
```

回帰テストは未登録ソース・プロジェクト、存在しない照合テスト、固定バージョンのずれを拒否することを確認する。また、間接的な独自公理・間接的なsorryAx・native_decide・privateモジュールの独自公理を含む4つの意図的違反について、ビルド成功後に公理監査が拒否することを確認する。構文・環境の失敗を拒否検出の成功に数えない。境界処理の変異ランナーについても、安全条件の削除と、検出されない変異・定義エラー・無関係な定理の失敗を区別する回帰テストを実行する。

## CIとGitHubのマージ保護

[共通validate workflow](../.github/workflows/validate.yml) の `formal` ジョブが、共通ランナーと検査機構の回帰テストを実行する。対象を登録すれば、このランナーがビルド・公理監査・変異検出を実行する。変異スイートはプロジェクトごとに5分で打ち切る（個別のLean検査は各ランナーでも制限）。B01〜B14を同じプロジェクトに登録したため、旧PoC用の3分から拡張した。登録した照合テストは既存の4分割Vitestジョブで実行する。新しい実行環境が必要な場合はCIのセットアップも更新する。

PRの [ci.yml](../.github/workflows/ci.yml) は全検証結果を `Check` に集約する。**workflowで失敗を集約することと、GitHubでマージを禁止する設定は別である。** mainの有効なルールセットまたはブランチ保護で、GitHub Actions由来の `Check` を必須ステータスチェックに指定する。推奨設定は更新済みブランチを要求し、バイパスを設けない構成である。設定後に適用先・有効状態・チェック名・提供元を読み戻して確認する。

設定の記録: PR #264時点の設定API書込は403で拒否され、PR #265の初回確認時にもチェックの配列は空だった。その後の管理者設定を受け、2026-11-17にmainの有効ルールを再度APIで読み戻し、`Check`（GitHub Actions、integration_id: 15368）が必須登録され、最新ブランチを要求する`strict_required_status_checks_policy=true`であることを確認した。これは設定の読み戻しであり、失敗したPRを実際にマージする実験や、従来のブランチ保護・全バイパス設定の網羅確認ではない。

Leanが保証するのは、明示した前提の下での抽象モデルの性質である。実装テスト、実環境の確認、実行中要求の取消し等の未検証範囲とは分けて記録する。
